# Тема 6: Dependency Injection, IoC и Spring Context

## Dependency Graph

**Определение:**

Dependency Graph — направленный граф, показывающий зависимости объектов друг от друга.

Например:

```text
PostController
      ↓
PostService
      ↓
PostRepository
```

Здесь:

```text
PostController depends on PostService
PostService depends on PostRepository
```

То есть зависимости приложения образуют не просто список, а целую структуру связей.

---

## Dependency Management

**Определение:**

Dependency Management — управление созданием, поиском и связыванием зависимостей между объектами.

Основные подходы из лекции:

```text
1. объект создаёт зависимость сам
2. объект ищет зависимость через registry
3. зависимость внедряет DI-контейнер
```

---

## Dependency Creation

**Определение:**

Dependency Creation — подход, при котором объект самостоятельно создаёт нужную ему зависимость.

Пример:

```java
public class PostService {

    private final PostRepository repository =
            new PostRepository();
}
```

Плюсы:

```text
просто
удобно
```

Минусы:

```text
сложно тестировать
сложно переиспользовать зависимости
сильная связанность
```

---

## Dependency Lookup

**Определение:**

Dependency Lookup — подход, при котором объект самостоятельно запрашивает нужную зависимость из специального реестра или контейнера.

Пример:

```java
PostService service =
        registry.get(PostService.class);
```

или внутри объекта:

```java
repository =
        registry.get(PostRepository.class);
```

Основной недостаток:

объект знает о существовании внешнего registry и становится связан с инфраструктурой.

---

## Registry

**Определение:**

Registry — объект-реестр, хранящий другие объекты и позволяющий искать их по имени или типу.

Условно:

```text
Registry
├── PostRepository
├── PostService
└── PostController
```

Получение:

```java
registry.get(PostService.class);
```

---

## Dependency Injection

**Определение:**

Dependency Injection (DI) — подход, при котором объект не создаёт и не ищет зависимости самостоятельно.

Необходимые зависимости передаются ему извне.

Пример:

```java
public class PostService {

    private final PostRepository repository;

    public PostService(PostRepository repository) {
        this.repository = repository;
    }
}
```

Сам `PostService` не знает:

* кто создал `PostRepository`;
* откуда он появился;
* кто управляет его жизненным циклом.

---

## DI Container

**Определение:**

DI Container — компонент, который:

```text
анализирует зависимости
        ↓
создаёт объекты
        ↓
связывает их
        ↓
внедряет зависимости
```

Например:

```text
PostController
      ↓
PostService
      ↓
PostRepository
```

контейнер сам создаёт в правильном порядке.

---

## Injection

**Определение:**

Injection — передача зависимости внутрь объекта извне.

Например:

```java
new PostService(repository);
```

Здесь `repository` внедряется в `PostService`.

---

## Constructor Injection

**Определение:**

Constructor Injection — внедрение зависимости через конструктор.

Пример:

```java
public class PostService {

    private final PostRepository repository;

    public PostService(PostRepository repository) {
        this.repository = repository;
    }
}
```

Это рекомендуемый подход в большинстве случаев.

Плюсы:

```text
зависимость обязательна
поле можно сделать final
объект нельзя создать в некорректном состоянии
проще тестировать
```

---

## Setter Injection

**Определение:**

Setter Injection — внедрение зависимости через setter.

Пример:

```java
public void setRepository(
        PostRepository repository
) {
    this.repository = repository;
}
```

Используется реже, обычно когда зависимость опциональна или может меняться.

---

## Field Injection

**Определение:**

Field Injection — внедрение зависимости непосредственно в поле через Reflection.

Пример:

```java
@Autowired
private PostRepository repository;
```

В лекции отмечено, что для application-кода этот подход обычно считается менее предпочтительным.

Основные причины:

```text
зависимость скрыта
сложнее тестировать
нельзя сделать поле final
объект можно создать в некорректном состоянии
```

---

## Inversion of Control

**Определение:**

IoC (Inversion of Control) — инверсия управления, при которой управление жизненным циклом и взаимодействием объектов передаётся framework или container.

Условно:

без IoC:

```text
наш код вызывает framework
```

с IoC:

```text
framework вызывает наш код
```

Например:

```text
Spring
   ↓
создаёт объект
   ↓
внедряет зависимости
   ↓
вызывает lifecycle-методы
```

---

## IoC Container

**Определение:**

IoC Container — контейнер, управляющий созданием, связыванием и жизненным циклом объектов приложения.

В Spring DI-container и IoC-container практически используются как близкие понятия.

---

## Spring Framework

**Определение:**

Spring Framework — framework для Java, предоставляющий DI/IoC-контейнер и множество инфраструктурных возможностей.

В контексте этой темы главное:

```text
Spring
   ↓
создаёт beans
   ↓
связывает dependencies
   ↓
управляет lifecycle
```

---

## Lightweight Container

**Определение:**

Lightweight Container — контейнер, который не требует от компонентов наследоваться от специальных framework-классов или реализовывать framework-интерфейсы.

Spring позволяет использовать обычные POJO.

---

## Bean

**Определение:**

Spring Bean — объект, который создаётся, хранится и управляется Spring-контейнером.

Важно:

```text
Spring Bean != JavaBean
```

Пример:

```java
@Service
public class PostService {
}
```

Если Spring создаёт этот объект и управляет им — это Spring Bean.

---

## BeanFactory

**Определение:**

BeanFactory — базовый интерфейс Spring-контейнера, отвечающий за создание и получение beans.

Пример:

```java
beanFactory.getBean(PostService.class);
```

Основная идея:

```text
Bean Definition
      ↓
BeanFactory
      ↓
Bean
```

---

## Bean Definition

**Определение:**

Bean Definition — описание того, как Spring должен создать bean.

Bean Definition может содержать:

* класс;
* имя bean;
* scope;
* зависимости;
* способ создания.

Например XML:

```xml
<bean
    id="postService"
    class="ru.example.PostService"/>
```

Это описание bean, а не сам объект.

---

## Bean Name

**Определение:**

Bean Name — имя bean внутри Spring-контейнера.

Например:

```text
postService
```

Получение:

```java
context.getBean("postService");
```

При Annotation Config имя обычно формируется из имени класса с маленькой первой буквы:

```text
PostService → postService
```

---

## `getBean()`

**Определение:**

`getBean()` — метод Spring-контейнера для получения bean.

По имени:

```java
context.getBean("postService");
```

По типу:

```java
context.getBean(PostService.class);
```

---

## Bean Scope

**Определение:**

Bean Scope — правило, определяющее, сколько экземпляров bean должен создавать Spring и как долго они живут.

Основные scope из лекции:

```text
singleton
prototype
```

---

## Singleton Scope

**Определение:**

`singleton` — стандартный scope Spring, при котором для одного Bean Definition создаётся один объект внутри контейнера.

Например:

```java
context.getBean(PostService.class)
==
context.getBean(PostService.class)
```

обычно возвращает один и тот же экземпляр.

Важно:

Spring Singleton — это singleton внутри конкретного Spring Context, а не обязательно глобальный singleton всей JVM.

---

## Prototype Scope

**Определение:**

`prototype` — scope Spring, при котором контейнер создаёт новый объект при каждом запросе bean.

Условно:

```java
var a = context.getBean(MyBean.class);
var b = context.getBean(MyBean.class);
```

```text
a != b
```

---

## Autowiring

**Определение:**

Autowiring — механизм Spring, автоматически подбирающий и внедряющий зависимости.

Например:

```java
public PostService(
        PostRepository repository
) {
    this.repository = repository;
}
```

Spring находит подходящий `PostRepository` и передаёт его в конструктор.

---

## Autowire by Type

**Определение:**

Autowire by Type — внедрение зависимости на основании её Java-типа.

Например:

```java
public PostService(
        PostRepository repository
)
```

Spring ищет bean типа:

```text
PostRepository
```

---

## Interface-Based Injection

**Определение:**

Interface-Based Injection — внедрение зависимости по интерфейсу, а не по конкретной реализации.

Пример:

```java
public class PostService {

    private final PostRepository repository;

    public PostService(
            PostRepository repository
    ) {
        this.repository = repository;
    }
}
```

Реализация:

```java
@Repository
public class PostRepositoryImpl
        implements PostRepository {
}
```

Преимущество:

```text
PostService зависит от абстракции,
а не от конкретной реализации
```

---

## `@Autowired`

**Определение:**

`@Autowired` — аннотация Spring, указывающая место, куда необходимо внедрить зависимость.

Можно использовать над:

```text
constructor
setter
field
```

Пример:

```java
@Autowired
public PostService(PostRepository repository) {
    this.repository = repository;
}
```

Если конструктор один, аннотация обычно не требуется.

---

## ApplicationContext

**Определение:**

ApplicationContext — основной интерфейс Spring-контекста приложения.

Он расширяет возможности BeanFactory.

Помимо DI предоставляет:

* работу с ресурсами;
* события;
* локализацию;
* environment;
* message source.

На практике используется значительно чаще, чем BeanFactory напрямую.

---

## Application Context

**Определение:**

Application Context — контейнер Spring, содержащий beans, их конфигурацию и инфраструктурные сервисы приложения.

Условно:

```text
ApplicationContext
├── PostController
├── PostService
├── PostRepository
└── Spring infrastructure beans
```

---

## `AnnotationConfigApplicationContext`

**Определение:**

`AnnotationConfigApplicationContext` — реализация ApplicationContext для конфигурации через аннотации и Java Config.

Пример:

```java
var context =
        new AnnotationConfigApplicationContext(
                "ru.example"
        );
```

или:

```java
var context =
        new AnnotationConfigApplicationContext(
                JavaConfig.class
        );
```

---

## Context Refresh

**Определение:**

`refresh()` — этап запуска ApplicationContext, во время которого Spring подготавливает контейнер и создаёт необходимые singleton beans.

Упрощённо:

```text
config
  ↓
refresh()
  ↓
BeanFactory setup
  ↓
BeanPostProcessors
  ↓
singleton initialization
  ↓
context ready
```

---

## Lazy Initialization

**Определение:**

Lazy Initialization — отложенное создание объекта только тогда, когда он действительно понадобился.

В лекции BeanFactory описана как более lazy:

```text
bean requested
      ↓
bean created
```

---

## Eager Initialization

**Определение:**

Eager Initialization — создание объектов заранее, при запуске контекста.

Для обычных singleton beans ApplicationContext обычно создаёт их во время `refresh()`.

---

## XML Config

**Определение:**

XML Config — способ настройки Spring через XML-файл.

Пример:

```xml
<bean
    id="postRepository"
    class="ru.example.PostRepository"/>
```

```xml
<bean
    id="postService"
    class="ru.example.PostService"
    autowire="constructor"/>
```

Spring читает XML и превращает его в Bean Definitions.

---

## Annotation Config

**Определение:**

Annotation Config — способ конфигурации Spring, при котором классы помечаются специальными аннотациями.

Например:

```java
@Service
public class PostService {
}
```

Spring сканирует классы и создаёт beans.

---

## Component Scanning

**Определение:**

Component Scanning — процесс поиска Spring-компонентов в указанных пакетах.

Spring ищет классы с аннотациями:

```text
@Component
@Service
@Repository
@Controller
```

и создаёт для них Bean Definitions.

---

## `@Component`

**Определение:**

`@Component` — базовая Spring-аннотация, обозначающая класс как компонент, который должен быть зарегистрирован как bean.

Пример:

```java
@Component
public class MailSender {
}
```

---

## `@Service`

**Определение:**

`@Service` — специализированная версия `@Component`, используемая для классов service layer.

Пример:

```java
@Service
public class PostService {
}
```

---

## `@Repository`

**Определение:**

`@Repository` — специализированная версия `@Component`, используемая для repository layer.

Пример:

```java
@Repository
public class PostRepositoryImpl {
}
```

---

## `@Controller`

**Определение:**

`@Controller` — специализированная версия `@Component`, используемая для controller layer.

Пример:

```java
@Controller
public class PostController {
}
```

---

## Stereotype Annotation

**Определение:**

Stereotype Annotation — специализированная аннотация Spring, показывающая роль компонента.

Основные:

```text
@Component
@Service
@Repository
@Controller
```

Они помогают не просто зарегистрировать bean, но и явно показать архитектурную роль класса.

---

## Java Config

**Определение:**

Java Config — способ конфигурации Spring через Java-код.

Используется специальный конфигурационный класс:

```java
@Configuration
public class AppConfig {
}
```

Bean создаётся методом:

```java
@Bean
public PostService postService() {
    return new PostService(postRepository());
}
```

---

## `@Configuration`

**Определение:**

`@Configuration` — аннотация, обозначающая класс конфигурации Spring.

Пример:

```java
@Configuration
public class AppConfig {
}
```

Методы с `@Bean` внутри него используются для создания beans.

---

## `@Bean`

**Определение:**

`@Bean` — аннотация над методом, результат которого Spring регистрирует как bean.

Пример:

```java
@Bean
public PostRepository postRepository() {
    return new PostRepositoryImpl();
}
```

Возвращаемый объект становится Spring Bean.

---

## Bean Method

**Определение:**

Bean Method — метод, помеченный `@Bean`, который описывает создание bean.

Пример:

```java
@Bean
public PostService postService(
        PostRepository repository
) {
    return new PostService(repository);
}
```

Параметр метода может автоматически использоваться для DI.

---

## Java Config with Method Parameters

**Определение:**

При Java Config зависимости можно передавать как параметры `@Bean`-методов.

Пример:

```java
@Bean
public PostService postService(
        PostRepository repository
) {
    return new PostService(repository);
}
```

Spring сам передаст подходящий bean `PostRepository`.

---

## Proxy

**Определение:**

Proxy — объект-посредник, который перехватывает вызовы к другому объекту и может изменить их поведение.

В лекции Java Config связывается с proxy-механизмом:

вызовы методов `@Bean` внутри `@Configuration` могут перехватываться Spring.

Это позволяет вместо обычного повторного создания объекта вернуть существующий singleton bean.

---

## Reflection API

**Определение:**

Reflection API — механизм Java, позволяющий во время выполнения анализировать классы, конструкторы, поля, методы и создавать объекты динамически.

Spring активно использует Reflection для:

* поиска constructors;
* создания beans;
* внедрения dependencies;
* анализа annotations.

---

## Bean Configuration

**Определение:**

Bean Configuration — описание того, какие beans существуют и как они создаются.

Основные способы из лекции:

```text
XML
Annotations
Java Config
Groovy
Kotlin
Programmatic registration
```

Наиболее распространённые:

```text
Annotation Config
Java Config
```

---

## Programmatic Bean Registration

**Определение:**

Programmatic Bean Registration — регистрация beans непосредственно через Java API Spring-контейнера.

То есть Bean Definitions создаются программно, без XML и component scanning.

---

## Circular Dependency

**Определение:**

Circular Dependency — циклическая зависимость между объектами.

Например:

```text
A depends on B
B depends on A
```

или:

```text
A → B → C → A
```

Такая структура часто указывает на проблему архитектуры.

---

## Ambiguous Dependency

**Определение:**

Ambiguous Dependency — ситуация, когда Spring находит несколько подходящих beans одного типа и не понимает, какой нужно внедрить.

Например:

```java
interface PaymentService {}
```

и два bean:

```text
CardPaymentService
CashPaymentService
```

При зависимости:

```java
PaymentService service
```

Spring не сможет автоматически выбрать один без дополнительной информации.

---

## Missing Dependency

**Определение:**

Missing Dependency — ситуация, когда Spring не может найти bean, необходимый для создания другого bean.

Например:

```java
public PostService(
        PostRepository repository
)
```

но ни одного `PostRepository` в context нет.

---

# Главное из темы

Самая важная идея:

```text
без DI
```

```java
PostRepository repository =
        new PostRepository();

PostService service =
        new PostService(repository);

PostController controller =
        new PostController(service);
```

```text
с DI
```

```text
Spring Container
      ↓
создаёт PostRepository
      ↓
создаёт PostService
      ↓
inject PostRepository
      ↓
создаёт PostController
      ↓
inject PostService
```

То есть:

```text
мы описываем зависимости
Spring собирает object graph
```

```text

```

```text
+

```

Практически всегда в обычном Spring-приложении используется:

```text
ApplicationContext
```

## Annotation Config

```java
@Repository
class PostRepositoryImpl {
}

@Service
class PostService {

    private final PostRepository repository;

    public PostService(
            PostRepository repository
    ) {
        this.repository = repository;
    }
}
```

Spring:

```text
сканирует классы
     ↓
создаёт Bean Definitions
     ↓
создаёт beans
     ↓
внедряет зависимости
```

---

## Java Config

```java
@Configuration
public class AppConfig {

    @Bean
    public PostRepository postRepository() {
        return new PostRepositoryImpl();
    }

    @Bean
    public PostService postService(
            PostRepository repository
    ) {
        return new PostService(repository);
    }
}
```

---

# Что важно для продакшена

В большинстве случаев предпочтительно:

```java
private final PostRepository repository;

public PostService(
        PostRepository repository
) {
    this.repository = repository;
}
```

То есть:

```text
Constructor Injection
+
final field
+
dependency by interface
```

Почему:

* зависимости видны сразу;
* объект нельзя создать без обязательной dependency;
* легче тестировать;
* меньше магии;
* проще поддерживать.
