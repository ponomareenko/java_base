# Тема 6: Spring Web MVC

## Spring Web MVC

**Определение:**

Spring Web MVC — web-framework из экосистемы Spring, построенный поверх Servlet API.

Он упрощает разработку HTTP/REST-приложений и берёт на себя типовые задачи:

```text
маршрутизация запросов
↓
поиск нужного Controller
↓
подготовка параметров метода
↓
вызов handler
↓
сериализация ответа
```

То есть вместо ручного:

```java
if (method.equals("GET") && path.equals("/api/posts")) {
    ...
}
```

мы можем написать:

```java
@GetMapping("/api/posts")
public List<Post> getPosts() {
    return service.getAll();
}
```

---

## Spring Boot

**Определение:**

Spring Boot — инструмент из экосистемы Spring, упрощающий создание и запуск Spring-приложений за счёт готовой конфигурации по умолчанию.

В рамках лекции Spring Boot автоматизирует, в частности:

* запуск встроенного Tomcat;
* создание Application Context;
* регистрацию `DispatcherServlet`;
* регистрацию стандартных `HttpMessageConverter`;
* настройку типовой инфраструктуры Spring Web MVC.

То есть большая часть ручной конфигурации:

```text
Tomcat
+
Spring Context
+
DispatcherServlet
+
MessageConverters
```

может быть настроена автоматически.

---

## Embedded Tomcat

**Определение:**

Embedded Tomcat — Tomcat, который запускается непосредственно внутри Java-приложения.

При классическом подходе:

```text
Tomcat
   ↓
deploy WAR
   ↓
application
```

при embedded-подходе:

```text
Java Application
      ↓
запускает Tomcat
      ↓
Tomcat принимает HTTP-запросы
```

Это позволяет запускать приложение как обычную Java-программу.

---

## DispatcherServlet

**Определение:**

`DispatcherServlet` — центральный servlet Spring Web MVC, который принимает HTTP-запросы и организует их дальнейшую обработку.

В лекции он рассматривается как значительно улучшенный аналог написанного ранее `MainServlet`.

Схема:

```text
HTTP Request
     ↓
DispatcherServlet
     ↓
поиск handler
     ↓
HandlerAdapter
     ↓
Controller method
     ↓
HTTP Response
```

Главное:

`DispatcherServlet` не должен содержать бизнес-логику.

Он занимается инфраструктурой обработки запроса.

---

## Dispatcher

**Определение:**

Dispatcher — компонент, который определяет, куда передать запрос для дальнейшей обработки.

В Spring MVC эту роль выполняет:

```text
DispatcherServlet
```

То есть:

```text
request
   ↓
dispatcher
   ↓
нужный handler
```

---

## ServletContainerInitializer

**Определение:**

`ServletContainerInitializer` — стандартный интерфейс Servlet API, позволяющий выполнять код во время запуска Servlet Container.

Контейнер вызывает:

```java
onStartup(...)
```

Упрощённо:

```text
Tomcat запускается
      ↓
находит ServletContainerInitializer
      ↓
вызывает onStartup()
```

Это позволяет программно настраивать web-приложение без `web.xml`.

---

## `onStartup()`

**Определение:**

`onStartup()` — метод инициализации web-приложения, вызываемый Servlet Container при старте.

Через него можно программно:

* зарегистрировать servlet;
* создать Spring Context;
* настроить mappings;
* выполнить начальную конфигурацию.

---

## SpringServletContainerInitializer

**Определение:**

`SpringServletContainerInitializer` — реализация `ServletContainerInitializer`, предоставленная Spring.

Она интегрирует механизм запуска Servlet Container со Spring.

Упрощённо:

```text
Tomcat
   ↓
SpringServletContainerInitializer
   ↓
WebApplicationInitializer
   ↓
Spring Web configuration
```

---

## WebApplicationInitializer

**Определение:**

`WebApplicationInitializer` — интерфейс Spring для программной настройки web-приложения при запуске.

Пример концепции:

```java
public class ApplicationInitializer
        implements WebApplicationInitializer {

    @Override
    public void onStartup(
            ServletContext servletContext
    ) {
        // настройка приложения
    }
}
```

Через него можно:

```text
создать Spring Context
↓
создать DispatcherServlet
↓
зарегистрировать DispatcherServlet
↓
задать mapping
```

## Web Application Context

**Определение:**

Web Application Context — разновидность Spring Application Context, предназначенная для web-приложений.

Он содержит beans приложения, но также связан с web-инфраструктурой.

В лекции такой context создаётся при настройке Spring Web MVC.

---

## AnnotationConfigWebApplicationContext

**Определение:**

`AnnotationConfigWebApplicationContext` — реализация web-контекста Spring, поддерживающая конфигурацию через аннотации.

Упрощённо:

```java
var context =
        new AnnotationConfigWebApplicationContext();

context.scan("ru.example");
context.refresh();
```

Он находит Spring-компоненты и создаёт соответствующие beans.

---

## `@RequestMapping`

**Определение:**

`@RequestMapping` — аннотация Spring MVC, связывающая HTTP-запрос с Controller или его методом.

Пример на уровне класса:

```java
@RestController
@RequestMapping("/api/posts")
public class PostController {
}
```

Теперь этот путь становится базовым для методов Controller.

---

## Hierarchical Mapping

**Определение:**

Hierarchical Mapping — построение итогового URL из mapping класса и mapping метода.

Например:

```java
@RequestMapping("/api/posts")
public class PostController {

    @GetMapping("/{id}")
    public Post getById(...) {
        ...
    }
}
```

Итоговый путь:

```text
/api/posts
+
/{id}
=
/api/posts/{id}
```

---

## `@GetMapping`

**Определение:**

`@GetMapping` — специализированная аннотация Spring MVC для обработки HTTP `GET`.

Пример:

```java
@GetMapping
public List<Post> getAll() {
    return service.getAll();
}
```

Она является более удобной формой `@RequestMapping` для GET-запросов.

---

## `@PostMapping`

**Определение:**

`@PostMapping` — специализированная аннотация для обработки HTTP `POST`.

Пример:

```java
@PostMapping
public Post save(
        @RequestBody Post post
) {
    return service.save(post);
}
```

---

## `@DeleteMapping`

**Определение:**

`@DeleteMapping` — специализированная аннотация для обработки HTTP `DELETE`.

Пример:

```java
@DeleteMapping("/{id}")
public void remove(
        @PathVariable long id
) {
    service.remove(id);
}
```

---

## Convenience Annotation

**Определение:**

Convenience Annotation — удобная специализированная аннотация, скрывающая более подробную конфигурацию.

Например:

```java
@GetMapping
```

по смыслу является удобной формой:

```java
@RequestMapping(method = RequestMethod.GET)
```

К таким аннотациям относятся:

```text
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping
@PatchMapping
```

---

## Handler

**Определение:**

Handler — метод, который Spring MVC вызывает для обработки конкретного HTTP-запроса.

Пример:

```java
@GetMapping("/{id}")
public Post getById(
        @PathVariable long id
) {
    return service.getById(id);
}
```

Метод:

```java
getById(...)
```

является handler.

---

## Handler Method

**Определение:**

Handler Method — метод Controller, зарегистрированный для обработки HTTP-запроса.

Обычно определяется аннотациями:

```text
@RequestMapping
@GetMapping
@PostMapping
@DeleteMapping
...
```

---

## Path Placeholder

**Определение:**

Path Placeholder — переменная часть URL.

Например:

```text
/api/posts/{id}
```

Здесь:

```text
{id}
```

является placeholder.

Если приходит запрос:

```text
/api/posts/15
```

то:

```text
id = 15
```

---

## `@PathVariable`

**Определение:**

`@PathVariable` — аннотация Spring MVC, позволяющая получить значение переменной из пути URL.

Пример:

```java
@GetMapping("/{id}")
public Post getById(
        @PathVariable long id
) {
    return service.getById(id);
}
```

Запрос:

```text
GET /api/posts/15
```

приведёт к:

```text
id = 15
```

---

## HandlerAdapter

**Определение:**

`HandlerAdapter` — компонент Spring MVC, который умеет подготовить и вызвать найденный handler.

Он, например:

* получает параметры из URL;
* подставляет `@PathVariable`;
* передаёт `HttpServletRequest`;
* передаёт `HttpServletResponse`;
* вызывает нужный метод Controller.

Условно:

```text
DispatcherServlet
      ↓
handler найден
      ↓
HandlerAdapter
      ↓
готовит аргументы
      ↓
handler(...)
```

---

## RequestMappingHandlerAdapter

**Определение:**

`RequestMappingHandlerAdapter` — реализация HandlerAdapter, предназначенная для вызова методов Controller, зарегистрированных через `@RequestMapping` и связанные аннотации.

Именно он обеспечивает значительную часть привычной «магии»:

```java
@GetMapping("/{id}")
public Post get(
        @PathVariable long id
) {
}
```

Spring сам понимает, откуда получить `id`.

## MVC

**Определение:**

MVC (Model-View-Controller) — архитектурный паттерн, разделяющий приложение на:

```text
Model
View
Controller
```

В классических web-приложениях Spring MVC Controller мог возвращать View.

Например:

```text
Controller
    ↓
Model
    ↓
View
    ↓
HTML
```

---

## Model

**Определение:**

Model в MVC — данные, которые должны быть использованы для формирования представления.

Например:

```text
User
Posts
Orders
```

---

## View

**Определение:**

View — представление данных, которое получает пользователь.

В классическом Spring MVC View мог быть:

* HTML;
* PDF;
* Excel;
* другое представление.

---

## View Resolution

**Определение:**

View Resolution — процесс определения того, какое View необходимо использовать для формирования HTTP-ответа.

Классическая схема:

```text
Controller
   ↓
view name
   ↓
resolve view
   ↓
render view
```

Для REST API обычно View не требуется.

---

## Render

**Определение:**

Render — формирование конечного представления, которое будет отправлено пользователю.

Например:

```text
Model
+
HTML template
↓
готовая HTML-страница
```

---

## `@ResponseBody`

**Определение:**

`@ResponseBody` — аннотация Spring MVC, означающая, что возвращаемое значение метода нужно записать непосредственно в тело HTTP-ответа.

Например:

```java
@GetMapping
@ResponseBody
public List<Post> getAll() {
    return service.getAll();
}
```

Spring не пытается воспринимать `List<Post>` как имя View.

Вместо этого объект передаётся механизму конвертации HTTP-сообщений.

---

## `@RequestBody`

**Определение:**

`@RequestBody` — аннотация Spring MVC, означающая, что тело HTTP-запроса нужно преобразовать в Java-объект и передать параметром handler-метода.

Например:

```java
@PostMapping
public Post save(
        @RequestBody Post post
) {
    return service.save(post);
}
```

Запрос:

```json
{
  "content": "Hello"
}
```

может быть преобразован в:

```java
Post post
```

---

## `@RestController`

**Определение:**

`@RestController` — аннотация Spring MVC для Controller, методы которого возвращают данные непосредственно в HTTP Body.

В рамках лекции:

```text
@RestController
=
@Controller
+
@ResponseBody для handler'ов
```

Пример:

```java
@RestController
@RequestMapping("/api/posts")
public class PostController {
}
```

Для REST API обычно используется именно `@RestController`.

---

## HttpMessageConverter

**Определение:**

`HttpMessageConverter` — механизм Spring MVC для преобразования между Java-объектами и телом HTTP-сообщения.

Два направления:

```text
HTTP Request Body
      ↓
HttpMessageConverter
      ↓
Java Object
```

и:

```text
Java Object
      ↓
HttpMessageConverter
      ↓
HTTP Response Body
```

Например:

```text
JSON → Post
```

и:

```text
Post → JSON
```

---

## Serialization в Spring MVC

**Определение:**

Serialization в Spring MVC — преобразование Java-объекта в формат тела HTTP-ответа.

Например:

```java
return new Post(1, "Hello");
```

может превратиться в:

```json
{
  "id": 1,
  "content": "Hello"
}
```

Эту работу выполняет подходящий `HttpMessageConverter`.

---

## Deserialization в Spring MVC

**Определение:**

Deserialization — преобразование тела HTTP-запроса в Java-объект.

Например:

```json
{
  "content": "Hello"
}
```

↓

```java
@RequestBody Post post
```

---

## GsonHttpMessageConverter

**Определение:**

`GsonHttpMessageConverter` — реализация `HttpMessageConverter`, использующая Gson для преобразования Java-объектов в JSON и обратно.

Схема:

```text
Post
 ↓
GsonHttpMessageConverter
 ↓
JSON
```

и наоборот.

В лекции он регистрируется внутри `RequestMappingHandlerAdapter`.

## Message Converter Registration

**Определение:**

Message Converter Registration — добавление конкретного `HttpMessageConverter` в конфигурацию Spring MVC.

Концептуально:

```java
adapter.getMessageConverters()
       .add(new GsonHttpMessageConverter());
```

После этого Spring понимает, как работать с JSON через Gson.

## Media Type

**Определение:**

Media Type — тип содержимого HTTP-сообщения, по которому Spring в том числе определяет подходящий Message Converter.

Например:

```text
application/json
text/plain
application/xml
```

`HttpMessageConverter` сообщает, с какими Media Types он умеет работать.

## `canRead()`

**Определение:**

`canRead()` — метод `HttpMessageConverter`, позволяющий определить, может ли converter преобразовать входящее HTTP-сообщение в нужный Java-тип.

Условно:

```text
application/json
+
Post.class
↓
может ли converter прочитать?
```

## `canWrite()`

**Определение:**

`canWrite()` — метод `HttpMessageConverter`, определяющий, может ли converter записать Java-объект в нужный формат HTTP-ответа.

Например:

```text
List<Post>
↓
application/json
```

## Classpath

**Определение:**

Classpath — набор классов и библиотек, доступных Java-приложению во время выполнения.

В лекции Spring Boot использует содержимое Classpath для принятия решений о конфигурации.

Например:

```text
есть Gson в Classpath
        ↓

```

## Auto-configuration

**Определение:**

Auto-configuration — автоматическая настройка Spring-приложения на основании подключённых зависимостей и доступных классов.

Идея:

```text
Spring Boot анализирует приложение
        ↓
видит необходимые библиотеки
        ↓
создаёт стандартные beans/config
```

Это избавляет разработчика от большого количества инфраструктурной настройки.

## `@SpringBootApplication`

**Определение:**

`@SpringBootApplication` — основная аннотация класса запуска Spring Boot-приложения.

В лекции итоговый код выглядит концептуально так:


## `SpringApplication.run()`

**Определение:**

`SpringApplication.run()` — стандартный способ запуска Spring Boot-приложения.

Он запускает процесс создания и настройки Spring Application Context и необходимой инфраструктуры приложения.

# Главное из темы

Основную цепочку Spring MVC нужно понимать так:

```text
HTTP Request
     ↓
Tomcat
     ↓
DispatcherServlet
     ↓
определение handler
     ↓
HandlerAdapter
     ↓
Controller method
     ↓
HttpMessageConverter
     ↓
HTTP Response
```

Например:

```text
GET /api/posts/15
```

↓

```java
@GetMapping("/{id}")
public Post getById(
        @PathVariable long id
) {
    return service.getById(id);
}
```

Spring выполняет примерно следующее:

```text
1. DispatcherServlet получает запрос
2. Spring находит getById()
3. HandlerAdapter подготавливает вызов
4. 15 преобразуется в параметр id
5. вызывается getById(15)
6. метод возвращает Post
7. HttpMessageConverter превращает Post в JSON
8. JSON записывается в HTTP Response Body
```

---

# Самое важное отличие старого подхода от Spring MVC

Раньше:

```java
if (method.equals("GET")) {
    if (path.matches(...)) {
        ...
    }
}
```

Теперь:

```java
@GetMapping("/{id}")
public Post getById(
        @PathVariable long id
) {
    return service.getById(id);
}
```

Раньше:

```java
Gson gson = new Gson();
response.getWriter()
        .print(gson.toJson(post));
```

Теперь:

```java
return post;
```

Раньше:

```java
String json = readBody(request);
Post post = gson.fromJson(json, Post.class);
```

Теперь:

```java
public Post save(
        @RequestBody Post post
)
```

Именно это и есть основная ценность Spring Web MVC: типовой инфраструктурный код уходит из бизнес-кода.

# Типичный REST Controller

```java
@RestController
@RequestMapping("/api/posts")
public class PostController {

    private final PostService service;

    public PostController(
            PostService service
    ) {
        this.service = service;
    }

    @GetMapping
    public List<Post> getAll() {
        return service.getAll();
    }

    @GetMapping("/{id}")
    public Post getById(
            @PathVariable long id
    ) {
        return service.getById(id);
    }

    @PostMapping
    public Post save(
            @RequestBody Post post
    ) {
        return service.save(post);
    }

    @DeleteMapping("/{id}")
    public void remove(
            @PathVariable long id
    ) {
        service.remove(id);
    }
}
```
