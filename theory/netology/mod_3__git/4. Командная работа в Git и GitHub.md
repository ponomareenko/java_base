# Командная работа в Git и GitHub

## 1. Командная работа

**Определение**
Командная работа — это процесс, когда несколько разработчиков работают над одним проектом через общий удалённый репозиторий.

**Пример**

```text
Разработчик #1 работает в папке colab-first.
Разработчик #2 работает в папке colab-second.

Оба проекта связаны с одним репозиторием на GitHub.
```

---

## 2. Командный проект

**Определение**
Командный проект — это проект, над которым работает несколько человек.

**Пример**

```text
Один разработчик добавил файл sample.md.
Другой разработчик изменил README.md.

Оба должны синхронизировать изменения через GitHub.
```

---

## 3. Устаревшая локальная копия

**Определение**
Устаревшая локальная копия — это локальный репозиторий, в котором нет свежих коммитов из удалённого репозитория.

**Пример**

```text
Ты работаешь в colab-first.
Коллега уже отправил новый коммит из colab-second.

Теперь твоя локальная копия устарела.
```

---

## 4. Синхронизация

**Определение**
Синхронизация — это процесс приведения локального и удалённого репозитория к актуальному состоянию.

**Пример**

```bash
git pull
git push
```

Сначала забираем чужие изменения, потом отправляем свои.

---

## 5. `git pull`

**Определение**
`git pull` — команда, которая забирает изменения из удалённого репозитория и добавляет их в текущую локальную ветку.

**Пример**

```bash
git pull
```

По сути, `git pull` делает две операции:

```text
git fetch + git merge
```

---

## 6. `git fetch`

**Определение**
`git fetch` — команда, которая забирает изменения из удалённого репозитория, но не применяет их к текущим файлам.

**Пример**

```bash
git fetch
```

После `fetch` Git знает о новых коммитах, но твои файлы ещё не изменены.

---

## 7. `git merge`

**Определение**
`git merge` — команда, которая сливает изменения из одной ветки или удалённой истории в текущую ветку.

**Пример**

```bash
git merge origin/main
```

---

## 8. `git pull = git fetch + git merge`

**Определение**
`git pull` — это удобная команда, которая сначала скачивает изменения, а потом сразу сливает их в текущую ветку.

**Пример**

```bash
git pull
```

То есть Git делает примерно следующее:

```bash
git fetch
git merge
```

---

## 9. `rejected`

**Определение**
`rejected` — сообщение Git, которое означает, что отправка изменений была отклонена.

**Пример**

```text
! [rejected] main -> main (fetch first)
```

Обычно это значит: в удалённом репозитории есть изменения, которых нет у тебя локально.

---

## 10. `fetch first`

**Определение**
`fetch first` — подсказка Git, что перед отправкой изменений нужно сначала забрать свежие данные из удалённого репозитория.

**Пример**

```text
! [rejected] main -> main (fetch first)
```

Что делать:

```bash
git pull
git push
```

---

## 11. `failed to push some refs`

**Определение**
`failed to push some refs` — сообщение Git о том, что он не смог отправить изменения в удалённый репозиторий.

**Пример**

```text
error: failed to push some refs to 'github.com:user/colab.git'
```

Частая причина: удалённая ветка ушла вперёд, а твоя локальная копия отстала.

---

## 12. Merge commit / коммит слияния

**Определение**
Merge commit — это коммит, который Git создаёт при слиянии двух историй изменений.

**Пример**

```text
Initial commit
sample added
README changed
Merge branch 'main' of github.com:user/colab
```

Коммит слияния появляется, когда Git объединяет изменения из разных источников.

---

## 13. Коммит слияния при `git pull`

**Определение**
Если при `git pull` Git объединяет удалённые и локальные изменения, он может создать отдельный коммит слияния.

**Пример**

```bash
git pull
```

Git может открыть редактор и предложить стандартное сообщение для merge commit.

---

## 14. Правило командной работы

**Определение**
В командной работе перед началом работы и перед отправкой изменений обычно нужно обновлять локальный репозиторий.

**Пример**

```bash
git pull
# работаешь с файлами
git add -A
git commit -m "change README"
git pull
git push
```

Это снижает риск конфликтов и отклонённого `push`.

---

## 15. Перемещение по истории

**Определение**
Перемещение по истории — это переход к старому коммиту, чтобы посмотреть состояние проекта в прошлом.

**Пример**

```bash
git checkout 413857f
```

---

## 16. `git checkout хеш-коммита`

**Определение**
`git checkout хеш-коммита` — команда для перехода к конкретному коммиту.

**Пример**

```bash
git checkout 413857f
```

После этого проект будет выглядеть так, как он выглядел в выбранном коммите.

---

## 17. Хеш коммита

**Определение**
Хеш коммита — это уникальный идентификатор коммита.

**Пример**

```text
413857f
cfb486b
```

По хешу Git понимает, к какому коммиту нужно перейти.

---

## 18. `HEAD`

**Определение**
`HEAD` — это указатель на то место в истории Git, где ты сейчас находишься.

**Пример**

```text
413857f (HEAD) Initial commit
```

Это значит, что сейчас проект находится на коммите `Initial commit`.

---

## 19. `git log --oneline --all`

**Определение**
`git log --oneline --all` — команда, которая показывает всю историю проекта в коротком формате.

**Пример**

```bash
git log --oneline --all
```

Полезно, когда ты переключился на старый коммит и обычный `git log` показывает не всю историю.

---

## 20. `--all`

**Определение**
`--all` — флаг, который просит Git показать всю доступную историю, а не только историю текущего положения.

**Пример**

```bash
git log --oneline --all
```

---

## 21. Режим вывода информации

**Определение**
Режим вывода информации — это режим терминала, когда Git показывает длинный текст, а новые команды временно нельзя вводить.

**Пример**

```bash
git log
```

Если история длинная, терминал может открыть просмотрщик.

---

## 22. `(END)`

**Определение**
`(END)` — надпись внизу терминала, которая показывает, что ты находишься в режиме просмотра длинного вывода.

**Пример**

```text
(END)
```

Чтобы выйти, нажми:

```text
Q
```

---

## 23. `Q`

**Определение**
`Q` — клавиша выхода из режима просмотра длинного вывода в терминале.

**Пример**

```text
Открылся длинный git log.
Внизу написано (END).
Нажимаешь Q — возвращаешься к обычному терминалу.
```

---

## 24. `git revert`

**Определение**
`git revert` — команда, которая отменяет изменения выбранного коммита, создавая новый обратный коммит.

**Пример**

```bash
git revert cfb486b
```

Важно: `git revert` не удаляет старый коммит из истории, а добавляет новый коммит, который отменяет его изменения.

---

## 25. Revert commit / обратный коммит

**Определение**
Обратный коммит — это новый коммит, который отменяет изменения другого коммита.

**Пример**

```text
README changed
Revert "README changed"
```

Первый коммит добавил строку, второй коммит её удалил.

---

## 26. Отмена коммита

**Определение**
Отмена коммита — это создание нового коммита, который убирает изменения выбранного старого коммита.

**Пример**

```bash
git revert cfb486b
git push
```

---

## 27. Почему `revert`, а не удаление коммита

**Определение**
В командной работе безопаснее отменять изменения через `git revert`, потому что история проекта сохраняется.

**Пример**

```text
Плохо: удалить коммит, который уже есть у коллег.
Лучше: создать новый коммит, который отменяет изменения.
```

Так коллеги смогут спокойно обновить свои локальные копии.

---

## 28. VIM

**Определение**
VIM — это консольный текстовый редактор, который Git может открыть для ввода сообщения коммита.

**Пример**

```text
Ты выполнил git revert.
Git открыл VIM, чтобы подтвердить сообщение коммита.
```

---

## 29. Выход из VIM при revert

**Определение**
Если Git открыл VIM или консольный редактор при `revert`, нужно сохранить сообщение и выйти.

**Пример из курса**

```text
Ctrl + X
Y
Enter
```

В некоторых версиях VIM часто используется:

```text
Esc
:wq
Enter
```

---

## 30. `.gitignore`

**Определение**
`.gitignore` — это файл-настройка, в котором указывают файлы и папки, которые Git должен игнорировать.

**Пример**

```text
private/
*.log
.env
```

---

## 31. Игнорирование файлов

**Определение**
Игнорирование файлов — это настройка, при которой Git не показывает определённые файлы в `git status` и не предлагает добавлять их в коммит.

**Пример**

```text
Файл .env содержит пароли.
Его нельзя отправлять на GitHub.
Добавляем .env в .gitignore.
```

---

## 32. Файл-настройка

**Определение**
Файл-настройка — это файл, который управляет поведением программы или инструмента.

**Пример**

```text
.gitignore — файл-настройка для Git.
```

---

## 33. Правило в `.gitignore`

**Определение**
Правило в `.gitignore` — это строка, которая сообщает Git, какие файлы или папки нужно игнорировать.

**Пример**

```gitignore
private/
```

Это правило игнорирует папку `private`.

---

## 34. Игнорирование папки

**Определение**
Чтобы Git игнорировал папку, нужно указать её имя со слэшем на конце.

**Пример**

```gitignore
private/
```

Слэш показывает, что это именно папка.

---

## 35. Игнорирование конкретного файла

**Определение**
Чтобы Git игнорировал конкретный файл, нужно указать его имя.

**Пример**

```gitignore
README.md
```

Git будет игнорировать только файл с названием `README.md`.

---

## 36. Игнорирование файлов по расширению

**Определение**
Чтобы Git игнорировал все файлы с определённым расширением, используют `*`.

**Пример**

```gitignore
*.md
```

Git будет игнорировать все файлы, которые заканчиваются на `.md`.

---

## 37. Игнорирование файла внутри папки

**Определение**
Можно игнорировать конкретный файл, который лежит в конкретной папке.

**Пример**

```gitignore
private/todo.md
```

Git будет игнорировать файл `todo.md` внутри папки `private`.

---

## 38. `*` в `.gitignore`

**Определение**
`*` — символ-шаблон, который означает «любое количество любых символов».

**Пример**

```gitignore
*.log
```

Означает: игнорировать все файлы, которые заканчиваются на `.log`.

---

## 39. Индексированный файл

**Определение**
Индексированный файл — это файл, который уже был добавлен в индекс через `git add`.

**Пример**

```bash
git add todo.md
```

После этого `.gitignore` уже не начнёт автоматически игнорировать этот файл.

---

## 40. Почему `.gitignore` не работает на уже добавленный файл

**Определение**
`.gitignore` работает только для файлов, которые ещё не добавлены в индекс Git.

**Пример**

```text
Ты уже сделал git add todo.md.
Потом добавил todo.md в .gitignore.

Git всё равно продолжит отслеживать todo.md.
```

Нужно убрать файл из индекса.

---

## 41. `git rm --cached`

**Определение**
`git rm --cached` — команда, которая убирает файл из индекса Git, но оставляет его на компьютере.

**Пример**

```bash
git rm --cached todo.md
```

Файл останется в папке, но Git перестанет его отслеживать.

---

## 42. `--cached`

**Определение**
`--cached` — флаг, который говорит Git удалить файл только из индекса, не удаляя его физически с компьютера.

**Пример**

```bash
git rm --cached private/todo.md
```

---

## 43. Отслеживаемый файл

**Определение**
Отслеживаемый файл — это файл, который Git уже контролирует.

**Пример**

```text
Если файл уже попадал в коммит, он отслеживаемый.
Одной записи в .gitignore недостаточно, чтобы Git забыл о нём.
```

---

## 44. Неотслеживаемый файл

**Определение**
Неотслеживаемый файл — это файл, который есть в папке проекта, но Git ещё не взял его под контроль.

**Пример**

```text
Создал private/todo.md.
Ещё не делал git add.
Файл пока неотслеживаемый.
```

---

## 45. Личные файлы проекта

**Определение**
Личные файлы проекта — это файлы, которые нужны конкретному разработчику, но не должны попадать в общий репозиторий.

**Пример**

```text
todo.md
notes.md
.env
local-settings.json
```

---

## 46. Секретные файлы

**Определение**
Секретные файлы — это файлы, которые могут содержать пароли, токены, ключи доступа или локальные настройки.

**Пример**

```text
.env
secrets.json
id_rsa
```

Такие файлы нельзя отправлять в публичный репозиторий.

---

## 47. `.env`

**Определение**
`.env` — файл с переменными окружения, в котором часто хранят настройки приложения, пароли, токены или адреса сервисов.

**Пример**

```env
DATABASE_URL=postgres://user:password@localhost:5432/app
API_TOKEN=secret-token
```

Обычно `.env` добавляют в `.gitignore`.

---

## 48. `git status` при `.gitignore`

**Определение**
`git status` показывает только те файлы, которые Git видит. Если файл успешно игнорируется, он исчезает из вывода `git status`.

**Пример**

```bash
git status
```

Если папка `private/` добавлена в `.gitignore`, Git больше не показывает её как неотслеживаемую.

---

## 49. Публикация на GitHub

**Определение**
Публикация на GitHub — это отправка локальных коммитов в удалённый репозиторий.

**Пример**

```bash
git push
```

---

## 50. Безопасность репозитория

**Определение**
Безопасность репозитория — это контроль того, какие файлы попадают в Git и GitHub.

**Пример**

```text
Хорошо:
.gitignore содержит .env

Плохо:
.env случайно попал в публичный GitHub-репозиторий.
```

---

# Коротко: что нужно запомнить

```text
git pull — забрать изменения из удалённого репозитория и влить их в текущую ветку.
git pull = git fetch + git merge.

В командной работе делай git pull:
1. перед началом работы;
2. перед git push.

Если push отклонён с fetch first — сначала сделай git pull.

git checkout хеш — посмотреть старое состояние проекта.
git checkout main — вернуться в актуальную ветку.

git log --oneline --all — посмотреть всю историю проекта.

git revert хеш — отменить изменения коммита через новый обратный коммит.
revert безопаснее для командной работы, чем переписывание истории.

.gitignore — файл правил, которые говорят Git, что не нужно отслеживать.
.gitignore работает только для файлов, которые ещё не добавлены в индекс.

git rm --cached имя-файла — убрать файл из индекса, но оставить на компьютере.
```

---

# Мини-шпаргалка команд

```bash
# Обновить локальный проект из GitHub
git pull

# Отправить свои коммиты на GitHub
git push

# Посмотреть историю коротко
git log --oneline

# Посмотреть всю историю
git log --oneline --all

# Перейти к старому коммиту
git checkout хеш_коммита

# Вернуться в основную ветку
git checkout main

# Отменить изменения конкретного коммита
git revert хеш_коммита

# Создать файл .gitignore
touch .gitignore

# Убрать файл из индекса, но оставить на компьютере
git rm --cached имя_файла

# Убрать папку из индекса рекурсивно
git rm -r --cached имя_папки
```

```gitignore
# Личные заметки

todo.md

# Локальные настройки
.env

# Логи
*.log

# Временные файлы
tmp/

```
