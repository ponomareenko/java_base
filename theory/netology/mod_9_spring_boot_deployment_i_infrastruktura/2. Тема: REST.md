# 2. Тема: REST

## REST

**Определение:**

REST (`Representational State Transfer`) — архитектурный стиль взаимодействия между компонентами распределённой системы. 

REST описывает набор архитектурных ограничений, которым следует API.

Главные ограничения REST из презентации:

```text
Client-Server
Stateless
Uniform Interface
Cacheable
Layered System
Code on Demand
```



REST — это **не протокол и не библиотека**. Это архитектурный стиль.

---

## RESTful API

**Определение:**

RESTful API — API, построенный с соблюдением ограничений архитектурного стиля REST.

В презентации RESTful-приложение определяется как приложение, построенное с учётом ограничений REST. 

Пример RESTful URL:

```http
GET /users/15
```

где:

```text
users → ресурс
15    → идентификатор ресурса
GET   → операция над ресурсом
```

Обычно REST API строится вокруг **ресурсов**, а действие определяется HTTP-методом.

---

## Resource

**Определение:**

Resource — сущность или данные, с которыми работает REST API.

Например:

```text
/users
/orders
/products
```

Конкретный ресурс:

```text
/users/15
```

В REST URL обычно описывает **что это за ресурс**, а не действие.

Лучше:

```http
DELETE /users/15
```

чем:

```http
POST /deleteUser?id=15
```

Это дополнение к презентации для практического понимания REST.

---

## Client-Server

**Определение:**

Client-Server — принцип REST, согласно которому клиент и сервер имеют разделённые обязанности.

Клиент:

```text
отправляет запросы
отображает данные
```

Сервер:

```text
обрабатывает запросы
работает с бизнес-логикой
работает с данными
```

Пример:

```text
React / Mobile app
       ↓ HTTP
Spring Boot REST API
       ↓
Database
```

Клиент-серверная архитектура указана в презентации как одно из ограничений REST. 

---

## Stateless

**Определение:**

Stateless — принцип REST, согласно которому сервер не должен зависеть от состояния предыдущего запроса клиента.

Каждый запрос должен содержать всю информацию, необходимую для его обработки.

Например:

```http
GET /profile
Authorization: Bearer <token>
```

Следующий запрос снова содержит необходимые данные авторизации.

Упрощённо:

```text
Запрос №1 → сервер
Запрос №2 → сервер
Запрос №3 → сервер
```

Каждый запрос рассматривается самостоятельно.

В презентации это ограничение называется **отсутствием состояния**. 

---

## Uniform Interface

**Определение:**

Uniform Interface — единообразный способ взаимодействия клиента с ресурсами REST API.

Например:

```http
GET    /users
GET    /users/10
POST   /users
PUT    /users/10
DELETE /users/10
```

API использует одни и те же понятные правила для разных ресурсов.

Это уменьшает связанность клиента и сервера.

Единообразный интерфейс входит в основные ограничения REST из презентации. 

---

## Cacheable

**Определение:**

Cacheable — принцип REST, согласно которому ответы сервера могут явно разрешать или запрещать кеширование.

Например, результат:

```http
GET /products
```

может некоторое время храниться в кеше, чтобы не запрашивать одинаковые данные у сервера заново.

Кеширование указано в презентации среди основных принципов REST. 

---

# REST в Spring

## `@RestController`

**Определение:**

`@RestController` — аннотация Spring, обозначающая класс, методы которого обрабатывают HTTP-запросы и возвращают данные в тело HTTP-ответа.

В презентации она обозначена как аннотация класса-обработчика пользовательских запросов. 

Пример:

```java
@RestController
@RequestMapping("/users")
public class UserController {

    @GetMapping
    public List<User> getUsers() {
        return userService.getUsers();
    }
}
```

Возвращаемый Java-объект Spring может автоматически сериализовать, например, в JSON.

---

## `@RequestMapping`

**Определение:**

`@RequestMapping` — аннотация Spring MVC, которая связывает HTTP-запрос с определённым контроллером или методом контроллера. 

Пример:

```java
@RestController
@RequestMapping("/users")
public class UserController {
}
```

Все методы этого контроллера теперь работают относительно:

```text
/users
```

На практике для конкретных HTTP-методов чаще используются более специализированные аннотации:

```java
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping
@PatchMapping
```

---

## `@RequestBody`

**Определение:**

`@RequestBody` — аннотация, указывающая Spring десериализовать тело HTTP-запроса в Java-объект. 

Запрос:

```http
POST /users
Content-Type: application/json
```

```json
{
  "name": "Danil",
  "age": 25
}
```

Контроллер:

```java
@PostMapping
public void createUser(@RequestBody UserRequest request) {
}
```

Spring преобразует JSON:

```json
{
  "name": "Danil",
  "age": 25
}
```

в:

```java
UserRequest
```

---

## `@RequestParam`

**Определение:**

`@RequestParam` — аннотация для получения параметра из query string HTTP-запроса. 

Запрос:

```http
GET /users?age=25
```

Код:

```java
@GetMapping
public List<User> getUsers(@RequestParam int age) {
    return userService.findByAge(age);
}
```

Здесь:

```text
age=25
```

— query parameter.

---

## `@PathVariable`

**Определение:**

`@PathVariable` — аннотация для получения значения непосредственно из пути HTTP-запроса. 

Например:

```http
GET /users/15
```

Контроллер:

```java
@GetMapping("/{id}")
public User getUser(@PathVariable Long id) {
    return userService.getById(id);
}
```

Здесь:

```text
15
```

будет передано в:

```java
id
```

### `@PathVariable` vs `@RequestParam`

```text
/users/15
       ↑
@PathVariable

/users?age=25
           ↑
@RequestParam
```

# Валидация

## Validation

**Определение:**

Validation — проверка входных данных на соответствие установленным ограничениям.

В презентации указано, что Spring использует Java Validation API для проверки объектов запросов. 

Например:

```java
public class UserRequest {

    @NotBlank
    private String name;

    @Min(18)
    private int age;
}
```

Теперь входные данные должны соответствовать заданным правилам.

---

## `@Validated`

**Определение:**

`@Validated` — аннотация Spring, включающая применение механизма валидации для соответствующего класса или метода.

В презентации указано, что контроллер или валидируемый объект должен быть помечен `@Validated`. 

Пример:

```java
@RestController
@Validated
public class UserController {
}
```

На практике при валидации `@RequestBody` также часто встретишь:

```java
@Valid
```

например:

```java
@PostMapping
public void create(@Valid @RequestBody UserRequest request) {
}
```

`@Valid` — стандарт Bean Validation, а `@Validated` предоставляет дополнительные возможности Spring, например validation groups.

# Обработка ошибок

## `HandlerExceptionResolver`

**Определение:**

`HandlerExceptionResolver` — интерфейс Spring MVC, реализации которого преобразуют исключения, возникшие при обработке запроса контроллером, в соответствующий HTTP-ответ. 

Упрощённо:

```text
HTTP request
     ↓
Controller
     ↓
Exception
     ↓
HandlerExceptionResolver
     ↓
HTTP response
```

Например:

```text
UserNotFoundException
        ↓
404 Not Found
```

---

## `DefaultHandlerExceptionResolver`

**Определение:**

`DefaultHandlerExceptionResolver` — стандартная реализация `HandlerExceptionResolver`, которая преобразует типовые исключения Spring MVC в соответствующие HTTP-статусы. 

Например, некорректный HTTP-метод или неправильно сформированный запрос может автоматически привести к соответствующему `4xx` ответу.

---

## `ExceptionHandlerExceptionResolver`

**Определение:**

`ExceptionHandlerExceptionResolver` — реализация `HandlerExceptionResolver`, которая позволяет обрабатывать исключения через специальные методы обработки ошибок. 

На практике с этим механизмом связана аннотация:

```java
@ExceptionHandler
```

Например:

```java
@ExceptionHandler(UserNotFoundException.class)
public ResponseEntity<String> handle(UserNotFoundException exception) {
    return ResponseEntity
            .status(HttpStatus.NOT_FOUND)
            .body(exception.getMessage());
}
```

---

## `SimpleMappingExceptionResolver`

**Определение:**

`SimpleMappingExceptionResolver` — реализация `HandlerExceptionResolver`, позволяющая декларативно сопоставлять исключения с определёнными представлениями. 

Для современных REST API используется заметно реже, чем механизмы `@ExceptionHandler` и глобальной обработки исключений.

---

# Настройка Spring MVC

## `WebMvcConfigurer`

**Определение:**

`WebMvcConfigurer` — интерфейс Spring MVC, позволяющий изменять и дополнять стандартную MVC-конфигурацию приложения. 

Через него можно, например:

* регистрировать interceptors;
* добавлять конвертеры;
* настраивать статические ресурсы.

Эти возможности отдельно перечислены в презентации. 

Пример:

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new LoggingInterceptor());
    }
}
```

---

## Interceptor

**Определение:**

Interceptor — компонент Spring MVC, позволяющий выполнить дополнительную логику **до или после обработки HTTP-запроса контроллером**.

Возможность регистрации interceptor-классов через `WebMvcConfigurer` указана в презентации. 

Например, interceptor можно использовать для:

```text
логирования
проверки некоторых условий запроса
измерения времени выполнения
добавления общей логики обработки
```

Схематично:

```text
Request
   ↓
Interceptor
   ↓
Controller
   ↓
Interceptor
   ↓
Response
```

---

## Converter

**Определение:**

`Converter<S, T>` — интерфейс Spring для преобразования значения одного типа в другой.

Презентация показывает пользовательский converter как способ обработки типов, которые Spring не может преобразовать стандартным способом. 

Пример:

```java
public class StringToRoleConverter
        implements Converter<String, Role> {

    @Override
    public Role convert(String source) {
        return Role.valueOf(source.toUpperCase());
    }
}
```

Регистрация:

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {

    @Override
    public void addFormatters(FormatterRegistry registry) {
        registry.addConverter(new StringToRoleConverter());
    }
}
```

После этого Spring сможет автоматически преобразовывать:

```text
"admin"
```

в:

```java
Role.ADMIN
```

---

## `DispatcherServlet`

**Определение:**

`DispatcherServlet` — центральный servlet Spring MVC, который принимает входящие HTTP-запросы и направляет их подходящим обработчикам.

В презентации отмечено, что Spring Boot создаёт и настраивает `DispatcherServlet` автоматически через механизм автоконфигурации. 

Упрощённая схема:

```text
HTTP Request
     ↓
DispatcherServlet
     ↓
Controller
     ↓
Service
     ↓
Response
```

Это одна из важнейших частей внутреннего устройства Spring MVC.

---

# Что обязательно запомнить из темы

Основную цепочку REST-запроса в Spring можно держать в голове так:

```text
Client
   ↓
HTTP Request
   ↓
DispatcherServlet
   ↓
@RestController
   ↓
@RequestMapping / @GetMapping / ...
   ↓
@RequestBody / @RequestParam / @PathVariable
   ↓
Validation
   ↓
Business Logic
   ↓
HTTP Response
```

При ошибке:

```text
Controller
   ↓
Exception
   ↓
HandlerExceptionResolver
   ↓
HTTP error response
```

А для дополнительной настройки Spring MVC:

```text
WebMvcConfigurer
       ↓
Interceptor
Converter
Static resources
другая MVC-конфигурация
```
