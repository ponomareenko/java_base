# Тема: HTTP и вызов удалённых серверов

## HTTP

**HTTP — Hypertext Transfer Protocol** — это протокол прикладного уровня, предназначенный для обмена данными между клиентом и сервером.

HTTP определяет:

* как клиент формирует запрос;
* как сервер формирует ответ;
* какие операции можно выполнять над ресурсами;
* как передаются заголовки и тело сообщения;
* как сервер сообщает результат обработки запроса.

HTTP может передавать не только HTML:

* JSON;
* XML;
* текст;
* изображения;
* видео;
* файлы;
* двоичные данные.

Типичное взаимодействие:

```text
Клиент → HTTP-запрос → Сервер
Клиент ← HTTP-ответ  ← Сервер
```

---

## Клиент-серверная модель

**Клиент-серверная модель** — это способ взаимодействия, при котором клиент инициирует запрос, а сервер принимает его, обрабатывает и возвращает ответ.

Клиентом может быть:

* браузер;
* мобильное приложение;
* Java-программа;
* другой сервер;
* утилита вроде `curl`;
* автоматический тест.

Сервером может быть:

* веб-приложение;
* REST API;
* файловый сервис;
* сервис авторизации;
* микросервис.

---

## Удалённый сервер

**Удалённый сервер** — это сервер, к которому программа обращается через сеть.

Слово «удалённый» не обязательно означает, что сервер физически находится далеко. Это может быть:

* сервер в другом дата-центре;
* контейнер в той же Kubernetes-сети;
* другой процесс на `localhost`;
* микросервис в соседней виртуальной машине.

Пример адреса удалённого сервиса:

```text
https://api.example.com/products
```

---

## Ресурс

**Ресурс** — это объект, к которому клиент обращается через HTTP.

Примеры ресурсов:

* пользователь;
* товар;
* заказ;
* изображение;
* файл;
* список комментариев.

Например:

```text
/users/15
```

может обозначать пользователя с идентификатором `15`.

---

## API

**API — Application Programming Interface** — это интерфейс, через который одна программа взаимодействует с другой.

HTTP API обычно описывает:

* доступные адреса;
* HTTP-методы;
* параметры;
* формат запросов;
* формат ответов;
* коды состояния;
* правила авторизации.

---

## Endpoint

**Endpoint** — это конкретная точка входа в API, обычно определяемая сочетанием HTTP-метода и пути.

Например:

```text
GET /users
```

и:

```text
POST /users
```

— это разные endpoints, хотя путь у них одинаковый.

Первый получает пользователей, второй создаёт пользователя.

---

# URI и URL

## URI

**URI — Uniform Resource Identifier** — это идентификатор ресурса.

URI является общим понятием. Он может идентифицировать ресурс по адресу, имени или другому правилу.

---

## URL

**URL — Uniform Resource Locator** — это URI, который указывает местоположение ресурса и способ обращения к нему.

Пример:

```text
https://api.example.com:443/users/15?details=true
```

Структура:

```text
https://api.example.com:443/users/15?details=true
└─┬─┘   └───────┬───────┘ └┬┘ └───┬───┘ └─────┬─────┘
схема          host         порт    path       query
```

---

## Scheme

**Scheme, или схема URL** — это часть адреса, определяющая используемый протокол.

Примеры:

```text
http
https
ftp
```

В адресе:

```text
https://example.com
```

схема — `https`.

---

## Host

**Host в URL** — это доменное имя или IP-адрес сервера.

Примеры:

```text
example.com
```

```text
192.168.1.10
```

Не следует путать host как часть URL и заголовок HTTP `Host`, хотя они обычно содержат связанное значение.

---

## Path

**Path, или путь к ресурсу** — это часть URL, определяющая ресурс на сервере.

Примеры:

```text
/users
```

```text
/users/15
```

```text
/products/10/reviews
```

Путь обычно отражает структуру ресурсов, а не физическое расположение файла на сервере.

---

## Path parameter

**Path parameter** — это динамическая часть пути.

Пример:

```text
/users/{id}
```

Для пользователя с идентификатором `15`:

```text
/users/15
```

Здесь `15` — значение path-параметра `id`.

Path-параметры обычно используют для идентификации конкретного ресурса.

---

## Query string

**Query string** — это часть URL после символа `?`, содержащая параметры запроса.

Пример:

```text
/products?category=books&page=2
```

Здесь:

```text
category=books
page=2
```

— query-параметры.

Несколько параметров разделяются символом `&`.

---

## Query parameter

**Query parameter** — это параметр запроса в формате:

```text
имя=значение
```

Пример:

```text
/users?active=true&limit=20
```

Query-параметры обычно используют для:

* фильтрации;
* сортировки;
* пагинации;
* поиска;
* изменения представления ответа.

Они не должны использоваться для передачи паролей, токенов и другой секретной информации: URL часто сохраняются в логах, истории браузера и системах аналитики.

---

## Percent encoding

**Percent encoding** — это способ кодирования специальных символов в URL.

Например, пробел может быть представлен как:

```text
%20
```

Строка:

```text
Java developer
```

в URL может выглядеть так:

```text
Java%20developer
```

При формировании URL не следует вручную заменять пробелы и другие символы. Для этого используют специальные классы и библиотеки.

---

# HTTP-запрос

## HTTP request

**HTTP request, или HTTP-запрос** — это сообщение, которое клиент отправляет серверу.

Логически запрос состоит из:

1. метода;
2. адреса ресурса;
3. заголовков;
4. необязательного тела.

В HTTP/1.1 текстовый запрос может выглядеть так:

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "name": "Alex",
  "age": 25
}
```

---

## Request line

**Request line, или стартовая строка запроса** — это первая строка HTTP/1.1-запроса.

Она содержит:

* HTTP-метод;
* путь к ресурсу;
* версию протокола.

Пример:

```http
GET /users/15 HTTP/1.1
```

Где:

```text
GET          — метод
/users/15    — путь
HTTP/1.1     — версия протокола
```

Это именно текстовое представление HTTP/1.1. В HTTP/2 и HTTP/3 данные передаются в бинарном формате и устроены иначе.

---

# HTTP-методы

## HTTP method

**HTTP-метод** — это часть запроса, обозначающая действие, которое клиент хочет выполнить над ресурсом.

Основные методы:

| Метод     | Типичное назначение                   |
| --------- | ------------------------------------- |
| `GET`     | Получить ресурс                       |
| `POST`    | Создать ресурс или выполнить операцию |
| `PUT`     | Полностью заменить ресурс             |
| `PATCH`   | Частично изменить ресурс              |
| `DELETE`  | Удалить ресурс                        |
| `HEAD`    | Получить только заголовки             |
| `OPTIONS` | Узнать доступные возможности          |
| `CONNECT` | Создать туннель                       |
| `TRACE`   | Диагностика прохождения запроса       |

Назначение методов — соглашение. Само слово `DELETE` физически не удаляет данные. Это делает серверная программа.

---

## GET

**GET** — это HTTP-метод для получения представления ресурса.

Пример:

```http
GET /users/15 HTTP/1.1
```

GET-запрос не должен изменять бизнес-состояние сервера.

Допустимо, что сервер при GET:

* записывает лог;
* обновляет статистику;
* считает метрики.

Но GET не должен создавать заказ, списывать деньги или удалять пользователя.

---

## POST

**POST** — это HTTP-метод для отправки данных серверу.

Частые сценарии:

* создание нового ресурса;
* запуск операции;
* отправка формы;
* загрузка файла;
* выполнение команды.

Пример:

```http
POST /users HTTP/1.1
Content-Type: application/json

{
  "name": "Alex"
}
```

POST не обязан быть идемпотентным.

Если дважды отправить:

```http
POST /orders
```

могут быть созданы два заказа.

---

## PUT

**PUT** — это HTTP-метод для полной записи или замены ресурса по известному адресу.

Пример:

```http
PUT /users/15 HTTP/1.1
Content-Type: application/json

{
  "name": "Alex",
  "age": 26,
  "email": "alex@example.com"
}
```

В REST-подобных API PUT обычно передаёт полное состояние ресурса.

Если поле не передано, сервер может считать, что оно должно быть удалено или сброшено. Конкретное поведение определяется контрактом API.

---

## PATCH

**PATCH** — это HTTP-метод для частичного изменения ресурса.

Пример:

```http
PATCH /users/15 HTTP/1.1
Content-Type: application/json

{
  "age": 26
}
```

В отличие от PUT, остальные поля ресурса обычно остаются без изменений.

---

## DELETE

**DELETE** — это HTTP-метод для удаления ресурса.

Пример:

```http
DELETE /users/15 HTTP/1.1
```

Сервер может:

* физически удалить запись;
* выполнить мягкое удаление;
* пометить ресурс как неактивный;
* запретить удаление.

---

## HEAD

**HEAD** — это метод, аналогичный GET, но сервер не должен отправлять тело ответа.

Пример:

```http
HEAD /files/report.pdf HTTP/1.1
```

HEAD используют, чтобы узнать:

* существует ли ресурс;
* его размер;
* тип содержимого;
* дату изменения;
* кэш-заголовки.

---

## OPTIONS

**OPTIONS** — это метод для получения информации о поддерживаемых возможностях ресурса или сервера.

Пример:

```http
OPTIONS /users HTTP/1.1
```

Ответ может содержать:

```http
Allow: GET, POST, OPTIONS
```

OPTIONS также используется браузерами при CORS preflight-запросах.

---

## CONNECT

**CONNECT** — это метод для создания сетевого туннеля через прокси-сервер.

Часто применяется при работе HTTPS через HTTP-прокси.

---

## TRACE

**TRACE** — это диагностический метод, который просит сервер вернуть полученный запрос.

В production-системах TRACE часто отключают по соображениям безопасности.

---

# Свойства HTTP-методов

## Safe method

**Безопасный метод** — это метод, который не должен изменять состояние ресурса.

К безопасным относятся:

* `GET`;
* `HEAD`;
* `OPTIONS`;
* `TRACE`.

«Безопасный» здесь не означает защищённый от взлома. Это термин о семантике операции.

---

## Idempotency

**Идемпотентность** — это свойство операции, при котором многократное выполнение одного и того же запроса приводит к тому же итоговому состоянию, что и однократное.

Обычно идемпотентны:

* `GET`;
* `HEAD`;
* `PUT`;
* `DELETE`;
* `OPTIONS`.

Обычно неидемпотентен:

* `POST`.

`PATCH` может быть как идемпотентным, так и неидемпотентным.

Пример идемпотентного PUT:

```http
PUT /users/15

{
  "status": "ACTIVE"
}
```

Повторная установка статуса `ACTIVE` не меняет итог.

Пример неидемпотентной операции:

```http
POST /balance/increase

{
  "amount": 100
}
```

Повторный запрос может дважды увеличить баланс.

---

## Idempotency key

**Idempotency key** — это уникальный идентификатор операции, который помогает серверу не выполнить один и тот же неидемпотентный запрос повторно.

Пример:

```http
Idempotency-Key: 8ce9b750-5f3f-4e8e-b08e-09b118a63068
```

Это особенно важно для:

* платежей;
* оформления заказов;
* резервирования;
* повторной отправки запросов после тайм-аута.

---

# HTTP-заголовки

## HTTP header

**HTTP-заголовок** — это служебная информация HTTP-запроса или ответа.

Формат:

```text
Имя: значение
```

Пример:

```http
Content-Type: application/json
```

Заголовки описывают:

* тип данных;
* поддерживаемые форматы;
* авторизацию;
* кэширование;
* cookies;
* сжатие;
* клиент;
* сервер;
* перенаправление.

Названия HTTP-заголовков регистронезависимы:

```text
Content-Type
content-type
CONTENT-TYPE
```

означают один заголовок.

---

## Host

**`Host`** — заголовок HTTP/1.1, определяющий доменное имя сервера, к которому обращается клиент.

```http
Host: api.example.com
```

Один физический сервер может обслуживать много доменов, поэтому `Host` помогает определить нужное виртуальное приложение.

---

## User-Agent

**`User-Agent`** — заголовок с информацией о клиентском приложении.

Пример:

```http
User-Agent: MyJavaService/1.0
```

Сервер может использовать его для:

* логирования;
* аналитики;
* совместимости;
* блокировки подозрительных клиентов.

В сервисных приложениях лучше указывать осмысленное название клиента, а не притворяться браузером.

---

## Accept

**`Accept`** — заголовок, указывающий, какие форматы ответа клиент готов обработать.

```http
Accept: application/json
```

Несколько форматов:

```http
Accept: application/json, application/xml
```

---

## Content-Type

**`Content-Type`** — заголовок, определяющий формат тела текущего сообщения.

В запросе:

```http
Content-Type: application/json
```

означает:

> тело запроса содержит JSON.

В ответе тот же заголовок означает:

> тело ответа содержит JSON.

Важно различать:

```http
Accept: application/json
```

— что клиент хочет получить;

```http
Content-Type: application/json
```

— что фактически находится в отправляемом теле.

---

## Media type

**Media type, или MIME-type** — это стандартное обозначение формата содержимого.

Примеры:

```text
application/json
text/html
text/plain
application/xml
image/png
application/pdf
multipart/form-data
application/octet-stream
```

Структура:

```text
тип/подтип
```

Например:

```text
application/json
```

---

## Content negotiation

**Content negotiation** — это согласование формата данных между клиентом и сервером.

Клиент сообщает:

```http
Accept: application/json
```

Сервер отвечает:

```http
Content-Type: application/json
```

Если сервер не может предоставить поддерживаемый клиентом формат, он может вернуть:

```text
406 Not Acceptable
```

---

## Authorization

**`Authorization`** — заголовок, содержащий данные для аутентификации клиента.

Примеры:

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

```http
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

Заголовок должен передаваться только через HTTPS.

---

## Authentication

**Аутентификация** — это проверка того, кто пользователь или клиент.

Вопрос:

> Кто вы?

Примеры:

* логин и пароль;
* access token;
* API key;
* клиентский сертификат.

---

## Authorization process

**Авторизация** — это проверка того, что аутентифицированному пользователю разрешено делать.

Вопрос:

> Что вам разрешено?

Например:

* пользователь вошёл в систему;
* но не имеет права удалять чужой заказ;
* сервер возвращает `403 Forbidden`.

Не следует путать процесс авторизации с HTTP-заголовком `Authorization`, историческое название которого немного сбивает с толку.

---

## Cookie

**`Cookie`** — заголовок запроса, через который клиент передаёт серверу сохранённые cookies.

```http
Cookie: sessionId=abc123
```

---

## Set-Cookie

**`Set-Cookie`** — заголовок ответа, через который сервер просит клиента сохранить cookie.

```http
Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Lax
```

Атрибуты:

* `HttpOnly` — JavaScript в браузере не может прочитать cookie;
* `Secure` — cookie передаётся только по HTTPS;
* `SameSite` — ограничивает отправку cookie в межсайтовых запросах;
* `Max-Age` или `Expires` — срок хранения;
* `Path` — путь, для которого действует cookie;
* `Domain` — домен cookie.

---

## Accept-Language

**`Accept-Language`** — заголовок с предпочтительными языками клиента.

```http
Accept-Language: ru-RU, ru;q=0.9, en;q=0.8
```

---

## Accept-Encoding

**`Accept-Encoding`** — заголовок, указывающий поддерживаемые клиентом способы сжатия ответа.

```http
Accept-Encoding: gzip, br
```

---

## Content-Encoding

**`Content-Encoding`** — заголовок, указывающий способ кодирования или сжатия тела.

```http
Content-Encoding: gzip
```

Сначала данные нужно распаковать, затем интерпретировать согласно `Content-Type`.

---

## Content-Length

**`Content-Length`** — размер тела сообщения в байтах.

```http
Content-Length: 128
```

Это именно байты, а не количество символов.

Например, строка в UTF-8 может содержать 10 символов, но занимать больше 10 байт.

---

# Тело HTTP-сообщения

## Message body

**Message body, или тело сообщения** — это данные, передаваемые внутри HTTP-запроса или ответа.

Тело может содержать:

* JSON;
* XML;
* HTML;
* текст;
* изображение;
* файл;
* бинарные данные.

Пример тела запроса:

```json
{
  "name": "Alex",
  "age": 25
}
```

Тело отделено от заголовков пустой строкой в текстовом представлении HTTP/1.1.

---

## GET с телом

HTTP формально не запрещает отправить тело с GET, но не определяет для него стандартную семантику.

Многие:

* серверы;
* прокси;
* кэши;
* библиотеки;
* API-шлюзы

могут проигнорировать или отклонить такое тело.

Поэтому данные GET-запроса передают через:

* path-параметры;
* query-параметры;
* заголовки.

---

## multipart/form-data

**`multipart/form-data`** — формат тела запроса, позволяющий передавать несколько частей, например текстовые поля и файлы.

Используется при загрузке файлов через HTML-формы.

Упрощённо:

```http
Content-Type: multipart/form-data; boundary=abc123
```

---

## application/octet-stream

**`application/octet-stream`** — универсальный media type для произвольных бинарных данных.

Используется, когда более конкретный формат неизвестен или не указан.

---

# HTTP-ответ

## HTTP response

**HTTP response, или HTTP-ответ** — это сообщение, которое сервер возвращает клиенту после обработки запроса.

Логически ответ содержит:

1. код состояния;
2. заголовки;
3. необязательное тело.

Пример HTTP/1.1:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{
  "id": 15,
  "name": "Alex"
}
```

---

## Status line

**Status line, или строка состояния** — это первая строка HTTP/1.1-ответа.

Она содержит:

* версию протокола;
* код состояния;
* текстовое пояснение.

Пример:

```http
HTTP/1.1 200 OK
```

В HTTP/2 текстовое пояснение вроде `OK` не является частью протокола. Для логики приложения нужно ориентироваться на числовой код.

---

## Status code

**HTTP status code, или код состояния** — это трёхзначное число, сообщающее результат обработки запроса.

Группы:

|  Диапазон | Значение        |
| --------: | --------------- |
| `100–199` | Информационные  |
| `200–299` | Успешные        |
| `300–399` | Перенаправления |
| `400–499` | Ошибки клиента  |
| `500–599` | Ошибки сервера  |

---

# Информационные коды

## 100 Continue

**`100 Continue`** означает, что сервер получил начальную часть запроса и клиент может продолжить отправку тела.

---

# Успешные коды

## 200 OK

**`200 OK`** означает, что запрос успешно обработан.

Точное значение зависит от метода.

Для GET обычно означает, что ресурс найден и передан в теле ответа.

---

## 201 Created

**`201 Created`** означает, что сервер успешно создал новый ресурс.

Ответ часто содержит:

```http
Location: /users/15
```

---

## 202 Accepted

**`202 Accepted`** означает, что запрос принят, но обработка ещё не завершена.

Используется для асинхронных операций:

* генерация отчёта;
* массовая обработка;
* отправка задачи в очередь.

---

## 204 No Content

**`204 No Content`** означает, что запрос успешно обработан, но тело ответа отсутствует.

Например, после успешного удаления:

```text
DELETE /users/15 → 204 No Content
```

---

# Перенаправления

## Redirect

**Redirect, или перенаправление** — это ответ, сообщающий клиенту, что ресурс нужно запросить по другому адресу.

Адрес обычно передаётся в заголовке:

```http
Location: https://example.com/new-address
```

---

## 301 Moved Permanently

**`301 Moved Permanently`** означает постоянное перемещение ресурса.

Клиенты и поисковые системы могут запомнить новый адрес.

---

## 302 Found

**`302 Found`** обычно используется для временного перенаправления.

Историческое поведение клиентов с POST-запросами может различаться, поэтому для строгой семантики предпочтительнее использовать `303`, `307` или `308`.

---

## 303 See Other

**`303 See Other`** указывает, что результат операции нужно получить отдельным GET-запросом по адресу из `Location`.

Часто применяется после POST:

```text
POST /orders
→ 303 See Other
→ Location: /orders/15
```

---

## 307 Temporary Redirect

**`307 Temporary Redirect`** — временное перенаправление с сохранением HTTP-метода и тела запроса.

POST останется POST.

---

## 308 Permanent Redirect

**`308 Permanent Redirect`** — постоянное перенаправление с сохранением метода и тела.

---

# Ошибки клиента

## 400 Bad Request

**`400 Bad Request`** означает, что сервер не может обработать запрос из-за его некорректного формата.

Причины:

* повреждённый JSON;
* отсутствует обязательный параметр;
* неверный формат поля;
* некорректный синтаксис.

---

## 401 Unauthorized

**`401 Unauthorized`** означает, что запрос не содержит корректных данных аутентификации.

Например:

* отсутствует токен;
* токен просрочен;
* токен повреждён.

Ответ может содержать:

```http
WWW-Authenticate: Bearer
```

---

## 403 Forbidden

**`403 Forbidden`** означает, что сервер понял запрос и, возможно, знает пользователя, но запрещает выполнение операции.

Разница:

```text
401 — сервер не подтвердил, кто вы;
403 — сервер знает, кто вы, но вам нельзя.
```

---

## 404 Not Found

**`404 Not Found`** означает, что запрашиваемый ресурс не найден.

Причины:

* неправильный URL;
* ресурс удалён;
* идентификатор отсутствует;
* сервер намеренно скрывает существование ресурса.

---

## 405 Method Not Allowed

**`405 Method Not Allowed`** означает, что ресурс существует, но данный HTTP-метод для него не поддерживается.

Например:

```text
POST /users/15
```

при поддержке только:

```text
GET, PUT, DELETE
```

Ответ может содержать:

```http
Allow: GET, PUT, DELETE
```

---

## 406 Not Acceptable

**`406 Not Acceptable`** означает, что сервер не может сформировать ответ в формате, указанном клиентом в `Accept`.

---

## 409 Conflict

**`409 Conflict`** означает конфликт запроса с текущим состоянием ресурса.

Примеры:

* пользователь с таким email уже существует;
* версия ресурса устарела;
* заказ уже отменён;
* невозможно создать дубликат.

---

## 415 Unsupported Media Type

**`415 Unsupported Media Type`** означает, что сервер не поддерживает формат тела запроса.

Например, сервер ожидает:

```http
Content-Type: application/json
```

а клиент отправил:

```http
Content-Type: text/plain
```

---

## 422 Unprocessable Content

**`422 Unprocessable Content`** означает, что синтаксис запроса корректен, но данные не проходят бизнес-валидацию.

Например:

```json
{
  "age": -15
}
```

JSON корректен, но возраст недопустим.

---

## 429 Too Many Requests

**`429 Too Many Requests`** означает превышение допустимого количества запросов.

Ответ может содержать:

```http
Retry-After: 60
```

Это означает, что запрос следует повторить не раньше чем через 60 секунд.

---

# Ошибки сервера

## 500 Internal Server Error

**`500 Internal Server Error`** означает непредвиденную ошибку на стороне сервера.

Клиент обычно не может исправить запрос так, чтобы гарантированно устранить такую ошибку.

---

## 502 Bad Gateway

**`502 Bad Gateway`** означает, что прокси или шлюз получил некорректный ответ от вышестоящего сервиса.

Часто встречается в микросервисной архитектуре.

---

## 503 Service Unavailable

**`503 Service Unavailable`** означает, что сервис временно недоступен.

Причины:

* перегрузка;
* технические работы;
* сервис ещё запускается;
* недоступна зависимость.

Ответ может содержать:

```http
Retry-After: 120
```

---

## 504 Gateway Timeout

**`504 Gateway Timeout`** означает, что шлюз или прокси не дождался ответа от другого сервиса.

---

# Stateful и stateless

## Stateless

**Stateless, или отсутствие состояния протокола** — это свойство HTTP, при котором каждый запрос рассматривается как самостоятельный.

Сервер не обязан помнить предыдущие запросы клиента.

Например, сервер не знает, что два запроса отправлены одним пользователем, если клиент не передаст идентификатор:

* в cookie;
* в токене;
* в заголовке;
* в параметре.

---

## Session

**Сессия** — это механизм сохранения состояния взаимодействия пользователя с сервером между HTTP-запросами.

Сервер может хранить данные сессии у себя, а клиент передаёт идентификатор:

```http
Cookie: sessionId=abc123
```

---

# Передача ответа

## Transfer-Encoding

**`Transfer-Encoding`** — заголовок, определяющий способ передачи тела HTTP/1.1-сообщения.

Пример:

```http
Transfer-Encoding: chunked
```

---

## Chunked transfer encoding

**Chunked transfer encoding** — способ передачи тела частями без предварительного указания полной длины.

Сервер может начинать отправку ответа ещё до того, как сформировано всё тело.

Актуально именно для HTTP/1.1. В HTTP/2 и HTTP/3 используются собственные механизмы фреймов.

---

## Keep-alive

**Keep-alive** — повторное использование одного сетевого соединения для нескольких HTTP-запросов.

Без keep-alive для каждого запроса пришлось бы заново:

* устанавливать TCP-соединение;
* выполнять TLS-handshake;
* закрывать соединение.

Это увеличило бы задержку и нагрузку.

В HTTP/1.1 постоянные соединения используются по умолчанию, если не указано обратное:

```http
Connection: close
```

---

# Кэширование

## HTTP cache

**HTTP-кэширование** — сохранение ответа для повторного использования без нового полного обращения к серверу.

Кэшироваться может:

* браузер;
* CDN;
* reverse proxy;
* промежуточный сервер;
* клиентское приложение.

---

## Cache-Control

**`Cache-Control`** — основной заголовок управления кэшированием.

Пример:

```http
Cache-Control: max-age=3600
```

Ответ можно использовать из кэша в течение 3600 секунд.

Другие директивы:

```text
no-cache
no-store
private
public
must-revalidate
```

`no-cache` не означает «не сохранять». Оно означает необходимость проверить актуальность перед повторным использованием.

Для полного запрета хранения используют:

```http
Cache-Control: no-store
```

---

## ETag

**`ETag`** — идентификатор версии представления ресурса.

Пример:

```http
ETag: "user-15-v3"
```

При повторном запросе клиент может отправить:

```http
If-None-Match: "user-15-v3"
```

Если ресурс не изменился, сервер отвечает:

```text
304 Not Modified
```

без полного тела.

---

## 304 Not Modified

**`304 Not Modified`** означает, что закэшированная версия ресурса всё ещё актуальна.

Это не обычный успешный ответ с телом. Клиент должен использовать ранее сохранённое содержимое.

---

## Vary

**`Vary`** — заголовок, указывающий, какие заголовки запроса влияют на выбор представления ресурса.

Пример:

```http
Vary: Accept-Encoding
```

Это означает, что сжатый и несжатый ответы должны храниться в кэше отдельно.

---

# Rate limiting

## Rate limit

**Rate limiting** — ограничение количества запросов от клиента за определённый период.

Используется для:

* защиты от перегрузки;
* ограничения тарифов;
* борьбы со злоупотреблениями;
* справедливого распределения ресурсов.

Сервер может возвращать заголовки:

```http
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 42
X-RateLimit-Reset: 1730000000
```

Названия `X-RateLimit-*` распространены, но не являются единым обязательным стандартом для всех API.

---

# CORS

## CORS

**CORS — Cross-Origin Resource Sharing** — это браузерный механизм, определяющий, может ли веб-страница обращаться к ресурсу другого origin.

CORS проверяется браузером. Обычная Java-программа не обязана соблюдать CORS-политику браузера.

---

## Origin

**Origin** определяется сочетанием:

* схемы;
* домена;
* порта.

Например:

```text
https://example.com:443
```

и:

```text
http://example.com:80
```

— разные origins.

---

## Access-Control-Allow-Credentials

**`Access-Control-Allow-Credentials`** — заголовок ответа CORS, разрешающий браузеру передавать cookies и другие credentials в межсайтовом запросе.

```http
Access-Control-Allow-Credentials: true
```

Он не является общей авторизацией клиента и работает в контексте браузерного CORS.

---

# HTTP-версии

## HTTP/1.1

**HTTP/1.1** — текстовая версия HTTP, в которой запросы и ответы представлены стартовыми строками, заголовками и телом.

Особенности:

* постоянные соединения;
* обязательный `Host`;
* последовательная передача сообщений;
* поддержка chunked encoding.

---

## HTTP/2

**HTTP/2** — бинарная версия HTTP, позволяющая передавать несколько потоков через одно соединение.

Основные возможности:

* мультиплексирование;
* бинарные фреймы;
* сжатие заголовков;
* эффективное использование соединения.

Методы, статусы и заголовки сохраняются логически, но передаются не в виде обычных текстовых строк HTTP/1.1.

---

## Multiplexing

**Мультиплексирование** — одновременная передача нескольких независимых HTTP-запросов и ответов через одно соединение.

Это уменьшает необходимость создавать много TCP-соединений.

---

## HTTP/3

**HTTP/3** — версия HTTP, работающая поверх QUIC.

В отличие от HTTP/1.1 и HTTP/2, она не использует TCP как транспортный протокол.

---

## QUIC

**QUIC** — транспортный протокол поверх UDP, включающий:

* надёжную доставку;
* шифрование;
* управление соединением;
* независимые потоки;
* быстрое восстановление после смены сети.

Фраза «HTTP/3 работает просто через UDP» слишком упрощает ситуацию. Над UDP находится QUIC, который реализует необходимые механизмы надёжности.

---

# HTTP-клиенты в Java

## HTTP client

**HTTP-клиент** — это библиотека или класс, который формирует HTTP-запросы, отправляет их и обрабатывает ответы.

HTTP-клиент обычно выполняет:

* создание соединения;
* DNS-разрешение;
* TLS;
* сериализацию тела;
* передачу заголовков;
* чтение ответа;
* обработку перенаправлений;
* управление соединениями;
* тайм-ауты.

---

## JDK HttpClient

**`java.net.http.HttpClient`** — встроенный HTTP-клиент Java, доступный начиная с Java 11.

Поддерживает:

* HTTP/1.1;
* HTTP/2;
* синхронные запросы;
* асинхронные запросы;
* HTTPS;
* redirects;
* тайм-ауты.

Для простых и средних задач обычно разумно сначала рассматривать встроенный `HttpClient`, поскольку он не требует внешней зависимости.

---

## Apache HttpClient

**Apache HttpClient** — внешняя Java-библиотека для выполнения HTTP-запросов.

Её используют, когда требуется:

* сложная настройка соединений;
* connection pool;
* proxy;
* разные схемы аутентификации;
* низкоуровневое управление;
* расширенная TLS-конфигурация;
* синхронный и асинхронный API.

Для нового кода не следует смешивать API Apache HttpClient 4.x и 5.x. Они используют разные пакеты и несовместимые классы.

---

## OkHttp

**OkHttp** — сторонний HTTP-клиент для Java и Android.

Он известен:

* компактным API;
* connection pooling;
* HTTP/2;
* WebSocket;
* удобными interceptors.

---

## HttpURLConnection

**`HttpURLConnection`** — старый встроенный HTTP API Java.

Он всё ещё существует, но для нового кода обычно менее удобен, чем `java.net.http.HttpClient`.

---

# Синхронные и асинхронные запросы

## Synchronous request

**Синхронный HTTP-запрос** блокирует текущий поток до получения ответа или ошибки.

Пример:

```java
HttpResponse<String> response =
        client.send(request, HttpResponse.BodyHandlers.ofString());
```

Пока `send()` не завершится, текущий поток не продолжит работу.

---

## Asynchronous request

**Асинхронный HTTP-запрос** возвращает объект, представляющий будущий результат, и не блокирует текущий поток на всё время ожидания.

```java
CompletableFuture<HttpResponse<String>> future =
        client.sendAsync(
                request,
                HttpResponse.BodyHandlers.ofString()
        );
```

Обработка:

```java
future.thenAccept(response ->
        System.out.println(response.body())
);
```

Асинхронность полезна при большом количестве независимых сетевых операций, но усложняет обработку ошибок и управление временем выполнения.

---

# Connection pool

## Connection pooling

**Connection pooling** — повторное использование заранее созданных сетевых соединений.

Вместо создания нового соединения для каждого запроса клиент:

1. берёт соединение из пула;
2. выполняет запрос;
3. возвращает соединение в пул.

Преимущества:

* меньше TCP-handshake;
* меньше TLS-handshake;
* ниже задержка;
* меньше нагрузка на сервер и клиент.

HTTP-клиент обычно следует создавать один раз и переиспользовать, а не создавать новый объект для каждого запроса.

Плохо:

```java
for (String url : urls) {
    HttpClient client = HttpClient.newHttpClient();
}
```

Лучше:

```java
HttpClient client = HttpClient.newHttpClient();

for (String url : urls) {
    // используем один client
}
```

---

# Builder

## Builder pattern

**Builder** — это порождающий паттерн, позволяющий пошагово настроить сложный объект перед созданием.

Пример:

```java
HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .followRedirects(HttpClient.Redirect.NORMAL)
        .version(HttpClient.Version.HTTP_2)
        .build();
```

Преимущества:

* читаемая конфигурация;
* именованные параметры через методы;
* возможность сделать итоговый объект неизменяемым;
* отсутствие огромного конструктора.

---

## Fluent API

**Fluent API** — это стиль API, в котором методы возвращают текущий объект или builder, позволяя объединять вызовы в цепочку.

```java
HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/users"))
        .header("Accept", "application/json")
        .GET()
        .build();
```

---

# Пример GET-запроса через JDK HttpClient

```java
import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;

public class Main {

    private static final URI POSTS_URI = URI.create(
            "https://jsonplaceholder.typicode.com/posts"
    );

    public static void main(String[] args) {
        HttpClient client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(5))
                .followRedirects(HttpClient.Redirect.NORMAL)
                .build();

        HttpRequest request = HttpRequest.newBuilder()
                .uri(POSTS_URI)
                .timeout(Duration.ofSeconds(30))
                .header("Accept", "application/json")
                .GET()
                .build();

        try {
            HttpResponse<String> response = client.send(
                    request,
                    HttpResponse.BodyHandlers.ofString()
            );

            System.out.println("Status: " + response.statusCode());
            System.out.println("Headers: " + response.headers().map());
            System.out.println("Body: " + response.body());

        } catch (InterruptedException exception) {
            Thread.currentThread().interrupt();
            System.err.println("Запрос был прерван");
        } catch (IOException exception) {
            System.err.println(
                    "Ошибка сетевого запроса: "
                            + exception.getMessage()
            );
        }
    }
}
```

Обработка `InterruptedException` важна: флаг прерывания потока нужно восстановить через:

```java
Thread.currentThread().interrupt();
```

# Проверка HTTP-ответа

Код состояния нужно проверять до преобразования тела:

```java
int statusCode = response.statusCode();

if (statusCode < 200 || statusCode >= 300) {
    throw new IllegalStateException(
            "Сервер вернул код " + statusCode
                    + ", body: " + response.body()
    );
}
```

Нельзя считать, что отсутствие `IOException` означает успешный бизнес-ответ.

Например:

```text
404
500
503
```

— это корректно полученные HTTP-ответы, а не ошибки сетевого соединения.

**JSON — JavaScript Object Notation** — это текстовый формат представления структурированных данных.

{

[

* объект;

# Сериализация и десериализация

## Serialization

**Сериализация** — это преобразование Java-объекта в формат для хранения или передачи.

Например:

```text
Java-объект → JSON
```

```java
Post post = new Post(1, "Java");

String json = objectMapper.writeValueAsString(post);
```

---

## Deserialization

**Десериализация** — это преобразование внешнего представления данных в Java-объект.

```text
JSON → Java-объект
```

```java
Post post = objectMapper.readValue(json, Post.class);
```

---

## JSON mapping

**JSON mapping** — это сопоставление свойств JSON с полями или свойствами Java-класса.

JSON:

```json
{
  "userId": 1,
  "title": "Java"
}
```

Java:

```java
public class Post {

    private int userId;
    private String title;

    // getters/setters
}
```

# Jackson

## Jackson

**Jackson** — это семейство Java-библиотек для работы с JSON и другими форматами данных.

Основные задачи:

* JSON → Java;
* Java → JSON;
* работа с JSON-деревом;
* настройка имён свойств;
* обработка дат;
* обработка коллекций;
* игнорирование или валидация полей.

В build-файле нужно использовать координаты и версию, соответствующие выбранной major-версии Jackson. Не следует бездумно смешивать зависимости и импорты из разных major-версий.

---

## ObjectMapper

**`ObjectMapper`** — основной класс Jackson для сериализации и десериализации.

```java
ObjectMapper objectMapper = new ObjectMapper();
```

Преобразование JSON в объект:

```java
Post post = objectMapper.readValue(json, Post.class);
```

Преобразование объекта в JSON:

```java
String json = objectMapper.writeValueAsString(post);
```

`ObjectMapper` — тяжёлый на конфигурацию объект. В приложении его обычно создают один раз и переиспользуют.

---

## DTO

**DTO — Data Transfer Object** — это объект, предназначенный для передачи данных между слоями или системами.

DTO обычно:

* не содержит сложной бизнес-логики;
* отражает структуру запроса или ответа;
* используется для JSON-маппинга;
* отделяет внешний контракт API от внутренних сущностей.

Пример:

```java
public record PostDto(
        int userId,
        int id,
        String title,
        String body
) {
}
```

---

## Record как DTO

Для неизменяемых DTO удобно использовать `record`:

```java
public record PostDto(
        int userId,
        int id,
        String title,
        String body
) {
}
```

Преимущества:

* поля автоматически `private final`;
* создаётся конструктор;
* создаются accessor-методы;
* создаются `equals()`, `hashCode()` и `toString()`;
* меньше шаблонного кода.

---

## @JsonProperty

**`@JsonProperty`** — аннотация Jackson, задающая имя JSON-свойства.

Она нужна, когда имя в JSON не совпадает с Java-именем.

JSON:

```json
{
  "user_id": 15
}
```

Java:

```java
public record UserDto(
        @JsonProperty("user_id")
        int userId
) {
}
```

Если имена совпадают:

```json
{
  "userId": 15
}
```

```java
public record UserDto(int userId) {
}
```

то `@JsonProperty` обычно не требуется.

---

## @JsonIgnoreProperties

**`@JsonIgnoreProperties`** — аннотация Jackson, позволяющая игнорировать неизвестные свойства JSON.

```java
@JsonIgnoreProperties(ignoreUnknown = true)
public record PostDto(
        int userId,
        int id,
        String title,
        String body
) {
}
```

Это полезно, когда внешний API может добавлять новые поля, а клиент не должен ломаться.

Однако бездумное игнорирование полей может скрыть несовместимое изменение контракта. Решение зависит от требований системы.

---

## TypeReference

**`TypeReference<T>`** — объект Jackson, позволяющий сохранить информацию о generic-типе во время десериализации.

Один объект:

```java
PostDto post = objectMapper.readValue(
        json,
        PostDto.class
);
```

Список объектов:

```java
List<PostDto> posts = objectMapper.readValue(
        json,
        new TypeReference<List<PostDto>>() {
        }
);
```

Нельзя написать:

```java
List<PostDto>.class
```

потому что такого class-объекта в Java не существует.

---

## Type erasure

**Стирание типов, или type erasure** — это механизм Java, при котором информация о generic-параметрах в значительной степени удаляется во время компиляции.

Во время выполнения:

```java
List<PostDto>
```

и:

```java
List<UserDto>
```

имеют один базовый runtime-класс `List`.

Поэтому Jackson нужен `TypeReference`, чтобы узнать тип элементов списка.

# Преобразование HTTP-ответа в Java-объекты

```java
import com.fasterxml.jackson.core.type.TypeReference;
import com.fasterxml.jackson.databind.ObjectMapper;

import java.io.IOException;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.util.List;

public class PostClient {

    private static final URI POSTS_URI = URI.create(
            "https://jsonplaceholder.typicode.com/posts"
    );

    private final HttpClient httpClient;
    private final ObjectMapper objectMapper;

    public PostClient(
            HttpClient httpClient,
            ObjectMapper objectMapper
    ) {
        this.httpClient = httpClient;
        this.objectMapper = objectMapper;
    }

    public List<PostDto> getPosts() throws IOException {
        HttpRequest request = HttpRequest.newBuilder()
                .uri(POSTS_URI)
                .header("Accept", "application/json")
                .GET()
                .build();

        try {
            HttpResponse<String> response = httpClient.send(
                    request,
                    HttpResponse.BodyHandlers.ofString()
            );

            validateResponse(response);

            return objectMapper.readValue(
                    response.body(),
                    new TypeReference<List<PostDto>>() {
                    }
            );

        } catch (InterruptedException exception) {
            Thread.currentThread().interrupt();

            throw new IOException(
                    "Получение постов было прервано",
                    exception
            );
        }
    }

    private void validateResponse(
            HttpResponse<String> response
    ) throws IOException {
        int statusCode = response.statusCode();

        if (statusCode < 200 || statusCode >= 300) {
            throw new IOException(
                    "Сервис вернул код "
                            + statusCode
                            + ", body: "
                            + response.body()
            );
        }

        String contentType = response.headers()
                .firstValue("Content-Type")
                .orElse("");

        if (!contentType.contains("application/json")) {
            throw new IOException(
                    "Ожидался JSON, получен: " + contentType
            );
        }
    }
}
```

DTO:

```java
public record PostDto(
        int userId,
        int id,
        String title,
        String body
) {
}
```

# HTTPS

## HTTPS

**HTTPS — Hypertext Transfer Protocol Secure** — это HTTP, передаваемый через защищённое TLS-соединение.

HTTPS обеспечивает:

* конфиденциальность;
* целостность;
* аутентификацию сервера.

HTTP-сообщение логически остаётся HTTP-запросом или ответом, но передаётся внутри зашифрованного TLS-соединения.

---

## Конфиденциальность

**Конфиденциальность** означает, что посторонний наблюдатель не может прочитать передаваемые данные.

---

## Целостность

**Целостность** означает, что изменение данных во время передачи будет обнаружено.

---

## Аутентификация сервера

**Аутентификация сервера** — проверка того, что клиент подключился к ожидаемому серверу, а не к подставному узлу.

Она выполняется с помощью сертификата и цепочки доверия.

HTTPS обычно аутентифицирует сервер. Пользователь аутентифицируется отдельно, например паролем или токеном.

---

## TLS certificate

**TLS-сертификат** — электронный документ, связывающий публичный ключ с доменным именем или организацией.

Клиент проверяет:

* срок действия;
* доменное имя;
* цепочку доверия;
* цифровую подпись;
* статус сертификата.

Формулировка «каждый запрос подписывается сертификатом» некорректна. Сертификат участвует в установлении доверенного TLS-соединения, после чего трафик защищается сессионными ключами.

---

# Продакшен-подход к HTTP-клиенту

При работе с удалённым API нужно предусматривать:

* тайм-аут соединения;
* тайм-аут запроса;
* проверку кода состояния;
* проверку `Content-Type`;
* ограничение размера ответа;
* корректное закрытие ресурсов;
* повторное использование HTTP-клиента;
* безопасное логирование;
* обработку `429`, `502`, `503`, `504`;
* повторные попытки только для подходящих операций;
* метрики и tracing;
* защиту секретных заголовков;
* валидацию JSON;
* обработку несовместимых изменений API.

Нельзя логировать без маскирования:

```http
Authorization
Cookie
Set-Cookie
API-Key
```

# Retry

## Retry

**Retry** — повторная попытка выполнить сетевую операцию после временной ошибки.

Повтор может быть уместен при:

```text
429
502
503
504
```

или временной сетевой ошибке.

Но нельзя автоматически повторять любой POST-запрос: операция могла выполниться на сервере, хотя клиент не получил ответ.

Для безопасного повторения используют:

* идемпотентные методы;
* idempotency key;
* проверку контракта API.

---

## Exponential backoff

**Exponential backoff** — стратегия, при которой задержка между повторными попытками постепенно увеличивается.

Например:

```text
1 секунда
2 секунды
4 секунды
8 секунд
```

Обычно добавляют случайное отклонение — jitter, чтобы много клиентов не повторили запрос одновременно.

---

## Circuit breaker

**Circuit breaker** — паттерн защиты системы от постоянных запросов к неработающему сервису.

Состояния:

* `CLOSED` — запросы разрешены;
* `OPEN` — запросы временно блокируются;
* `HALF_OPEN` — выполняются пробные запросы.

Circuit breaker не является частью HTTP. Это механизм устойчивости клиентского приложения.
