# Тема 4: Сборка проектов. Maven и Gradle

## Сборка проекта

**Определение:**

Сборка проекта — это процесс подготовки Java-проекта к запуску, тестированию или публикации.

Во время сборки могут выполняться разные действия:

* компиляция исходного кода;
* запуск тестов;
* копирование ресурсов;
* создание `.jar` или `.war` файла;
* подключение зависимостей;
* публикация готового артефакта в репозиторий.

Слово «сборка» может означать и сам процесс, и результат этого процесса.

**Пример:**

```bash
mvn clean package
```

Эта команда очищает старые результаты сборки и собирает новый `.jar` или `.war` файл.

---

## Build

**Определение:**

`Build` — это английское название сборки.

В Java-разработке `build` обычно означает процесс, при котором проект превращается из исходного кода в готовый результат: например, в `.jar` файл.

Также `build` может означать готовый файл, который получился после сборки.

**Пример:**

```bash
./gradlew build
```

Команда запускает сборку Gradle-проекта.

---

## Сборщик проекта

**Определение:**

Сборщик проекта — это инструмент, который автоматизирует сборку приложения.

Он помогает:

* компилировать код;
* запускать тесты;
* подключать библиотеки;
* создавать итоговые файлы;
* управлять версиями;
* собирать многомодульные проекты.

В Java чаще всего используют два сборщика:

* Maven;
* Gradle.

**Пример:**

```bash
mvn test
```

```bash
./gradlew test
```

Обе команды запускают тесты, но первая используется в Maven, а вторая — в Gradle.

---

## Maven

**Определение:**

Maven — это инструмент для управления и сборки Java-проектов.

Он позволяет описать проект в файле `pom.xml`, подключить зависимости, запустить тесты, собрать `.jar` или `.war` файл и управлять жизненным циклом проекта.

Maven работает декларативно: разработчик описывает, что нужно проекту, а Maven сам выполняет нужные шаги.

**Пример:**

```bash
mvn clean install
```

Команда очищает старую сборку, компилирует код, запускает тесты, собирает проект и устанавливает результат в локальный Maven-репозиторий.

---

## Gradle

**Определение:**

Gradle — это система сборки проектов, которая часто используется для Java-приложений.

Gradle похож на Maven по назначению, но вместо `pom.xml` использует файлы `build.gradle` или `build.gradle.kts`.

Gradle сочетает декларативный и процедурный подход: можно просто описывать настройки проекта, а можно добавлять собственную логику сборки.

**Пример:**

```bash
./gradlew build
```

Команда собирает Gradle-проект и запускает основные проверки.

---

## pom.xml

**Определение:**

`pom.xml` — это главный файл Maven-проекта.

В нём описывается информация о проекте:

* название;
* группа проекта;
* имя артефакта;
* версия;
* тип упаковки;
* зависимости;
* плагины;
* репозитории;
* настройки сборки.

`pom` расшифровывается как `Project Object Model`.

**Пример:**

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <groupId>ru.netology</groupId>
    <artifactId>my-app</artifactId>
    <version>1.0.0</version>
    <packaging>jar</packaging>
</project>
```

---

## Project Object Model

**Определение:**

`Project Object Model`, или `POM`, — это модель описания Maven-проекта.

Она определяет, как Maven должен понимать проект: какие у него зависимости, версия, структура, плагины и правила сборки.

Файл `pom.xml` — это практическая форма этой модели.

**Пример:**

```xml
<modelVersion>4.0.0</modelVersion>
```

Этот тег указывает версию модели POM.

---

## modelVersion

**Определение:**

`modelVersion` — это тег в `pom.xml`, который указывает версию модели POM.

Обычно в Maven используется значение:

```xml
<modelVersion>4.0.0</modelVersion>
```

Этот тег почти всегда пишется одинаково.

**Пример:**

```xml
<project>
    <modelVersion>4.0.0</modelVersion>
</project>
```

---

## groupId

**Определение:**

`groupId` — это идентификатор группы, организации или команды, которой принадлежит проект.

Часто `groupId` пишут в формате обратного домена.

Например:

```text
ru.netology
com.google
org.springframework
```

Вместе с `artifactId` и `version` он помогает Maven однозначно определить проект или библиотеку.

**Пример:**

```xml
<groupId>ru.netology</groupId>
```

---

## artifactId

**Определение:**

`artifactId` — это имя конкретного проекта или библиотеки.

Если `groupId` отвечает на вопрос «чей проект?», то `artifactId` отвечает на вопрос «какой именно проект?».

**Пример:**

```xml
<artifactId>my-app</artifactId>
```

Для зависимости это может выглядеть так:

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <version>5.10.0</version>
</dependency>
```

---

## version

**Определение:**

`version` — это версия проекта или зависимости.

Версия помогает понять, какая именно сборка проекта используется.

Один и тот же проект может иметь разные версии:

```text
1.0.0
1.1.0
2.0.0
1.0.0-SNAPSHOT
```

**Пример:**

```xml
<version>1.0.0</version>
```

---

## GAV

**Определение:**

`GAV` — это сокращение от:

* `groupId`;
* `artifactId`;
* `version`.

Эта тройка однозначно идентифицирует Maven-артефакт.

Проще говоря, Maven понимает зависимость не по одному названию, а по полной связке:

```text
groupId:artifactId:version
```

**Пример:**

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <version>5.10.0</version>
</dependency>
```

Эту зависимость можно представить так:

```text
org.junit.jupiter:junit-jupiter-api:5.10.0
```

---

## Артефакт

**Определение:**

Артефакт — это результат сборки проекта или отдельная библиотека, которую можно использовать как зависимость.

Чаще всего артефактом является файл:

* `.jar`;
* `.war`;
* `.ear`.

В Maven и Gradle артефакты хранятся в репозиториях.

**Пример:**

```text
my-app-1.0.0.jar
```

Это артефакт проекта `my-app` версии `1.0.0`.

---

## packaging

**Определение:**

`packaging` — это тег в Maven, который указывает, во что должен быть упакован проект.

Основные варианты:

* `jar` — обычное Java-приложение или библиотека;
* `war` — веб-приложение для запуска на сервере;
* `pom` — родительский проект без собственного исполняемого кода.

**Пример:**

```xml
<packaging>jar</packaging>
```

---

## JAR

**Определение:**

`JAR` — это формат архива для Java-приложений и библиотек.

Файл `.jar` может содержать:

* скомпилированные `.class` файлы;
* ресурсы;
* файл `MANIFEST.MF`;
* служебные файлы.

JAR часто используют для обычных Java-приложений и библиотек.

**Пример:**

```xml
<packaging>jar</packaging>
```

После сборки Maven может создать файл:

```text
target/my-app-1.0.0.jar
```

---

## WAR

**Определение:**

`WAR` — это формат архива для Java web-приложений.

Файл `.war` обычно разворачивается на веб-сервере или сервере приложений.

Например:

* Tomcat;
* Jetty;
* WildFly.

**Пример:**

```xml
<packaging>war</packaging>
```

---

## MANIFEST.MF

**Определение:**

`MANIFEST.MF` — это служебный файл внутри JAR-архива.

Он может содержать мета-информацию о приложении:

* главный класс для запуска;
* версию;
* автора;
* classpath;
* другие параметры.

Если JAR должен запускаться командой `java -jar`, в манифесте часто указывают `Main-Class`.

**Пример:**

```text
Main-Class: ru.netology.Main
```

---

## Зависимость

**Определение:**

Зависимость — это внешняя библиотека, которая нужна проекту для работы, тестирования или сборки.

Например, если проект использует JUnit для тестов, JUnit будет зависимостью.

Сборщик сам скачивает зависимости из репозиториев и подключает их к проекту.

**Пример Maven:**

```xml
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter-api</artifactId>
        <version>5.10.0</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

**Пример Gradle:**

```groovy
dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter-api:5.10.0'
}
```

---

## dependencies

**Определение:**

`dependencies` — это раздел, в котором перечисляются зависимости проекта.

В Maven это XML-тег.

В Gradle это блок в файле `build.gradle`.

**Пример Maven:**

```xml
<dependencies>
    <dependency>
        <groupId>org.apache.commons</groupId>
        <artifactId>commons-lang3</artifactId>
        <version>3.14.0</version>
    </dependency>
</dependencies>
```

**Пример Gradle:**

```groovy
dependencies {
    implementation 'org.apache.commons:commons-lang3:3.14.0'
}
```

---

## dependency

**Определение:**

`dependency` — это описание одной конкретной зависимости в Maven.

Внутри неё обычно указывают:

* `groupId`;
* `artifactId`;
* `version`;
* иногда `scope`.

**Пример:**

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>3.14.0</version>
</dependency>
```

---

## Репозиторий

**Определение:**

Репозиторий — это хранилище артефактов.

Из репозитория Maven или Gradle скачивает зависимости.

В репозиторий также можно публиковать собственные библиотеки и собранные проекты.

**Пример Maven:**

```xml
<repositories>
    <repository>
        <id>company-repo</id>
        <url>https://repo.company.com/maven</url>
    </repository>
</repositories>
```

**Пример Gradle:**

```groovy
repositories {
    mavenCentral()
}
```

---

## Локальный репозиторий Maven

**Определение:**

Локальный репозиторий Maven — это папка на компьютере разработчика, где Maven хранит скачанные зависимости и локально установленные артефакты.

По умолчанию он находится здесь:

```text
~/.m2/repository
```

Если зависимость уже есть в локальном репозитории, Maven не скачивает её заново.

**Пример:**

```bash
mvn install
```

Команда устанавливает собранный артефакт в локальный репозиторий.

---

## Центральный репозиторий Maven

**Определение:**

Центральный репозиторий Maven — это публичное хранилище Java-библиотек.

Именно оттуда Maven и Gradle чаще всего скачивают зависимости.

Например, библиотеки JUnit, Mockito, Lombok, Jackson и многие другие обычно доступны через Maven Central.

**Пример Gradle:**

```groovy
repositories {
    mavenCentral()
}
```

---

## Корпоративный репозиторий

**Определение:**

Корпоративный репозиторий — это внутреннее хранилище артефактов внутри компании.

Он нужен, чтобы хранить:

* внутренние библиотеки компании;
* приватные версии проектов;
* проверенные зависимости;
* промежуточные сборки.

В продакшене это часто делают через Nexus, Artifactory или похожие системы.

**Пример Maven:**

```xml
<repositories>
    <repository>
        <id>internal-repo</id>
        <url>https://repo.company.com/maven</url>
    </repository>
</repositories>
```

---

## build

**Определение:**

`build` — это раздел в `pom.xml`, который описывает настройки самой сборки.

В нём можно указать:

* где лежит исходный код;
* куда складывать результат компиляции;
* какие ресурсы копировать;
* какое имя будет у итогового файла;
* какие плагины использовать.

**Пример:**

```xml
<build>
    <finalName>app</finalName>
    <outputDirectory>target/classes</outputDirectory>
</build>
```

---

## sourceDirectory

**Определение:**

`sourceDirectory` — это тег Maven, который указывает, где лежат исходные Java-файлы.

По умолчанию Maven ожидает исходный код здесь:

```text
src/main/java
```

Обычно этот тег не указывают, если проект использует стандартную структуру Maven.

**Пример:**

```xml
<build>
    <sourceDirectory>src/main/java</sourceDirectory>
</build>
```

---

## resources

**Определение:**

`resources` — это раздел Maven, который описывает папки с ресурсами проекта.

Ресурсы — это не Java-код, а дополнительные файлы:

* `.properties`;
* `.xml`;
* `.json`;
* картинки;
* конфигурации.

При сборке ресурсы обычно копируются в итоговый результат.

**Пример:**

```xml
<build>
    <resources>
        <resource>
            <directory>src/main/resources</directory>
        </resource>
    </resources>
</build>
```

---

## outputDirectory

**Определение:**

`outputDirectory` — это тег Maven, который указывает, куда складывать результат компиляции.

Обычно Maven складывает скомпилированные `.class` файлы сюда:

```text
target/classes
```

**Пример:**

```xml
<build>
    <outputDirectory>target/classes</outputDirectory>
</build>
```

---

## finalName

**Определение:**

`finalName` — это тег Maven, который задаёт имя итогового файла сборки.

По умолчанию Maven формирует имя так:

```text
artifactId-version
```

Например:

```text
my-app-1.0.0.jar
```

Через `finalName` можно задать другое имя.

**Пример:**

```xml
<build>
    <finalName>application</finalName>
</build>
```

После сборки может получиться:

```text
application.jar
```

---

## target

**Определение:**

`target` — это папка, в которую Maven складывает результаты сборки.

В ней могут находиться:

* `.class` файлы;
* итоговый `.jar` или `.war`;
* отчёты тестов;
* временные файлы сборки.

Обычно папку `target` не добавляют в Git.

**Пример:**

```text
target/
├── classes/
├── generated-sources/
├── surefire-reports/
└── my-app-1.0.0.jar
```

---

## src/main/java

**Определение:**

`src/main/java` — это стандартная папка Maven и Gradle для основного Java-кода приложения.

Именно сюда обычно кладут классы, которые относятся к рабочей части программы.

**Пример:**

```text
src/main/java/ru/netology/Main.java
```

---

## src/main/resources

**Определение:**

`src/main/resources` — это стандартная папка для ресурсов приложения.

Туда кладут файлы, которые нужны программе во время работы, но не являются Java-кодом.

Например:

```text
application.properties
config.json
logback.xml
```

**Пример:**

```text
src/main/resources/application.properties
```

---

## src/test/java

**Определение:**

`src/test/java` — это стандартная папка для тестового Java-кода.

Туда кладут классы с unit-тестами.

**Пример:**

```text
src/test/java/ru/netology/CalculatorTest.java
```

---

## src/test/resources

**Определение:**

`src/test/resources` — это стандартная папка для ресурсов, которые нужны только тестам.

Например:

* тестовые JSON-файлы;
* тестовые конфиги;
* файлы с ожидаемыми результатами.

**Пример:**

```text
src/test/resources/test-data.json
```

---

## Жизненный цикл сборки

**Определение:**

Жизненный цикл сборки — это заранее определённая последовательность фаз, через которые проходит проект при сборке.

Например, Maven не просто «собирает проект», а проходит по фазам:

* проверить проект;
* скомпилировать код;
* запустить тесты;
* упаковать результат;
* установить или опубликовать артефакт.

**Пример:**

```bash
mvn package
```

Команда выполнит не только фазу `package`, но и предыдущие фазы жизненного цикла.

---

## Фаза сборки

**Определение:**

Фаза сборки — это отдельный этап жизненного цикла сборки.

Каждая фаза отвечает за конкретную часть процесса.

Например:

* `compile` — компиляция;
* `test` — запуск тестов;
* `package` — упаковка проекта.

**Пример:**

```bash
mvn test
```

Команда запускает фазу `test` и все нужные фазы до неё.

---

## validate

**Определение:**

`validate` — это фаза Maven, которая проверяет, корректно ли описан проект и достаточно ли информации для сборки.

На этом этапе Maven убеждается, что проект можно собирать дальше.

**Пример:**

```bash
mvn validate
```

---

## compile

**Определение:**

`compile` — это фаза Maven, которая компилирует основной исходный код проекта.

Java-файлы из `src/main/java` превращаются в `.class` файлы.

**Пример:**

```bash
mvn compile
```

После выполнения скомпилированные классы обычно появляются в:

```text
target/classes
```

---

## test

**Определение:**

`test` — это фаза Maven, которая запускает тесты проекта.

Обычно тесты лежат в папке:

```text
src/test/java
```

Если тесты не проходят, сборка обычно считается неуспешной.

**Пример:**

```bash
mvn test
```

---

## package

**Определение:**

`package` — это фаза Maven, которая упаковывает проект в итоговый файл.

Например:

* `.jar`;
* `.war`.

Перед `package` Maven выполняет предыдущие фазы: проверку, компиляцию и тесты.

**Пример:**

```bash
mvn package
```

Результат может появиться здесь:

```text
target/my-app-1.0.0.jar
```

---

## verify

**Определение:**

`verify` — это фаза Maven, которая выполняет проверки, подтверждающие, что собранный пакет соответствует требованиям качества.

Например, на этой фазе могут запускаться дополнительные проверки или интеграционные тесты.

**Пример:**

```bash
mvn verify
```

---

## install

**Определение:**

`install` — это фаза Maven, которая устанавливает собранный артефакт в локальный Maven-репозиторий.

После этого другой локальный проект на твоём компьютере может подключить этот артефакт как зависимость.

**Пример:**

```bash
mvn install
```

---

## deploy

**Определение:**

`deploy` — это фаза Maven, которая публикует собранный артефакт в удалённый репозиторий.

Обычно используется в командной разработке или на CI/CD-сервере.

После `deploy` артефакт становится доступен другим разработчикам или проектам.

**Пример:**

```bash
mvn deploy
```

---

## clean

**Определение:**

`clean` — это фаза, которая удаляет результаты предыдущей сборки.

В Maven обычно удаляется папка:

```text
target
```

`clean` не запускается автоматически. Её нужно явно указать в команде.

**Пример:**

```bash
mvn clean
```

Часто используют так:

```bash
mvn clean install
```

---

## mvn clean install

**Определение:**

`mvn clean install` — это частая команда Maven для полной пересборки проекта.

Она делает две основные вещи:

1. `clean` — удаляет старые результаты сборки.
2. `install` — собирает проект и устанавливает артефакт в локальный Maven-репозиторий.

При запуске `install` Maven также выполнит предыдущие фазы жизненного цикла: `validate`, `compile`, `test`, `package`, `verify`.

**Пример:**

```bash
mvn clean install
```

## scope

**Определение:**

`scope` — это область видимости зависимости в Maven.

Она показывает, когда именно нужна зависимость:

* при компиляции;
* при запуске приложения;
* только для тестов;
* предоставляется внешней средой.

Например, JUnit нужен только для тестов, поэтому ему обычно ставят `scope` со значением `test`.

**Пример:**

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <version>5.10.0</version>
    <scope>test</scope>
</dependency>
```

---

## compile scope

**Определение:**

`compile` — это область видимости зависимости Maven по умолчанию.

Такая зависимость нужна и при компиляции, и при запуске приложения.

Если `scope` не указан, Maven обычно считает, что используется `compile`.

**Пример:**

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
    <version>3.14.0</version>
</dependency>
```

---

## test scope

**Определение:**

`test` — это область видимости зависимости Maven, при которой библиотека нужна только для тестов.

Такая зависимость не нужна рабочему приложению после сборки.

Типичный пример — JUnit.

**Пример:**

```xml
<dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter-api</artifactId>
    <version>5.10.0</version>
    <scope>test</scope>
</dependency>
```

---

## provided scope

**Определение:**

`provided` — это область видимости Maven, при которой зависимость нужна для компиляции, но во время запуска её предоставляет внешняя среда.

Например, веб-сервер может сам предоставлять некоторые библиотеки.

**Пример:**

```xml
<dependency>
    <groupId>jakarta.servlet</groupId>
    <artifactId>jakarta.servlet-api</artifactId>
    <version>6.0.0</version>
    <scope>provided</scope>
</dependency>
```

---

## runtime scope

**Определение:**

`runtime` — это область видимости Maven, при которой зависимость не нужна для компиляции, но нужна во время запуска программы.

Например, драйвер базы данных часто нужен именно во время выполнения приложения.

**Пример:**

```xml
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>42.7.3</version>
    <scope>runtime</scope>
</dependency>
```

---

## properties

**Определение:**

`properties` — это раздел в `pom.xml`, где можно объявлять переменные.

Их удобно использовать для версий зависимостей или настроек проекта.

Если одна и та же версия используется в нескольких местах, её лучше вынести в `properties`.

**Пример:**

```xml
<properties>
    <junit.version>5.10.0</junit.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter-api</artifactId>
        <version>${junit.version}</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

---

## Плагин Maven

**Определение:**

Плагин Maven — это расширение, которое выполняет определённые задачи во время сборки.

Например, плагины могут:

* компилировать код;
* запускать тесты;
* проверять стиль кода;
* создавать JAR;
* генерировать отчёты.

Maven сам выполняет задачи сборки через плагины.

**Пример:**

```xml
<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-compiler-plugin</artifactId>
            <version>3.12.1</version>
        </plugin>
    </plugins>
</build>
```

## Модуль

**Определение:**

Модуль — это функционально законченная часть проекта, которую можно разрабатывать и собирать отдельно.

Модуль может отвечать за конкретную часть приложения:

* работу с базой данных;
* бизнес-логику;
* API;
* веб-интерфейс.

Многомодульность помогает не превращать проект в одну огромную папку «тут всё, не трогать, оно живое».

**Пример:**

```text
my-project/
├── app-api/
├── app-db/
├── app-service/
└── pom.xml
```

---

## Многомодульный проект

**Определение:**

Многомодульный проект — это проект, который состоит из нескольких связанных модулей.

В Maven родительский проект обычно имеет `packaging` со значением `pom` и перечисляет дочерние модули в разделе `modules`.

**Пример Maven:**

```xml
<packaging>pom</packaging>

<modules>
    <module>app-api</module>
    <module>app-db</module>
</modules>
```

**Пример Gradle:**

```groovy
include 'app-api'
include 'app-db'
```

---

## parent

**Определение:**

`parent` — это раздел в `pom.xml`, который указывает родительский Maven-проект.

Дочерний модуль может наследовать от родителя:

* версию;
* общие зависимости;
* настройки плагинов;
* свойства;
* настройки сборки.

**Пример:**

```xml
<parent>
    <groupId>ru.netology</groupId>
    <artifactId>app-parent</artifactId>
    <version>1.0.0</version>
</parent>
```

---

## modules

**Определение:**

`modules` — это раздел в родительском `pom.xml`, где перечисляются модули проекта.

Maven будет понимать, что эти подпроекты относятся к одной общей сборке.

**Пример:**

```xml
<modules>
    <module>app-api</module>
    <module>app-db</module>
    <module>app-service</module>
</modules>
```

## build.gradle

**Определение:**

`build.gradle` — это главный файл описания сборки Gradle-проекта.

Он похож по назначению на `pom.xml` в Maven.

В нём можно описать:

* плагины;
* зависимости;
* репозитории;
* версию проекта;
* группу проекта;
* дополнительные задачи сборки.

**Пример:**

```groovy
plugins {
    id 'java'
}

group = 'ru.netology'
version = '1.0.0'

repositories {
    mavenCentral()
}

dependencies {
    testImplementation 'org.junit.jupiter:junit-jupiter-api:5.10.0'
}
```

## build.gradle.kts

**Определение:**

`build.gradle.kts` — это файл описания сборки Gradle на языке Kotlin DSL.

Он выполняет ту же роль, что и `build.gradle`, но пишется на Kotlin, а не на Groovy.

**Пример:**

```kotlin
plugins {
    java
}

group = "ru.netology"
version = "1.0.0"

repositories {
    mavenCentral()
}
```

## settings.gradle

**Определение:**

`settings.gradle` — это файл настроек Gradle-проекта.

В нём обычно указывают:

* имя корневого проекта;
* список модулей;
* настройки подключения подпроектов.

**Пример:**

```groovy
rootProject.name = 'my-app'

include 'app-api'
include 'app-db'
```

## Gradle Wrapper

**Определение:**

Gradle Wrapper — это механизм, который позволяет запускать проект с нужной версией Gradle без ручной установки Gradle на компьютер.

В проекте обычно есть файлы:

```text
gradlew
gradlew.bat
gradle/wrapper/gradle-wrapper.jar
gradle/wrapper/gradle-wrapper.properties
```

В продакшене лучше запускать Gradle через Wrapper, потому что команда получает одинаковую версию Gradle у всех разработчиков и на CI.

**Пример:**

```bash
./gradlew build
```

На Windows:

```bash
gradlew.bat build
```

## gradlew

`gradlew` — это скрипт Gradle Wrapper для Linux и macOS.

Он запускает сборку проекта через ту версию Gradle, которая указана в настройках wrapper.

**Пример:**

```bash
./gradlew test
```

## gradlew.bat

**Определение:**

`gradlew.bat` — это скрипт Gradle Wrapper для Windows.

Он выполняет ту же задачу, что и `gradlew`, но используется в Windows-системах.

**Пример:**


## implementation

```groovy
dependencies {
```

```groovy
repositories {
```

`./gradlew assemble` — это команда Gradle, которая собирает итоговый артефакт без полного цикла проверок.

## CI

**Определение:**

`CI`, или `Continuous Integration`, — это непрерывная интеграция.

Это автоматический процесс, при котором код регулярно собирается и тестируется.

Обычно CI запускается после отправки кода в репозиторий.

Сборщики Maven и Gradle хорошо подходят для CI, потому что позволяют запускать сборку одной командой.

**Пример:**

```bash
mvn clean test
```

или:

```bash
./gradlew test
```

---

## Continuous Integration

**Определение:**

`Continuous Integration` — это полное название CI.

Главная идея: часто проверять, что новый код не сломал проект.

В реальной разработке CI помогает быстрее находить ошибки, потому что проект автоматически собирается и тестируется после изменений.

**Пример:**

```text
Разработчик отправил код в GitHub
        ↓
CI-сервер запустил сборку
        ↓
Запустились тесты
        ↓
Команда увидела результат
```

---

## SNAPSHOT

**Определение:**

`SNAPSHOT` — это версия проекта, которая находится в разработке и может часто меняться.

Например:

```text
1.0.0-SNAPSHOT
```

Такую версию обычно используют до финального релиза.

Она означает: «это ещё не стабильная финальная версия, она может обновляться».

**Пример:**

```xml
<version>1.0.0-SNAPSHOT</version>
```

---

## Релизная версия

**Определение:**

Релизная версия — это стабильная версия проекта, которую можно использовать как готовый результат.

В отличие от `SNAPSHOT`, релизная версия не должна постоянно меняться.

**Пример:**

```xml
<version>1.0.0</version>
```

---

## Версионность проекта

**Определение:**

Версионность проекта — это процесс ведения и документирования версий проекта.

Она нужна, чтобы понимать:

* какая версия сейчас используется;
* какие изменения были внесены;
* какую версию можно безопасно подключать;
* чем одна сборка отличается от другой.

**Пример:**

```text
1.0.0  — первый стабильный релиз
1.1.0  — добавили новую функциональность
1.1.1  — исправили ошибку
2.0.0  — крупное изменение проекта
```
