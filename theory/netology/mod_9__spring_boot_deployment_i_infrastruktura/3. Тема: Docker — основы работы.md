# 3. Тема: Docker — основы работы

## Docker

**Определение:**

Docker — программное обеспечение для развёртывания и управления переносимой средой, в которой работает приложение. 

Главная идея Docker — упаковать приложение вместе с необходимым окружением и зависимостями, чтобы оно одинаково запускалось на разных машинах.

```text
Приложение
+
зависимости
+
окружение
        ↓
Docker Image
        ↓
Docker Container
```

В презентации среди преимуществ Docker отдельно отмечены переносимость окружения, совместная упаковка приложения и зависимостей и возможность декларативно описать сборку через `Dockerfile`. 

---

## Docker Image

**Определение:**

Docker Image, или Docker-образ, — шаблон, на основе которого создаются контейнеры.

Один и тот же образ можно использовать для запуска нескольких одинаковых контейнеров. 

Например:

```text
my-app:1.0
       ↓
 ┌───────────┐
 │Container 1│
 └───────────┘

 ┌───────────┐
 │Container 2│
 └───────────┘
```

Образ сам по себе не является запущенным приложением.

---

## Docker Container

**Определение:**

Docker Container — набор процессов, выполняющихся в запущенной копии Docker-образа. 

Проще:

```text
Image     → шаблон
Container → запущенный экземпляр этого шаблона
```

Аналогия с Java:

```text
Class  → Image
Object → Container
```

Аналогия не идеальная, но хорошо помогает запомнить различие.

---

## Image Layer

**Определение:**

Layer — отдельный слой Docker-образа.

Docker-образ состоит из логической последовательности слоёв. 

Например:

```text
┌─────────────────────────┐
│ COPY app.jar            │
├─────────────────────────┤
│ установка зависимостей  │
├─────────────────────────┤
│ Java Runtime            │
├─────────────────────────┤
│ базовый Linux-образ     │
└─────────────────────────┘
```

Слои можно переиспользовать, если они не изменились, что ускоряет последующие сборки образа. Это преимущество отдельно отмечено в презентации. 

---

## Docker Client

**Определение:**

Docker Client — клиентская часть Docker, через которую пользователь отправляет команды Docker.

Например:

```bash
docker build
docker run
docker pull
```

На архитектурной схеме презентации Docker Client взаимодействует с Docker daemon, а уже daemon управляет образами, контейнерами и обращается к registry. 

---

## Docker Daemon

**Определение:**

Docker Daemon — фоновый процесс Docker, который выполняет основную работу с контейнерами и образами.

Схематично:

```text
Developer
   ↓
Docker Client
   ↓
Docker Daemon
   ↓
Images / Containers
```

Docker daemon также взаимодействует с registry образов. Такая архитектура показана на странице 7 презентации. 

---

## Docker Registry

**Определение:**

Docker Registry — хранилище Docker-образов.

Схема:

```text
Registry
   ↓ pull
Docker
   ↓
Image
   ↓
Container
```

На архитектурной схеме презентации registry является отдельным компонентом, с которым работает Docker daemon. 

---

# Dockerfile

## Dockerfile

**Определение:**

`Dockerfile` — текстовый файл, описывающий метаданные и слои будущего Docker-образа. 

Пример из презентации по смыслу выглядит так:

```dockerfile
FROM openjdk:8-jdk-alpine

EXPOSE 8080

ADD build/libs/app.jar app.jar

ENTRYPOINT ["java", "-jar", "app.jar"]
```

Docker читает инструкции сверху вниз и на их основе строит образ.

---

## `FROM`

**Определение:**

`FROM` — инструкция Dockerfile, которая задаёт базовый образ для создаваемого Docker-образа. 

Пример:

```dockerfile
FROM ubuntu
```

Или для Java:

```dockerfile
FROM eclipse-temurin:21-jdk
```

Базовый образ можно воспринимать как фундамент будущего образа:

```text
Ubuntu / Java Runtime
        ↓
наше приложение
        ↓
итоговый image
```

---

## Base Image

**Определение:**

Base Image — базовый, или родительский, образ, который используется как исходная основа для нового Docker-образа. 

Например:

```dockerfile
FROM ubuntu
```

Здесь:

```text
ubuntu
```

— базовый образ.

---

## `RUN`

**Определение:**

`RUN` — инструкция Dockerfile для выполнения команды во время сборки образа.

Она используется для выполнения команд, изменения файловой системы и установки библиотек или пакетов. 

Пример:

```dockerfile
RUN apt-get update
```

или:

```dockerfile
RUN apt-get install -y curl
```

Важно понимать:

```text
RUN выполняется при BUILD образа
```

то есть при:

```bash
docker build
```

а не при обычном запуске контейнера.

---

## `COPY`

**Определение:**

`COPY` — инструкция Dockerfile, копирующая файлы из контекста сборки внутрь Docker-образа. 

Пример:

```dockerfile
COPY . /src
```

Означает:

```text
файлы проекта
     ↓
Docker image
     ↓
/src
```

Для Java часто можно встретить:

```dockerfile
COPY target/app.jar app.jar
```

---

## Build Context

**Определение:**

Build Context — каталог с файлами, доступными Docker во время сборки образа.

В презентации понятие появляется при объяснении `COPY`: содержимое каталога, переданного при сборке Docker, можно копировать внутрь образа. 

Например:

```bash
docker build .
```

`.` — контекст сборки.

---

## `ADD`

**Определение:**

`ADD` — инструкция Dockerfile для добавления файлов в образ.

В презентации показаны дополнительные возможности `ADD`: получение файла с удалённого адреса и автоматическая распаковка архивов. 

Пример:

```dockerfile
ADD ./assets.zip /var/www/htdocs/assets/
```

По материалу презентации архив будет распакован в указанный каталог.

---

## `ENV`

**Определение:**

`ENV` — инструкция Dockerfile, задающая переменные окружения для контейнеров, запускаемых из этого образа. 

Пример:

```dockerfile
ENV WEBAPP_PORT=8080
```

После запуска контейнера приложение сможет использовать эту переменную.

Значение также можно передать при запуске:

```bash
docker run -e WEBAPP_PORT=8000 my-app
```

---

## Environment Variable

**Определение:**

Environment Variable — переменная окружения, используемая для передачи конфигурационных значений приложению или процессу.

В Docker они могут задаваться через `ENV` в Dockerfile или при `docker run`. 

Например:

```text
DATABASE_URL
SERVER_PORT
SPRING_PROFILES_ACTIVE
```

---

## `EXPOSE`

**Определение:**

`EXPOSE` — инструкция Dockerfile, описывающая порты, на которых предполагается работа приложения внутри контейнера.

В презентации приведены примеры: 

```dockerfile
EXPOSE 8080
```

или:

```dockerfile
EXPOSE 80 443
```

Важно различать:

```text
EXPOSE 8080
```

и фактическую публикацию порта при запуске контейнера.

`EXPOSE` описывает предполагаемый порт контейнера, но сам по себе не делает его доступным снаружи.

---

# Запуск приложения

## `ENTRYPOINT`

**Определение:**

`ENTRYPOINT` — инструкция Dockerfile, задающая основную команду, которая должна выполняться при запуске контейнера.

В презентации показан пример: 

```dockerfile
ENTRYPOINT ["nginx"]
```

Для Java-приложения типичный вариант:

```dockerfile
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Контейнер запускается → запускается Java-приложение.

---

## `CMD`

**Определение:**

`CMD` — инструкция Dockerfile, задающая команду или аргументы по умолчанию для запуска контейнера.

В презентации `CMD` показан совместно с `ENTRYPOINT`: 

```dockerfile
ENTRYPOINT ["nginx"]
CMD ["-g", "daemon off;"]
```

Итоговая команда по смыслу:

```text
nginx -g "daemon off;"
```

Удобная модель для запоминания:

```text
ENTRYPOINT → что запускаем

CMD → с какими параметрами запускаем по умолчанию
```

---

## `ARG`

**Определение:**

`ARG` — инструкция Dockerfile для определения переменной, доступной во время сборки образа. 

Главное отличие от `ENV`:

```text
ARG → используется во время build

ENV → доступна контейнеру во время работы
```

---

## `HEALTHCHECK`

**Определение:**

`HEALTHCHECK` — инструкция Dockerfile, задающая команду для проверки состояния контейнера. 

Упрощённо:

```text
Container
   ↓
HEALTHCHECK
   ↓
healthy / unhealthy
```

Это позволяет Docker определять, работает ли приложение внутри контейнера корректно.

---

## `LABEL`

**Определение:**

`LABEL` — инструкция Dockerfile для добавления метаданных к Docker-образу. 

Например:

```dockerfile
LABEL version="1.0"
```

---

## `WORKDIR`

**Определение:**

`WORKDIR` — инструкция Dockerfile, задающая рабочую директорию для следующих инструкций. 

Например:

```dockerfile
WORKDIR /app

COPY app.jar app.jar
```

Теперь:

```text
app.jar
```

будет находиться относительно:

```text
/app
```

---

## `VOLUME`

**Определение:**

`VOLUME` — инструкция Dockerfile, создающая точку монтирования для работы с постоянным хранилищем данных. 

Главная идея:

```text
Container
   ↓
Volume
   ↓
данные могут существовать независимо
от файловой системы контейнера
```

Это особенно важно, например, для баз данных.

---

## `USER`

**Определение:**

`USER` — инструкция Dockerfile, задающая пользователя или UID, от имени которого выполняется сборка или запускается контейнер. 

---

## `SHELL`

**Определение:**

`SHELL` — инструкция Dockerfile, позволяющая указать программу, используемую для интерпретации команд строкового формата, например `RUN` и `CMD`. 

---

# Docker Build Cache

## Build Cache

**Определение:**

Build Cache — механизм повторного использования уже построенных слоёв Docker-образа.

Если соответствующая инструкция Dockerfile и необходимые ей данные не изменились, Docker может использовать уже существующий слой вместо повторного выполнения операции.

Поэтому в презентации рекомендуется сначала размещать редко изменяемые инструкции и использовать кеш для ускорения сборки. 

Например:

```dockerfile
FROM eclipse-temurin:21-jdk

COPY pom.xml .
RUN mvn dependency:go-offline

COPY src ./src
```

Если исходный код изменился, а зависимости нет, Docker потенциально сможет повторно использовать ранее созданный слой с зависимостями.

---

# Best Practices Dockerfile

В презентации выделены три основных правила:

```text
1. Использовать минимальное количество слоёв.

2. Сначала размещать статичные
   и редко изменяемые инструкции.

3. Использовать Docker build cache
   для ускорения сборки.
```



Основная причина — Docker строит образ слоями, поэтому порядок инструкций напрямую влияет на возможность переиспользовать кеш.

# Что обязательно запомнить из темы

Главная цепочка:

```text
Dockerfile
    ↓
docker build
    ↓
Docker Image
    ↓
docker run
    ↓
Docker Container
    ↓
работающее приложение
```

Архитектура Docker:

```text
Docker Client
      ↓
Docker Daemon
   ↙       ↘
Images   Containers
   ↑
Registry
```

И самое важное различие:

```text
Dockerfile → инструкция, как собрать образ

Image      → готовый шаблон приложения

Container  → запущенный экземпляр image
```

Для Dockerfile стоит в первую очередь помнить:

```text
FROM       → базовый образ

RUN        → выполнить команду при сборке

COPY       → скопировать файл в image

ENV        → переменная окружения

EXPOSE     → порт приложения

WORKDIR    → рабочая директория

ENTRYPOINT → основная запускаемая команда

CMD        → аргументы/команда по умолчанию
```
