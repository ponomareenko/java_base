# Тема 6: Мониторинг: Spring Boot Actuator, Prometheus и Grafana

## Мониторинг — Monitoring

**Определение:**

Мониторинг — это регулярный сбор и анализ показателей работы системы, позволяющий замечать проблемы и оценивать её состояние.

В продакшене мониторинг помогает обнаружить рост ошибок, нехватку ресурсов и замедление приложения до массовых жалоб пользователей.

**Пример:**

Для Java-приложения отслеживают:

- использование памяти JVM;
- время ответа на запросы;
- количество ответов HTTP 500;
- доступность приложения.

---

## Метрика — Metric

**Определение:**

Метрика — это числовой показатель работы системы: количество запросов, объём занятой памяти или длительность операции.

Для анализа важны не только значения, но и их изменение во времени.

**Пример:**

```text
jvm_memory_used_bytes{area="heap",id="G1 Old Gen"} 52428800
```

Значение показывает, что указанный пул heap-памяти занимает 50 МиБ.

---

## Инструментирование — Instrumentation

**Определение:**

Инструментирование — это добавление в приложение механизмов измерения его работы.

Оно бывает автоматическим, например сбор HTTP-метрик средствами Spring Boot, и ручным — когда разработчик добавляет собственные измерения.

**Пример:**

```java
Counter orderCounter = registry.counter("orders.created");
orderCounter.increment();
```

Каждый вызов `increment()` регистрирует создание заказа.

---

## Prometheus

**Определение:**

Prometheus — система мониторинга, которая собирает метрики, хранит их историю, выполняет запросы и проверяет условия алертов.

В типичной конфигурации Prometheus сам обращается к приложениям за метриками.

**Пример:**

```text
Spring Boot: отдаёт метрики
        ↓
Prometheus: собирает и хранит
        ↓
Grafana: запрашивает и отображает
```

Источник: [обзор Prometheus](https://prometheus.io/docs/introduction/overview/).

---

## Pull-модель — Pull Model

**Определение:**

Pull-модель — способ сбора данных, при котором система мониторинга сама запрашивает метрики у наблюдаемых сервисов.

**Пример:**

Каждые 5 секунд Prometheus отправляет запрос:

```http
GET http://app:8080/actuator/prometheus
```

Приложение отвечает текущими значениями метрик.

---

## Сбор метрик — Scrape

**Определение:**

Scrape — отдельная попытка Prometheus получить и обработать метрики наблюдаемого сервиса.

Scrape interval — промежуток между такими попытками.

**Пример:**

```yaml
global:
  scrape_interval: 5s
```

Prometheus по умолчанию собирает метрики каждые 5 секунд. Это не частота HTTP-запросов пользователей.

---

## Цель сбора — Target

**Определение:**

Target — адрес сервиса, с которого Prometheus собирает метрики.

Для получения полного URL также учитываются протокол и путь к endpoint.

**Пример:**

```yaml
metrics_path: /actuator/prometheus
static_configs:
  - targets:
      - app:8080
```

Полный адрес сбора при стандартном протоколе HTTP:

```text
http://app:8080/actuator/prometheus
```

---

## Задание сбора — Job

**Определение:**

Job — именованная группа экземпляров, объединённых общей конфигурацией сбора метрик.

Instance — конкретный экземпляр внутри этой группы.

**Пример:**

```yaml
scrape_configs:
  - job_name: spring
    static_configs:
      - targets:
          - app-1:8080
          - app-2:8080
```

Здесь один job `spring` и два instance: `app-1:8080` и `app-2:8080`.

Источник: [Jobs and instances](https://prometheus.io/docs/concepts/jobs_instances/).

---

## Метка — Label

**Определение:**

Label — пара «имя — значение», которая уточняет, к чему относится метрика.

Метки позволяют фильтровать и группировать показатели.

**Пример:**

```promql
http_server_requests_seconds_count{
  job="spring",
  status="500",
  method="GET"
}
```

Запрос выбирает счётчики GET-запросов, завершившихся ответом HTTP 500, у задания `spring`.

---

## Временной ряд — Time Series

**Определение:**

Временной ряд — последовательность значений с отметками времени, определяемая именем метрики и полным набором её меток.

Изменение значения метки создаёт другой временной ряд.

**Пример:**

```text
http_server_requests_seconds_count{status="200"}
http_server_requests_seconds_count{status="500"}
```

Это разные временные ряды, хотя имя метрики одинаковое.

Источник: [модель данных Prometheus](https://prometheus.io/docs/concepts/data_model/).

---

## Кардинальность — Cardinality

**Определение:**

Кардинальность — количество различных временных рядов, возникающих из сочетаний значений меток.

Высокая кардинальность увеличивает расход памяти, объём хранения и стоимость запросов.

**Пример:**

Подходящая метка:

```text
status="500"
```

Опасная метка:

```text
request_id="уникальный идентификатор каждого запроса"
```

Во втором случае каждый запрос может создавать отдельный временной ряд. Поэтому уникальные идентификаторы пользователей, заказов и запросов обычно не используют как метки метрик.

Источник: [рекомендации Prometheus по именованию и меткам](https://prometheus.io/docs/practices/naming/).

---

## Счётчик — Counter

**Определение:**

Counter — тип метрики для накопительного подсчёта событий.

Он увеличивается, а при перезапуске процесса может сброситься. Уменьшать его для отражения текущего состояния нельзя.

**Пример:**

```text
Обработано запросов: 100 → 101 → 102
После перезапуска:  0 → 1 → 2
```

Counter подходит для числа ошибок и заказов. Для текущего количества активных пользователей нужен другой тип.

---

## Текущее значение — Gauge

**Определение:**

Gauge — тип метрики, который отражает текущее состояние и может увеличиваться и уменьшаться.

**Пример:**

```text
Использование памяти: 100 МиБ → 150 МиБ → 90 МиБ
```

Gauge подходит для занятой памяти, длины очереди и количества активных соединений.

---

## Гистограмма — Histogram

**Определение:**

Histogram — тип метрики для измерения распределения значений, например времени ответа.

Классическая гистограмма Prometheus хранит количество наблюдений по порогам — buckets, а также общее количество и сумму значений.

**Пример:**

```text
Время ответа ≤ 0,1 с: 80 запросов
Время ответа ≤ 0,5 с: 95 запросов
Время ответа ≤ 1,0 с: 100 запросов
```

Buckets накопительные: запрос длительностью 0,05 с попадёт во все перечисленные пороги.

Источник по типам метрик: [Metric types](https://prometheus.io/docs/concepts/metric_types/).

---

## Spring Boot Actuator

**Определение:**

Spring Boot Actuator — модуль Spring Boot, который предоставляет средства наблюдения за приложением: состояние здоровья, метрики и другую эксплуатационную информацию.

**Пример:**

```properties
management.endpoints.web.exposure.include=health,prometheus
```

Настройка открывает соответствующие endpoints через HTTP при наличии необходимых компонентов.

---

## Endpoint метрик

**Определение:**

Endpoint метрик — HTTP-адрес, по которому приложение предоставляет измерения системе мониторинга.

В Spring Boot endpoint `/actuator/prometheus` выдаёт метрики в формате, который понимает Prometheus.

**Пример:**

```http
GET http://localhost:8080/actuator/prometheus
```

Для его работы нужны Actuator, реестр Prometheus и разрешение на доступ через HTTP.

Источник: [endpoints Spring Boot Actuator](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html).

---

## Проверка здоровья — Health Check

**Определение:**

Health check — проверка состояния приложения и выбранных зависимостей, например базы данных.

Она отвечает на вопрос «работает ли проверяемая часть системы?», но не заменяет анализ производительности.

**Пример:**

```http
GET /actuator/health
```

Возможный ответ:

```json
{
  "status": "UP"
}
```

Приложение может иметь статус `UP` и при этом медленно отвечать пользователям.

Источник: [health endpoint](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.health).

---

## Micrometer

**Определение:**

Micrometer — библиотека для измерения работы JVM-приложений и интеграции с разными системами мониторинга.

Она предоставляет общий API: разработчик использует `Counter`, `Timer` и другие инструменты, а конкретный реестр подготавливает данные для выбранной системы.

**Пример:**

```gradle
runtimeOnly 'io.micrometer:micrometer-registry-prometheus'
```

Зависимость добавляет поддержку экспорта метрик в Prometheus.

Источник: [метрики Spring Boot](https://docs.spring.io/spring-boot/reference/actuator/metrics.html).

---

## Реестр измерителей — MeterRegistry

**Определение:**

`MeterRegistry` — центральный объект Micrometer, через который регистрируют и получают измерители.

Обычная переменная Java не становится метрикой автоматически: измеритель нужно зарегистрировать.

**Пример:**

```java
public class OrderService {
    private final Counter createdOrders;

    public OrderService(MeterRegistry registry) {
        this.createdOrders = registry.counter("orders.created");
    }

    public void recordCreatedOrder() {
        createdOrders.increment();
    }
}
```

Пример показывает только регистрацию и увеличение счётчика; импорты опущены.

---

## Таймер — Timer

**Определение:**

`Timer` — измеритель Micrometer, который учитывает количество завершённых операций и суммарную длительность их выполнения.

Он позволяет рассчитывать среднее время операции. Публикация гистограммы настраивается отдельно.

**Пример:**

```java
Timer timer = registry.timer("orders.processing");

timer.record(() -> processOrder());
```

`Timer` уже считает выполненные операции, поэтому отдельный `Counter` для тех же событий часто не нужен.

Источник: [измерители Micrometer](https://docs.micrometer.io/micrometer/reference/concepts/meters.html).

---

## Кастомная метрика — Custom Metric

**Определение:**

Кастомная метрика — показатель, который разработчик добавляет для конкретной логики приложения.

Такие метрики показывают бизнес-события, которые стандартный мониторинг JVM не знает.

**Пример:**

```java
Counter declinedPayments = registry.counter("payments.declined");
declinedPayments.increment();
```

Метрика отражает отклонённые платежи.

---

## PromQL

**Определение:**

PromQL — язык запросов Prometheus для выбора, фильтрации, преобразования и объединения временных рядов.

Он используется в Prometheus, панелях Grafana и правилах алертов.

**Пример:**

```promql
sum by (status) (
  http_server_requests_seconds_count{job="spring"}
)
```

Запрос суммирует значения счётчиков отдельно для каждого кода ответа.

Источник: [основы PromQL](https://prometheus.io/docs/prometheus/latest/querying/basics/).

---

## Окно времени — Range Window

**Определение:**

Окно времени — интервал истории метрики относительно момента вычисления запроса.

Окно `[1m]` выбирает данные за последнюю минуту. Оно сдвигается при каждом следующем вычислении.

**Пример:**

```promql
http_server_requests_seconds_count{status="500"}[1m]
```

Это данные за последнюю минуту, а не обязательно за календарную минуту, например с 14:00 до 14:01.

---

## Прирост счётчика — increase()

**Определение:**

`increase()` — функция PromQL, оценивающая, насколько вырос счётчик за указанное окно времени.

Она учитывает сбросы счётчика и экстраполирует результат на всё окно, поэтому значение может быть дробным.

**Пример:**

```promql
sum(
  increase(
    http_server_requests_seconds_count{
      job="spring",
      status="500"
    }[1m]
  )
)
```

Запрос оценивает количество ответов HTTP 500 за последнюю минуту.

---

## Скорость изменения счётчика — rate()

**Определение:**

`rate()` — функция PromQL, которая рассчитывает среднюю скорость увеличения счётчика в секунду за заданное окно.

**Пример:**

```promql
sum(
  rate(http_server_requests_seconds_count{job="spring"}[5m])
)
```

Результат `2` означает в среднем два запроса в секунду за последние пять минут.

Источник по функциям: [Query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/).

---

## Метрика доступности — up

**Определение:**

`up` — метрика, которую Prometheus создаёт для цели сбора:

- `1` — последний сбор метрик завершился успешно;
- `0` — последний сбор завершился ошибкой.

Она показывает успешность сбора, а не исправность всех функций приложения.

**Пример:**

```promql
up{job="spring"}
```

Приложение может возвращать HTTP 500 пользователям, но иметь `up = 1`, если endpoint метрик доступен.

Источник: [автоматически создаваемые метрики](https://prometheus.io/docs/concepts/jobs_instances/).

## Grafana

**Определение:**

Grafana — платформа для визуализации и анализа данных из разных источников.

В нашем проекте она запрашивает метрики из Prometheus и отображает их на графиках.

**Пример:**

```text
Prometheus хранит историю использования памяти.
Grafana показывает эту историю на графике.
```

## Источник данных — Data Source

**Определение:**

Data source в Grafana — настроенное подключение к системе, из которой Grafana получает данные.

**Пример:**

```text
Тип: Prometheus
URL: http://prometheus:9090
```

Если Grafana работает в контейнере, адрес должен быть доступен из этого контейнера. `localhost` внутри него указывает на сам контейнер Grafana.

Источник: [источники данных Grafana](https://grafana.com/docs/grafana/latest/datasources/).

## Дашборд и панель — Dashboard and Panel

**Определение:**

Dashboard — экран, объединяющий связанные показатели системы.

Panel — отдельный элемент дашборда: график, таблица или числовой показатель.

**Пример:**

Дашборд «Java-приложение» содержит панели:

- использование heap-памяти;
- число ответов HTTP 500;
- среднее время ответа.

Источник: [обзор дашбордов Grafana](https://grafana.com/docs/grafana/latest/fundamentals/dashboards-overview/).

## Автоматическая настройка — Provisioning

**Определение:**

Provisioning в Grafana — создание и настройка ресурсов через конфигурационные файлы.

В продакшене это помогает воспроизводить окружение и хранить настройки в Git.

**Пример:**

```text
datasource.yml    — настройка подключения к Prometheus
dashboard.yml     — настройка загрузки дашбордов
my-dashboard.json — описание конкретного дашборда
```

Наличие файлов само по себе недостаточно: их нужно подключить к соответствующим каталогам Grafana.

Источник: [Provision Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/).

## Правило алерта — Alerting Rule

**Определение:**

Правило алерта — условие, по которому система мониторинга определяет наличие проблемы.

В Prometheus правило содержит PromQL-выражение и может включать метки и описание.

**Пример:**

```yaml
- alert: TooManyHttp500
  expr: |
    sum(increase(http_server_requests_seconds_count{
      job="spring",
      status="500"
    }[1m])) > 10
  annotations:
    summary: "Больше 10 ответов HTTP 500 за минуту"
```

Здесь используется оценка прироста счётчиков за скользящее окно.

---

## Порог срабатывания — Threshold

**Определение:**

Порог — значение, при превышении или достижении которого выполняется условие алерта.

Оператор сравнения определяет, включается ли само граничное значение.

**Пример:**

```promql
errors > 10
```

Условие истинно при значении больше 10.

```promql
errors >= 10
```

Условие истинно уже при значении 10.

---

## Интервал проверки — Evaluation Interval

**Определение:**

Evaluation interval — периодичность вычисления правил Prometheus.

Он задаётся отдельно от интервала сбора метрик.

**Пример:**

```yaml
global:
  scrape_interval: 5s
  evaluation_interval: 10s
```

Метрики собираются каждые 5 секунд, а правила проверяются каждые 10 секунд.

Источник: [конфигурация Prometheus](https://prometheus.io/docs/prometheus/latest/configuration/configuration/).

---

## Выдержка условия — for

**Определение:**

`for` — параметр правила Prometheus, который требует, чтобы условие сохранялось на каждой проверке в течение указанного времени до срабатывания алерта.

Он помогает не реагировать на кратковременные скачки.

**Пример:**

```yaml
- alert: ApplicationUnavailable
  expr: up{job="spring"} == 0
  for: 30s
```

Алерт сработает, если сбор метрик остаётся неуспешным на проверках в течение 30 секунд.

---

## Состояния алерта — Inactive, Pending, Firing

**Определение:**

В интерфейсе Prometheus различают состояния:

- **Inactive** — условие не выполняется.
- **Pending** — условие выполняется, но время `for` ещё не прошло.
- **Firing** — алерт сработал.

**Пример:**

Для правила с `for: 30s`:

```text
Условие стало истинным → Pending
Остаётся истинным 30 секунд → Firing
Условие стало ложным → Inactive
```

Если `for` не задан, срабатывание возможно при первой проверке, на которой условие выполнено.

Источник по правилам и состояниям: [Alerting rules](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/).

---

## Alertmanager

**Определение:**

Alertmanager — компонент, который принимает алерты от Prometheus, группирует их и управляет отправкой уведомлений.

Он помогает уменьшать количество повторяющихся сообщений и направлять их нужным получателям.

**Пример:**

```text
Prometheus обнаружил проблему
        ↓
Alertmanager обработал алерт
        ↓
Команда получила уведомление
```

Статус `Firing` в Prometheus сам по себе не означает, что сообщение отправлено в почту или Telegram.

Источник: [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/).

---

## Grafana Alerting

**Определение:**

Grafana Alerting — система управления алертами Grafana.

Правила, управляемые Grafana, вычисляются средствами Grafana. Правила из `alerts.yml` нашего проекта вычисляет Prometheus.

**Пример:**

```text
alerts.yml → Prometheus проверяет условие.

Правило, созданное как Grafana-managed →
Grafana проверяет условие.
```

Это два способа организовать алертинг. Создание графика само по себе не создаёт правило алерта.
