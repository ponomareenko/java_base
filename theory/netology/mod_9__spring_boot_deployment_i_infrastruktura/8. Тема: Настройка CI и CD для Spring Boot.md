# Тема 8: Настройка CI/CD для Spring Boot

> Основа: презентация курса «Настройка CI/CD для Spring Boot» и практическая инструкция «Как настроить CI/CD для Spring Boot». Термины, ранее раскрытые в теме 2 (Docker, Dockerfile, Docker Registry, контейнеризация, развёртывание и т. д.), здесь не повторяются. Понятия, добавленные для полноты, отмечены как **дополнение**.

## CI/CD (Continuous Integration / Continuous Delivery / Continuous Deployment)

**Определение:**

CI/CD — набор практик и инструментов для автоматизации проверки, сборки и доставки изменений программного обеспечения.

- **CI** — регулярное объединение изменений с автоматической проверкой.
- **CD** — автоматизация подготовки и доставки новой версии приложения; может означать *Continuous Delivery* или *Continuous Deployment*.

**Пример:** после `git push` система запускает тесты, собирает Spring Boot-приложение и, если проверки прошли, подготавливает новую версию к выпуску.

---

## Непрерывная интеграция (Continuous Integration, CI)

**Определение:**

Непрерывная интеграция — практика частого внесения изменений в общую кодовую базу с автоматической сборкой и тестированием, чтобы как можно раньше находить ошибки.

**Важно:** успешная сборка не гарантирует отсутствие всех ошибок — она подтверждает прохождение настроенных проверок.

**Пример:** при отправке коммита в GitHub автоматически выполняется команда:

```bash
./mvnw verify
```

---

## Непрерывная доставка (Continuous Delivery) — дополнение

**Определение:**

Непрерывная доставка — практика, при которой изменения автоматически проверяются и подготавливаются к выпуску, но перевод в production может требовать ручного подтверждения.

**Пример:** CI собрал и проверил JAR-файл; ответственный сотрудник нажимает кнопку запуска production-деплоя.

---

## Непрерывное развёртывание (Continuous Deployment)

**Определение:**

Непрерывное развёртывание — практика, при которой изменения, прошедшие все предусмотренные проверки, автоматически попадают в production без обязательного ручного подтверждения.

**Разница:** при *Continuous Delivery* выпуск может подтверждаться человеком, при *Continuous Deployment* он автоматизирован полностью.

---

## CI/CD-пайплайн (Pipeline)

**Определение:**

Пайплайн — автоматизированный процесс, состоящий из этапов проверки, сборки, упаковки и доставки приложения.

**Типичная последовательность для Spring Boot:**

```text
Git push → Build → Test → Package → Publish → Deploy
```

Если обязательная проверка завершается с ошибкой, зависимые этапы не должны запускаться.

---

## Сборка (Build)

**Определение:**

Сборка — процесс преобразования исходного кода и ресурсов в результат, пригодный для запуска или дальнейшей упаковки. Обычно включает компиляцию и обработку зависимостей.

**Пример:**

```bash
./mvnw clean package
```

Эта команда Maven очищает предыдущие результаты и выполняет жизненный цикл до фазы `package`, включая тесты по умолчанию.

---

## Автоматизированное тестирование (Automated Testing)

**Определение:**

Автоматизированное тестирование — выполнение проверок программой без ручного повторения каждого тестового сценария.

В CI/CD применяют, в частности:

- **Unit tests** — проверяют отдельные классы и методы в изоляции.
- **Integration tests** — проверяют взаимодействие компонентов, например приложения с базой данных.

**Пример:**

```bash
./mvnw test
```

Обычно запускает тесты, настроенные для фазы `test`; интеграционные тесты могут быть настроены на отдельную фазу `verify`.

---

## Артефакт сборки (Build Artifact)

**Определение:**

Артефакт сборки — файл или набор файлов, созданных процессом сборки и используемых на следующих этапах пайплайна.

**Пример:** исполняемый `app.jar` Spring Boot-приложения. В GitHub Actions артефактом также называют загруженный результат запуска workflow, доступный для скачивания или передачи между задачами.

**Важно:** это не новое определение Docker Image — образ уже разобран в теме 2.

---

## Упаковка (Package)

**Определение:**

Упаковка — подготовка собранного приложения к хранению, публикации или запуску в целевой среде.

**Пример:** Maven создаёт исполняемый JAR, после чего пайплайн может включить его в Docker-образ.

```bash
./mvnw package
docker build -t myapp:1.0 .
```

---

## Публикация (Publish)

**Определение:**

Публикация — размещение готового артефакта или образа в хранилище, откуда его можно получить для последующих операций.

**Пример:** после сборки Docker-образ отправляют в Docker Hub, а затем загружают на сервер. Команды `push` и `pull` разобраны в теме 2.

---

## Окружение (Environment)

**Определение:**

Окружение — набор инфраструктуры, конфигурации и внешних сервисов, в которых запускается приложение.

**Типичные окружения:**

- **Test** — для автоматизированных или ручных проверок.
- **Staging** — максимально приближённое к production окружение для проверки перед выпуском.
- **Production (prod)** — рабочее окружение реальных пользователей (основное определение — в теме 2).

**Важно:** приложение может использовать один и тот же артефакт в разных окружениях, но разные переменные конфигурации.

---

## Откат (Rollback)

**Определение:**

Откат — возврат к предыдущей работоспособной версии приложения после проблемного обновления.

**Пример:** после выпуска `myapp:1.2` обнаружена ошибка. Команда возвращает на сервер версию `myapp:1.1`.

В production возможность быстрого отката планируют **до** обновления, а не после аварии.

---

## GitHub Actions

**Определение:**

GitHub Actions — встроенная в GitHub платформа автоматизации задач, включая CI/CD. Сценарии описываются в YAML-файлах внутри репозитория.

**Пример расположения файла:**

```text
.github/workflows/ci-cd.yml
```

Также в презентации рассматриваются **GitLab CI/CD** (аналогичная система в экосистеме GitLab) и **Jenkins** (расширяемый сервер автоматизации, часто устанавливаемый на собственной инфраструктуре).

---

## Workflow (рабочий процесс)

**Определение:**

Workflow — автоматизированный сценарий GitHub Actions, описанный YAML-файлом. Он определяет события запуска и задачи, которые требуется выполнить.

**Пример:**

```yaml
name: Java CI

on:
  push:
    branches: [main]
```

Этот workflow настроен на запуск при `push` в ветку `main` (для выполнения задач нужно также добавить раздел `jobs`).

---

## Событие запуска (Trigger / Event)

**Определение:**

Триггер — событие или условие, которое запускает выполнение workflow.

**Примеры:** `push`, `pull_request`, запуск по расписанию или вручную через `workflow_dispatch`.

```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
```

---

## Job (задача GitHub Actions)

**Определение:**

Job — набор шагов одного workflow, выполняемых на выделенном runner. Разные jobs могут выполняться параллельно или зависеть друг от друга.

**Пример:**

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Running tests"
```

---

## Step (шаг GitHub Actions)

**Определение:**

Step — отдельное действие внутри job: запуск shell-команды или использование готового GitHub Action.

Шаги одной job выполняются последовательно.

**Пример:**

```yaml
steps:
  - name: Checkout
    uses: actions/checkout@v4
  - name: Run tests
    run: ./mvnw test
```

`uses` подключает готовое действие, `run` запускает команду.

---

## Runner (исполнитель) — дополнение

**Определение:**

Runner — компьютер или виртуальная среда, на которой GitHub Actions выполняет job.

Runner может предоставляться GitHub или управляться командой самостоятельно (*self-hosted runner*).

**Пример:**

```yaml
runs-on: ubuntu-latest
```

---

## Зависимости между задачами (Job Dependencies)

**Определение:**

Зависимости между jobs задают порядок их выполнения: одна задача запускается после успешного завершения другой, если не настроено иное поведение.

В GitHub Actions для этого используют ключ `needs`.

**Пример:**

```yaml
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Tests passed"

  deploy:
    needs: build-and-test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying"
```

---

## YAML (YAML Ain't Markup Language)

**Определение:**

YAML — человекочитаемый формат представления структурированных данных, часто используемый для конфигурационных файлов.

В GitHub Actions структура workflow задаётся ключами, списками и **отступами из пробелов**.

**Пример:**

```yaml
name: Spring Boot CI
jobs:
  test:
    runs-on: ubuntu-latest
```

Неверные отступы могут привести к ошибке разбора файла или неправильной структуре конфигурации.

---

## Секрет (Secret / GitHub Actions Secrets)

**Определение:**

Секрет — конфиденциальное значение (например, токен или приватный SSH-ключ), которое хранится отдельно от исходного кода и передаётся пайплайну при выполнении.

**Пример:**

```yaml
steps:
  - name: Use token
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}
    run: test -n "$API_TOKEN"
```

**Важно:** нельзя записывать пароли, токены и приватные ключи непосредственно в репозиторий. Маскирование логов — дополнительная защита, но не гарантия от любой утечки.

---

## Переменная окружения (Environment Variable)

**Определение:**

Переменная окружения — пара «имя — значение», передаваемая процессу при запуске и используемая для настройки его поведения.

**Пример:**

```yaml
env:
  SPRING_PROFILES_ACTIVE: test
```

**Разница:** переменная окружения — способ передачи настройки; secret — способ защищённого хранения чувствительного значения, которое тоже можно передать через переменную окружения.

---

## SSH (Secure Shell)

**Определение:**

SSH — сетевой протокол защищённого удалённого подключения и выполнения команд на другом компьютере.

В рассматриваемом пайплайне SSH применяется для подключения к виртуальной машине и запуска команд обновления приложения.

**Пример:**

```bash
ssh deploy@192.0.2.10
```

Адрес указан условно. Для CI предпочтительна аутентификация ключом и отдельный пользователь с минимально необходимыми правами.

---

## Кэширование зависимостей (Dependency Caching)

**Определение:**

Кэширование зависимостей — сохранение ранее скачанных библиотек и других повторно используемых данных между запусками пайплайна.

**Зачем нужно:** уменьшает время сборки, поскольку Maven или Gradle не скачивают одни и те же зависимости заново при каждом запуске.

**Пример:** GitHub Actions может кэшировать локальный репозиторий зависимостей Maven (`~/.m2/repository`).

---

## Отладка пайплайна (Pipeline Debugging)

**Определение:**

Отладка пайплайна — поиск причин ошибок сборки, тестирования, публикации или деплоя по журналам выполнения и диагностическим командам.

**Пример:** открыть GitHub → **Actions** → нужный workflow → неуспешный запуск → конкретный шаг и его логи.

В shell-скриптах можно использовать:

```bash
set -x
./mvnw test
```

`set -x` показывает выполняемые команды. **Осторожно:** в отладочные логи могут попасть секреты и чувствительные данные.

---

## Timeout (тайм-аут)

**Определение:**

Тайм-аут — максимальное время ожидания операции или выполнения задачи, после которого система прекращает ожидание или прерывает процесс.

**Пример:**

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - run: ./mvnw test
```

---

## Принцип минимальных привилегий (Least Privilege)

**Определение:**

Принцип минимальных привилегий — правило безопасности: пользователю, токену или сервису предоставляются только те права, которые необходимы для выполнения его задач.

**Пример:** учётной записи для деплоя разрешён доступ к конкретному серверу и нужным операциям, но не выданы неограниченные права администратора.

---

## Статический анализ кода (Static Code Analysis)

**Определение:**

Статический анализ — проверка исходного кода без его обычного выполнения с целью выявления потенциальных ошибок, нарушений правил качества или небезопасных конструкций.

**Пример:** отдельная проверка в CI с помощью статического анализатора Java-кода. Это дополняет, но не заменяет тестирование.

---

## Сканирование уязвимостей (Vulnerability Scanning)

**Определение:**

Сканирование уязвимостей — автоматическая проверка зависимостей, образов или других компонентов на известные проблемы безопасности.

**Пример:** CI анализирует зависимости Maven и сообщает о библиотеке с известной уязвимостью.

**Дополнение:** Dependabot может отслеживать и предлагать обновления зависимостей; он упомянут в презентации как инструмент для поддержания их актуальности.

---

## Maven Lifecycle (жизненный цикл Maven) — дополнение из инструкции

**Определение:**

Жизненный цикл Maven — упорядоченный набор фаз, через которые проходит проект при сборке. Вызов более поздней фазы запускает необходимые предыдущие фазы того же жизненного цикла.

**Пример:**

```bash
mvn clean test       # очистить target и выполнить тесты
mvn clean package    # очистить, скомпилировать, протестировать и упаковать JAR
mvn spring-boot:run  # запустить приложение через плагин Spring Boot
```

**Важно:** `clean` относится к отдельному жизненному циклу, `package` — фаза стандартного жизненного цикла, а `spring-boot:run` — цель плагина, а не фаза.

---

## Maven Wrapper (`mvnw`) — дополнение

**Определение:**

Maven Wrapper — файлы проекта и скрипт запуска Maven с указанной проектом версией, даже если Maven не установлен глобально.

**Пример:**

```bash
./mvnw clean verify    # macOS / Linux
```

В CI предпочтительно использовать Wrapper, если он присутствует в репозитории: это снижает риск расхождения версий Maven между компьютером разработчика и сервером сборки.

---

## SNAPSHOT-версия — дополнение

**Определение:**

`SNAPSHOT` — суффикс версии Maven, обозначающий промежуточную, потенциально изменяемую сборку, ещё не выпущенную как стабильный релиз.

**Пример:** `calculator-0.0.1-SNAPSHOT.jar` — имя JAR из инструкции курса.

---

## Пара SSH-ключей (Public Key / Private Key) — дополнение

**Определение:**

Пара SSH-ключей — связанные криптографические ключи для аутентификации: **закрытый** (private) хранится у клиента и не раскрывается, **открытый** (public) разрешается разместить на сервере.

**Пример:**

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_deploy
ssh -i ~/.ssh/id_ed25519_deploy deploy@192.168.1.235
```

В инструкции показан RSA-ключ на 4096 бит; Ed25519 — современная альтернатива для типичных SSH-сценариев.

---

## `authorized_keys` и `known_hosts` — дополнение

**Определение:**

- `~/.ssh/authorized_keys` на сервере содержит открытые ключи, которым разрешён вход в учётную запись.
- `~/.ssh/known_hosts` на клиенте хранит сведения о ключах серверов для проверки их подлинности при подключении.

**Почему важно:** эти файлы решают **разные** задачи. `authorized_keys` проверяет клиента, а `known_hosts` помогает клиенту проверить сервер.

---

## SSH-аутентификация по ключу (Key-based Authentication) — дополнение

**Определение:**

Способ подтверждения личности клиента при SSH-подключении, при котором клиент доказывает владение закрытым ключом, не передавая его серверу.

**Пример:** GitHub Actions подключается к тестовой ВМ для выполнения команд деплоя; закрытый ключ передаётся из GitHub Secrets, а соответствующий открытый ключ заранее добавлен на ВМ в `authorized_keys`.

---

## Сетевой мост (Bridged Networking) — дополнение из инструкции

**Определение:**

Режим сети виртуальной машины, при котором ВМ подключается к физической сети через адаптер хоста и обычно получает собственный IP-адрес в этой сети.

**Пример:** ноутбук и виртуальная машина Ubuntu находятся в одной домашней сети; к ВМ можно обращаться по её локальному IP при корректных настройках сети и брандмауэра.

---

## Проброс портов (Port Forwarding) — дополнение из инструкции

**Определение:**

Правило сетевого устройства или платформы, которое перенаправляет входящее соединение с одного адреса и порта на другой адрес и порт.

**Пример из инструкции:**

```text
Публичный_IP:50000 → 192.168.1.235:22    (SSH)
Публичный_IP:51000 → 192.168.1.235:8080  (Spring Boot)
```

**Важно:** обращение извне должно идти на `:51000`, а не на `:8080`, если правило настроено именно так. Открывать SSH наружу без ограничений и усиленной защиты не рекомендуется.

---

## NAT (Network Address Translation) — дополнение

**Определение:**

Преобразование сетевых адресов и, при необходимости, портов при прохождении трафика через маршрутизатор. Часто используется, когда несколько устройств локальной сети выходят в интернет через один публичный IP.

**Пример:** домашний роутер перенаправляет входящий TCP-порт `51000` на порт `8080` виртуальной машины.

---

## NAT Hairpin (NAT Loopback) — дополнение из инструкции

**Определение:**

Возможность маршрутизатора направлять запрос от устройства внутри локальной сети к другому внутреннему устройству через внешний IP-адрес этого же маршрутизатора.

**Пример:** из домашней сети пользователь обращается к `http://публичный-IP:51000`, а роутер перенаправляет запрос на ВМ `192.168.1.235:8080`.

Если NAT loopback не поддерживается или отключён, такой запрос может не сработать, хотя доступ извне работает.

---

## GitHub Actions: `uses`, `run`, `with` — дополнение из инструкции

**Определение:**

- `uses` — подключить готовое GitHub Action.
- `run` — выполнить команду в оболочке runner.
- `with` — передать входные параметры готовому action.

**Пример:**

```yaml
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-java@v4
    with:
      distribution: temurin
      java-version: '17'
  - run: ./mvnw test
```

**Важно:** использовать актуальные поддерживаемые версии actions и, для критичных сборок, закреплять их по полному SHA коммита.

## Output-переменные шага (Step Outputs) — дополнение из инструкции

**Определение:**

Именованные выходные значения шага GitHub Actions, которые можно использовать далее в том же job либо объявить как выходные значения job для передачи зависимым задачам.

**Пример:**

```yaml
- name: Save JAR path
  id: jar
  run: echo "path=target/app.jar" >> "$GITHUB_OUTPUT"

- name: Show path
  run: echo "${{ steps.jar.outputs.path }}"
```

**Важно:** в инструкции применяется `::set-output`, но эта команда устарела. Для современных workflow используется файл `$GITHUB_OUTPUT`.

---

## Передача артефактов между jobs (Upload / Download Artifact) — дополнение

**Определение:**

Сохранение файла, созданного одним job, в хранилище артефактов GitHub Actions с последующей загрузкой в другом job. Это необходимо, поскольку jobs обычно выполняются в отдельных рабочих окружениях.

**Пример:**

```yaml
# В job сборки:
- uses: actions/upload-artifact@v4
  with:
    name: app-jar
    path: target/app.jar

# В следующем job:
- uses: actions/download-artifact@v4
  with:
    name: app-jar
    path: target
```

**Важно:** `needs` задаёт зависимость между jobs, но **сам по себе не переносит файлы**.

---

## Фоновый режим контейнера (Detached Mode) — дополнение

**Определение:**

Режим запуска Docker-контейнера, при котором команда возвращает управление терминалу, а контейнер продолжает работать в фоне.

**Пример из инструкции:**

```bash
docker run -d --name calculator -p 8080:8080 user/calculator:latest
```

Здесь `-d` — фоновый режим, `--name` задаёт имя, `-p` публикует порт контейнера на хосте.
