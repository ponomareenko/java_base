# 1. Тема: Spring Boot — назначение и внутреннее устройство

## Spring Boot

**Определение:**

Spring Boot — это инструмент экосистемы Spring, который упрощает создание и запуск Java-приложений за счёт автоконфигурации, готовых наборов зависимостей и встроенного сервера.

В презентации Spring Boot описывается как средство быстрого создания `production-ready` приложений с высоким уровнем абстракции. 

Spring Boot не заменяет Spring Framework, а строится поверх него и убирает большую часть ручной настройки.

**Пример:**

```java
@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

После запуска Spring Boot:

1. создаёт Spring-контекст;
2. выполняет поиск компонентов;
3. применяет автоконфигурацию;
4. при необходимости запускает встроенный web-сервер.

---

## Stand-alone приложение

**Определение:**

Stand-alone приложение — приложение, которое можно запустить самостоятельно, без предварительной установки отдельного application server.

Spring Boot позволяет собрать приложение в обычный `.jar` и запустить:

```bash
java -jar application.jar
```

Это одна из ключевых возможностей Spring Boot, отмеченных в презентации. 

---

## Embedded container

**Определение:**

Embedded container — сервер, встроенный непосредственно в приложение.

Для web-приложения Spring Boot может автоматически запускать, например, встроенный Tomcat.

То есть вместо схемы:

```text
Tomcat
  ↓
WAR-приложение
```

можно получить:

```text
JAR
 ├── приложение
 └── встроенный Tomcat
```

И запустить всё одной командой:

```bash
java -jar app.jar
```

Именно благодаря этому Spring Boot-приложение обычно является stand-alone приложением. Встроенные контейнеры указаны среди основных особенностей Spring Boot. 

---

## Starter dependency

**Определение:**

Starter dependency — готовый набор зависимостей для определённой функциональности приложения.

Вместо того чтобы вручную подключать множество библиотек, разработчик подключает один starter.

Например:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>
```

`spring-boot-starter-web` подтягивает зависимости, необходимые для создания web-приложения.

Starter dependencies указаны в презентации как одна из основных особенностей Spring Boot. 

**Практический смысл:**

```text
starter
   ↓
набор совместимых библиотек
   ↓
меньше ручной настройки зависимостей
```

---

## Автоконфигурация

**Определение:**

Автоконфигурация — механизм Spring Boot, который автоматически создаёт и настраивает бины в `ApplicationContext` на основании того, какие зависимости присутствуют в `classpath` приложения. 

Например, если Spring Boot обнаруживает зависимости для web-приложения, он может автоматически настроить необходимую инфраструктуру.

Упрощённо:

```text
Spring Boot смотрит:

Что есть в classpath?
        ↓
Какие бины уже существуют?
        ↓
Какие настройки указаны?
        ↓
Создаёт необходимые бины
```

Это одна из центральных идей Spring Boot.

---

## `@EnableAutoConfiguration`

**Определение:**

`@EnableAutoConfiguration` — аннотация, включающая механизм автоконфигурации Spring Boot. 

Обычно напрямую её писать не нужно, потому что она уже входит в:

```java
@SpringBootApplication
```

---

## `@SpringBootApplication`

**Определение:**

`@SpringBootApplication` — основная аннотация Spring Boot-приложения, объединяющая несколько механизмов конфигурации Spring.

В презентации отдельно выделены три её задачи:

* конфигурирование;
* поиск компонентов;
* включение автоконфигурации. 

Пример:

```java
@SpringBootApplication
public class Application {

    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}
```

Концептуально её можно воспринимать примерно как комбинацию:

```java
@Configuration
@EnableAutoConfiguration
@ComponentScan
```

Поэтому пакет, в котором расположен основной класс, имеет значение: от него Spring начинает поиск компонентов. Презентация также показывает, что базовый пакет поиска можно изменить. 

### Почему основной класс обычно помещают в корневой пакет

Например:

```text
com.example.shop
│
├── Application.java
├── controller
├── service
└── repository
```

Так Spring автоматически увидит все дочерние пакеты.

Если сделать:

```text
com.example.application.Application
com.example.controller
com.example.service
```

поиск компонентов может не охватить соседние пакеты без дополнительной настройки.

## Spring Boot Actuator

**Определение:**

Spring Boot Actuator — модуль Spring Boot для мониторинга и получения технической информации о работающем приложении.

В презентации среди возможностей Actuator приведены:

```text
health
metrics
configprops
...
```



Actuator особенно полезен в production-среде для мониторинга состояния приложения.

---

## Actuator Endpoint

**Определение:**

Endpoint — точка Actuator, через которую можно получить определённую служебную информацию об приложении или выполнить управляющее действие.

Например:

```text
/actuator/health
```

может показывать состояние приложения.

```text
/actuator/metrics
```

предоставляет метрики.

В презентации также упомянут:

```text
configprops
```

для просмотра конфигурационных параметров. 

---

## Health endpoint

**Определение:**

`health` — endpoint Spring Boot Actuator, показывающий состояние приложения. 

Например:

```http
GET /actuator/health
```

Ответ может выглядеть примерно так:

```json
{
  "status": "UP"
}
```

В production такой endpoint часто используется системами мониторинга или оркестраторами.

---

## Metrics

**Определение:**

Metrics — числовые показатели состояния и работы приложения.

Например:

```text
количество HTTP-запросов
использование памяти
время выполнения запросов
загрузка JVM
```

В Spring Boot информацию о метриках можно получать через Actuator. В презентации `metrics` указан как один из monitoring endpoints. 

---

## `@Conditional`

**Определение:**

`@Conditional` — механизм условной регистрации Spring-бинов.

Бин добавляется в контекст только тогда, когда выполняется определённое условие.

В презентации условие связывается с классом, реализующим интерфейс `Condition`. 

Упрощённо:

```text
условие выполнено
       ↓
бин создаётся

условие НЕ выполнено
       ↓
бин не создаётся
```

Этот механизм активно используется внутри автоконфигурации Spring Boot.

---

## `@ConditionalOnBean`

**Определение:**

`@ConditionalOnBean` — регистрирует конфигурацию или бин только в том случае, если определённый бин уже существует в Spring-контексте. 

Пример:

```java
@Bean
@ConditionalOnBean(DataSource.class)
public MyService myService() {
    return new MyService();
}
```

Логика:

```text
DataSource существует?
       ↓
      да
       ↓
создать MyService
```

---

## `@ConditionalOnMissingBean`

**Определение:**

`@ConditionalOnMissingBean` — регистрирует бин только в том случае, если подходящего бина ещё нет в контексте. 

Пример:

```java
@Bean
@ConditionalOnMissingBean
public PaymentService paymentService() {
    return new DefaultPaymentService();
}
```

Это очень важный механизм Spring Boot.

Например, библиотека может предоставить реализацию по умолчанию:

```text
нет пользовательского PaymentService
               ↓
Spring Boot создаёт DefaultPaymentService
```

Но если разработчик написал:

```java
@Bean
public PaymentService paymentService() {
    return new CustomPaymentService();
}
```

автоконфигурация отступает и не создаёт свой бин.

Это позволяет Spring Boot иметь разумные настройки **по умолчанию**, но оставлять разработчику возможность их переопределить.

---

## `@ConditionalOnClass`

**Определение:**

`@ConditionalOnClass` — активирует конфигурацию только в том случае, если определённый класс присутствует в `classpath`. 

Например:

```java
@ConditionalOnClass(DataSource.class)
@Configuration
public class DatabaseConfiguration {
}
```

Если:

```text
DataSource.class присутствует
```

конфигурация может быть активирована.

Именно поэтому автоконфигурация может ориентироваться на подключённые зависимости.

---

## `@ConditionalOnProperty`

**Определение:**

`@ConditionalOnProperty` — позволяет создавать бин или включать конфигурацию в зависимости от значения свойства приложения. 

Например:

```properties
payment.enabled=true
```

```java
@Bean
@ConditionalOnProperty(
        name = "payment.enabled",
        havingValue = "true"
)
public PaymentService paymentService() {
    return new PaymentService();
}
```

Если:

```properties
payment.enabled=false
```

бин создан не будет.

# Конфигурация Spring Boot

## `application.properties`

**Определение:**

`application.properties` — один из стандартных файлов конфигурации Spring Boot.

Например:

```properties
server.port=8081

app.name=MyApplication

payment.enabled=true
```

Spring Boot ищет конфигурационные файлы в нескольких стандартных местах, включая `classpath`, текущую директорию и каталоги `config`. 

---

## `application.yml` / `application.yaml`

**Определение:**

YAML — альтернативный формат конфигурации Spring Boot.

Например, properties:

```properties
server.port=8081
app.name=my-app
```

аналогичен YAML:

```yaml
server:
  port: 8081

app:
  name: my-app
```

---

## Relaxed Binding

**Определение:**

Relaxed Binding — механизм Spring Boot, позволяющий связывать параметры конфигурации с Java-свойствами, даже если их имена записаны в разных соглашениях.

Презентация приводит варианты:

```text
my-property.id
my_property.id
MY_PROPERTY.ID
myProperty.id
```

и рекомендует для конфигурационных файлов `kebab-case`. 

Например:

```properties
mail-service.timeout=5000
```

может быть связан со свойством Java:

```java
private int timeout;
```

в конфигурационном объекте `MailServiceProperties`.

---

## `@Value`

**Определение:**

`@Value` — аннотация Spring, позволяющая внедрять отдельные значения из конфигурации приложения.

В презентации показано, что значение задаётся через placeholder, а после `:` можно указать значение по умолчанию. 

Пример:

```properties
app.name=MyApplication
```

```java
@Value("${app.name}")
private String applicationName;
```

Значение по умолчанию:

```java
@Value("${app.name:DefaultApplication}")
private String applicationName;
```

Если:

```properties
app.name
```

не существует, будет использовано:

```text
DefaultApplication
```

---

## `@ConfigurationProperties`

**Определение:**

`@ConfigurationProperties` — аннотация для привязки группы связанных конфигурационных параметров к Java-объекту.

Например:

```properties
mail.host=smtp.example.com
mail.port=587
mail.timeout=5000
```

Можно объединить их:

```java
@ConfigurationProperties(prefix = "mail")
public class MailProperties {

    private String host;
    private int port;
    private int timeout;

    // getters / setters
}
```

Вместо трёх отдельных:

```java
@Value("${mail.host}")
private String host;

@Value("${mail.port}")
private int port;

@Value("${mail.timeout}")
private int timeout;
```

Поэтому для группы связанных настроек `@ConfigurationProperties` обычно значительно удобнее.

Презентация отдельно отмечает, что `@ConfigurationProperties` поддерживает Relaxed Binding, в отличие от более ограниченного поведения `@Value`. 

---

## Placeholder

**Определение:**

Placeholder — выражение, указывающее на параметр конфигурации.

Например:

```java
@Value("${database.url}")
```

Здесь:

```text
${database.url}
```

— placeholder.

Можно задать значение по умолчанию:

```java
@Value("${server.port:8080}")
```

где:

```text
server.port
```

— название свойства,

а:

```text
8080
```

— значение по умолчанию.

---

## SpEL — Spring Expression Language

**Определение:**

SpEL — язык выражений Spring, позволяющий вычислять выражения внутри конфигурации Spring.

Презентация отмечает важное различие:

```text
@ConfigurationProperties → SpEL не поддерживает
@Value                  → SpEL поддерживает
```



Пример:

```java
@Value("#{10 * 5}")
private int value;
```

Получим:

```text
50
```

# Главное, что нужно вынести из темы

На уровне Junior я бы запомнил цепочку:

```text
Spring Boot
    ↓
@SpringBootApplication
    ↓
Component Scan
+
Auto Configuration
    ↓
@Conditional...
    ↓
создание нужных Bean
    ↓
ApplicationContext
```

И отдельно конфигурацию:

```text
application.properties / application.yml
                ↓
       параметры приложения
          ↓             ↓
       @Value    @ConfigurationProperties
```

А смысл Spring Boot можно сформулировать одной фразой:

> **Spring Boot использует Spring Framework, но берёт на себя большую часть типовой конфигурации приложения.**

И ещё одно важное различие, которое уже стоит знать для собеседования:

```text
Spring Framework
        ↓
даёт основные механизмы:
IoC, DI, Beans, ApplicationContext...

Spring Boot
        ↓
автоматически настраивает эти механизмы
и предоставляет удобные настройки по умолчанию
```
