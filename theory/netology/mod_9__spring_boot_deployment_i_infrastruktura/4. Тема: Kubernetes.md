# 4. Тема: Kubernetes

## Kubernetes

**Определение:**

Kubernetes — программное обеспечение для автоматизации развёртывания, масштабирования и управления контейнеризированными приложениями. Kubernetes

Упрощённо:

```text
Docker → запускает контейнеры

Kubernetes → управляет большим количеством контейнеров
```

Kubernetes особенно нужен, когда приложение состоит из множества контейнеров и нужно автоматически следить за их состоянием, количеством и распределением по серверам.

---

## Kubernetes Cluster

**Определение:**

Kubernetes Cluster — совокупность управляющих компонентов Kubernetes и рабочих серверов, на которых запускаются контейнеризированные приложения.

На архитектурной схеме презентации кластер состоит из управляющей части и нескольких Kubernetes Node. Kubernetes

Упрощённо:

```text
Kubernetes Cluster
│
├── Control Plane
│
└── Worker Nodes
    ├── Node
    ├── Node
    └── Node
```

---

## Control Plane

**Определение:**

Control Plane — управляющая часть Kubernetes-кластера, которая принимает решения о состоянии и размещении приложений.

В презентации эта часть обозначена как `Kubernetes Master Server(s)` и включает:

```text
API Server
Scheduler
Controller Manager
etcd
```

Kubernetes

Упрощённо:

```text
Control Plane
     ↓
решает:
что запустить
где запустить
сколько экземпляров поддерживать
```

---

## Node

**Определение:**

Node — рабочий сервер Kubernetes-кластера, на котором непосредственно запускаются контейнеры приложения.

На схеме презентации каждая Node содержит:

```text
Docker
Kubelet
Kubernetes Proxy
```

Kubernetes

То есть:

```text
Cluster
   ↓
Nodes
   ↓
Pods
   ↓
Containers
```

---

## API Server

**Определение:**

API Server — компонент управляющей части Kubernetes, через который происходит взаимодействие с кластером.

На архитектурной схеме именно управляющая часть получает команды от `kubectl`. Kubernetes

Упрощённо:

```text
kubectl
   ↓
API Server
   ↓
Kubernetes Cluster
```

---

## Scheduler

**Определение:**

Scheduler — компонент Kubernetes, отвечающий за выбор Node, на которой должен быть размещён Pod.

На схеме презентации `Scheduler` входит в управляющую часть Kubernetes. Kubernetes

Упрощённо:

```text
Нужно запустить новый Pod
        ↓
Scheduler
        ↓
выбирает подходящую Node
```

---

## Controller Manager

**Определение:**

Controller Manager — компонент управляющей части Kubernetes, отвечающий за работу контроллеров, которые следят за соответствием фактического состояния кластера требуемому.

В презентации `Controller Manager` показан как один из основных компонентов управляющего сервера. Kubernetes

---

## etcd

**Определение:**

`etcd` — компонент Kubernetes, входящий в управляющую часть кластера и используемый для хранения данных о состоянии кластера.

В презентации `etcd` показан в составе Kubernetes Master Server. Kubernetes

---

## Kubelet

**Определение:**

Kubelet — компонент Kubernetes, работающий на каждой Node.

На архитектурной схеме презентации `Kubelet` расположен на каждом Kubernetes Node рядом с контейнерной средой. Kubernetes

Упрощённо:

```text
Control Plane
      ↓
Kubelet
      ↓
контейнеры на конкретной Node
```

---

## Kubernetes Proxy

**Определение:**

Kubernetes Proxy — компонент, работающий на Kubernetes Node и связанный с сетевым взаимодействием внутри кластера.

В презентации он показан на каждой рабочей Node. Kubernetes

---

## `kubectl`

**Определение:**

`kubectl` — утилита командной строки для управления Kubernetes-кластером.

На архитектурной схеме презентации `kubectl` отправляет manifest в Kubernetes. Kubernetes

Пример:

```bash
kubectl apply -f deployment.yaml
```

Упрощённо:

```text
Developer
   ↓
kubectl
   ↓
Kubernetes
```

---

## Manifest

**Определение:**

Manifest — декларативное описание Kubernetes-ресурса.

Обычно manifest записывается в YAML.

В презентации manifest показан как описание, которое передаётся в Kubernetes через `kubectl`. Kubernetes

Пример:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: my-pod

spec:
  containers:
    - name: app
      image: my-app
```

---

# Основные возможности Kubernetes

## Self-healing

**Определение:**

Self-healing — способность Kubernetes автоматически обнаруживать упавшие контейнеры и перезапускать их. Kubernetes

Например:

```text
Pod работает
    ↓
контейнер упал
    ↓
Kubernetes обнаружил проблему
    ↓
восстановил нужное состояние
```

---

## Load Balancing

**Определение:**

Load Balancing — распределение нагрузки между несколькими экземплярами приложения.

В презентации отмечено, что Kubernetes может балансировать нагрузку между контейнерами. Kubernetes

Упрощённо:

```text
Request
   ↓
Kubernetes
 ↙   ↓   ↘
Pod  Pod  Pod
```

---

## Declarative Configuration

**Определение:**

Declarative Configuration — подход, при котором разработчик описывает желаемое состояние системы, а Kubernetes самостоятельно старается его поддерживать.

В презентации декларативный подход указан как одна из ключевых особенностей Kubernetes. Kubernetes

Например:

```yaml
replicas: 3
```

Это означает:

```text
"Я хочу, чтобы работало 3 экземпляра"
```

а не:

```text
"Создай Pod №1,
потом Pod №2,
потом Pod №3"
```

---

# Pod

## Pod

**Определение:**

Pod — наименьшая единица, которую можно создать в Kubernetes.

Pod содержит один или несколько контейнеров, которые размещаются рядом и используют общие ресурсы. Kubernetes

Упрощённо:

```text
Pod
│
├── Container
└── Container
```

Контейнеры внутри одного Pod могут совместно использовать:

```text
localhost
Volume
```

Это показано на схеме страницы 7 презентации. Kubernetes

---

## Pod Manifest

**Определение:**

Pod Manifest — YAML-описание Pod.

В презентации приведён пример примерно такой структуры: Kubernetes

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: my-pod

spec:
  containers:
    - name: kube-boot
      image: docker-boot
```

Главные части:

```text
apiVersion → версия API

kind       → тип ресурса

metadata   → информация о ресурсе

spec       → описание желаемого состояния
```

---

## `metadata`

**Определение:**

`metadata` — секция Kubernetes manifest, содержащая информацию о ресурсе.

Например:

```yaml
metadata:
  name: my-pod
  labels:
    app: my-app
```

В примере Pod из презентации в `metadata` находятся имя Pod и labels. Kubernetes

---

## `spec`

**Определение:**

`spec` — секция Kubernetes manifest, которая описывает желаемую конфигурацию ресурса.

Для Pod внутри `spec` может быть указан список контейнеров:

```yaml
spec:
  containers:
    - name: app
      image: my-app
```

---

## Label

**Определение:**

Label — метка `key:value`, которая прикрепляется к Kubernetes-ресурсам и позволяет объединять и выбирать их.

Пример из материала:

```yaml
labels:
  app: my-app
```

Labels особенно важны при работе с `Service`, потому что через них Service выбирает подходящие Pod. Это показано на схемах страниц 19–20. Kubernetes

---

# ReplicaSet

## ReplicaSet

**Определение:**

ReplicaSet — Kubernetes-ресурс, поддерживающий необходимое количество одинаковых Pod.

На страницах 10–12 презентации показано:

```text
есть 3 Pod
     ↓
один Pod выходит из строя
     ↓
создаётся новый Pod
     ↓
снова работает 3 Pod
```

Kubernetes

Главная идея:

```text
Desired State = 3 Pods

Actual State = 2 Pods

ReplicaSet
    ↓

создать ещё один Pod
```

---

## Replica

**Определение:**

Replica — отдельный экземпляр одного и того же приложения.

Например:

```yaml
replicas: 3
```

означает, что Kubernetes должен поддерживать три экземпляра Pod.

---

# Deployment

## Deployment

**Определение:**

Deployment — Kubernetes-ресурс для декларативного управления Pod и их версиями.

В manifest Deployment из презентации присутствуют:

```yaml
kind: Deployment

spec:
  replicas: 1
  selector:
  template:
```

Kubernetes

Deployment управляет Pod не напрямую, а через ReplicaSet.

Удобная цепочка:

```text
Deployment
    ↓
ReplicaSet
    ↓
Pods
    ↓
Containers
```

---

## Rolling Update

**Определение:**

Rolling Update — постепенное обновление приложения, при котором старые экземпляры заменяются новыми не одновременно, а последовательно.

Это показано на страницах 13–17 презентации: версия `v32` постепенно заменяется версией `v33`. Kubernetes

Схема:

```text
v32 v32 v32

      ↓

v33 v32 v32

      ↓

v33 v33 v32

      ↓

v33 v33 v33
```

Преимущество — приложение может продолжать работать во время обновления.

---

# Service

## Service

**Определение:**

Service — Kubernetes-ресурс, который предоставляет стабильную точку доступа к группе Pod.

В презентации показан manifest Service с:

```yaml
kind: Service

spec:
  ports:
  selector:
  type:
```

Kubernetes

Service нужен потому, что Pod могут создаваться, удаляться и заменяться.

Вместо обращения напрямую к конкретному Pod:

```text
Client
   ↓
Pod
```

используется:

```text
Client
   ↓
Service
   ↓
Pod
Pod
Pod
```

---

## Selector

**Определение:**

Selector — правило, по которому Kubernetes выбирает ресурсы с определёнными labels.

Например:

```yaml
selector:
  app: my-app
```

означает:

```text
найти Pod,
у которых:

app = my-app
```

На страницах 19–20 презентации показано, как изменение selector меняет набор Pod, на которые направляет трафик Service. Kubernetes

---

## ClusterIP

**Определение:**

`ClusterIP` — тип Kubernetes Service.

Он указан в одном из примеров manifest Service в презентации. Kubernetes

Такой Service используется как внутренняя точка доступа внутри Kubernetes-кластера.

---

## NodePort

**Определение:**

`NodePort` — тип Kubernetes Service, указанный во втором примере manifest в презентации. Kubernetes

Он позволяет обращаться к Service через порт Node.

---

# Что обязательно запомнить из темы

Самая важная иерархия:

```text
Kubernetes Cluster
        ↓
       Node
        ↓
Deployment
        ↓
ReplicaSet
        ↓
       Pod
        ↓
   Container
```

И отдельно:

```text
Service
   ↓
по Labels / Selector
   ↓
Pods
```

Управление происходит примерно так:

```text
Developer
    ↓
Manifest YAML
    ↓
kubectl
    ↓
API Server
    ↓
Kubernetes
```

Если совсем коротко:

```text
Pod
→ запускает контейнеры

ReplicaSet
→ следит за количеством Pod

Deployment
→ управляет ReplicaSet и обновлениями

Service
→ даёт стабильный доступ к Pod
```
