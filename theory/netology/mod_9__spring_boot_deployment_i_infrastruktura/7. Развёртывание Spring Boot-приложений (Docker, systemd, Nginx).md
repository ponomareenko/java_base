# Тема : Развёртывание Spring Boot-приложений (Docker, systemd, Nginx)

> Основа: презентация «Разворачивание Spring Boot приложений (nginx, systemd, firewall, journalctl)», Виктор Лоскутов. Дополнительные пояснения и уточнения выделены там, где материал презентации упрощён.

## Развёртывание приложения (Deployment)

**Определение:**

Развёртывание — процесс доставки и запуска приложения в целевой среде (например, на Linux-сервере), чтобы оно было доступно пользователям и им можно было управлять.

Недостаточно один раз запустить `java -jar`: в рабочей среде нужны настройка доступа, управление перезапусками, мониторинг состояния и диагностика ошибок.

**Пример:**

```bash
java -jar app.jar
```

Эта команда запускает приложение, но сама по себе не настраивает его как постоянно работающий сервис.

---

## Рабочая среда (Production Environment)

**Определение:**

Production — окружение, в котором приложение обслуживает реальных пользователей. Оно может отличаться от локальной разработки версиями ПО, конфигурацией, доступом к сети и требованиями к надёжности.

**Важно:** обычно различают `dev` (разработка), `test`/`stage` (тестирование) и `prod` (рабочая среда).

---

## Процесс (Process)

**Определение:**

Процесс — выполняющийся экземпляр программы, которому операционная система выделяет ресурсы и присваивает идентификатор (PID).

Spring Boot-приложение, запущенное через `java -jar`, работает как процесс JVM. Один сервер может одновременно запускать несколько процессов приложений.

**Пример:**

```bash
ps aux | grep java
```

Команда помогает найти Java-процессы в Linux/macOS.

---

## Контейнеризация (Containerization)

**Определение:**

Контейнеризация — способ упаковать приложение с необходимыми зависимостями и запустить его в изолированной среде.

Контейнеры используют ядро хостовой ОС (в Linux); они не запускают отдельную полноценную гостевую ОС, как виртуальные машины.

**Зачем:** снизить различия между окружением разработчика, тестовым и production-сервером.

---

## Docker

**Определение:**

Docker — платформа инструментов для сборки образов, запуска контейнеров и управления ими.

Docker упрощает перенос приложения между машинами и воспроизводимый запуск с одинаковыми зависимостями.

---

## Docker Engine

**Определение:**

Docker Engine — компонент Docker, который создаёт и запускает контейнеры, управляет образами и другими ресурсами Docker. Включает фоновый демон и API для взаимодействия с ним.

**Пример:**

```bash
docker version
```

---

## Docker Image (образ)

**Определение:**

Docker-образ — неизменяемый шаблон, из которого создают контейнеры. Содержит файловую систему приложения и метаданные для его запуска.

**Аналогия:** образ — рецепт или шаблон; контейнер — запущенный экземпляр по этому шаблону.

**Пример:**

```bash
docker images
```

---

## Docker Container (контейнер)

**Определение:**

Docker-контейнер — экземпляр Docker-образа с собственным изолированным окружением исполнения и процессами.

Из одного образа можно запустить несколько контейнеров.

**Пример:**

```bash
docker run -d --name myapp -p 8080:8080 myapp:1.0
```

`-d` — фоновый запуск, `--name` — имя контейнера, `-p 8080:8080` — публикация порта хоста на порт контейнера.

---

## Dockerfile

**Определение:**

Dockerfile — текстовый файл с инструкциями, по которым Docker собирает образ.

**Пример для Spring Boot:**

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /usr/local/app
COPY target/*.jar app.jar
EXPOSE 8080
CMD ["java", "-jar", "app.jar"]
```

- `FROM` — базовый образ;
- `WORKDIR` — рабочая директория;
- `COPY` — копирование файлов в образ;
- `EXPOSE` — документация о предполагаемом порте приложения, **не** публикация порта наружу;
- `CMD` — команда запуска контейнера.

В презентации также показаны `RUN` (команда во время сборки), `USER` (пользователь процесса) и параметры JVM `-Xms`, `-Xmx`.

---

## Слой образа (Image Layer)

**Определение:**

Слой Docker-образа — часть файловой системы образа, создаваемая при сборке. Слои можно кешировать и переиспользовать, что ускоряет повторные сборки.

**Уточнение:** не каждая инструкция Dockerfile создаёт файловый слой: некоторые инструкции изменяют только метаданные образа.

---

## Docker Registry

**Определение:**

Docker Registry — сервис хранения и распространения Docker-образов. Пример публичного реестра — Docker Hub.

**Пример:**

```bash
docker pull nginx:latest
```

Команда скачивает образ из реестра.

---

## Build, Tag, Push, Pull, Run

**Определение:**

Это основные операции в жизненном цикле Docker-образа и контейнера:

- **Build** — собрать образ по Dockerfile;
- **Tag** — назначить образу имя и тег версии;
- **Push** — загрузить образ в registry;
- **Pull** — скачать образ из registry;
- **Run** — создать и запустить контейнер из образа.

**Пример:**

```bash
docker build -t myapp:1.0 .
docker run --rm -p 8080:8080 myapp:1.0
```

`--rm` удаляет контейнер после его остановки.

---

## Виртуальная машина (Virtual Machine, VM)

**Определение:**

Виртуальная машина — изолированная вычислительная среда с собственной гостевой операционной системой, работающая под управлением гипервизора.

**Разница:** VM виртуализирует машину и запускает отдельную ОС; контейнер изолирует процессы, используя ядро хоста (в Docker Desktop для macOS/Linux-контейнеров используется вспомогательная Linux-VM).

---

## Жизненный цикл сервиса (Service Lifecycle)

**Определение:**

Жизненный цикл сервиса — последовательность состояний и операций над работающим приложением: запуск, работа, остановка, перезапуск и восстановление после сбоя.

Для production важно не только запустить сервис, но и контролировать его состояние.

---

## Система инициализации (Init System)

**Определение:**

Система инициализации — компонент ОС, запускающий необходимые службы после загрузки и управляющий их зависимостями и жизненным циклом.

В презентации сравниваются классическая `SysVinit` (скрипты запуска) и современная `systemd` (юниты и зависимости).

---

## PID 1 (Init-процесс)

**Определение:**

PID (Process ID) — идентификатор процесса. **PID 1** — первый процесс пользовательского пространства Linux, обычно выполняющий роль системы инициализации.

На системах с systemd PID 1 обычно принадлежит `systemd`.

**Уточнение:** PID 1 не является непосредственным родителем каждого процесса; процессы образуют дерево, а PID 1 участвует, в частности, в принятии осиротевших процессов.

---

## systemd

**Определение:**

systemd — система инициализации и менеджер сервисов Linux, управляющий запуском, остановкой, зависимостями, автозапуском и, при настройке, перезапуском служб.

В отличие от простого запуска в терминале, service-unit позволяет управлять приложением как системным сервисом.

**Важно:** на macOS штатным менеджером служб является `launchd`, а не `systemd`.

---

## Unit (юнит) systemd

**Определение:**

Unit — управляемый объект systemd, описываемый конфигурацией. Тип юнита определяет, чем именно управляет systemd.

Основные типы из презентации:

- `.service` — процесс/сервис;
- `.target` — объединение юнитов для достижения состояния системы;
- `.timer` — запуск по расписанию;
- `.socket` — сокет и активация сервиса при обращении;
- `.mount` — точка монтирования.

---

## Unit-файл (Unit File)

**Определение:**

Unit-файл — конфигурационный файл systemd, который определяет, что запускать, от чего зависит сервис, как запускать процесс и как подключать его к автозапуску.

**Пример:**

```ini
[Unit]
Description=My Spring Boot application
After=network.target

[Service]
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/java -jar /opt/myapp/app.jar
Restart=on-failure
User=myapp

[Install]
WantedBy=multi-user.target
```

- `[Unit]` — описание и зависимости;
- `[Service]` — параметры запуска и перезапуска;
- `[Install]` — подключение юнита к целевым состояниям автозапуска.

Путь к Java и имя пользователя нужно адаптировать к конкретному Linux-серверу.

---

## systemctl

**Определение:**

`systemctl` — консольная утилита управления systemd и его юнитами.

**Основные команды:**

```bash
sudo systemctl start myapp.service    # запустить
sudo systemctl stop myapp.service     # остановить
sudo systemctl restart myapp.service  # перезапустить
systemctl status myapp.service        # проверить состояние
sudo systemctl enable myapp.service   # включить автозапуск
sudo systemctl disable myapp.service  # отключить автозапуск
```

`enable` не равнозначно `start`: первое настраивает автозапуск, второе запускает сервис сейчас.

---

## Логирование (Logging) и журнал systemd

**Определение:**

Логирование — запись событий работы приложения для диагностики ошибок и наблюдения за состоянием сервиса.

В Linux `systemd-journald` собирает журнальные записи системы и сервисов; `journalctl` позволяет их просматривать.

---

## journalctl

**Определение:**

`journalctl` — утилита для чтения и фильтрации записей системного журнала systemd.

**Пример:**

```bash
journalctl -u myapp.service         # записи конкретного сервиса
journalctl -u myapp.service -f      # следить в реальном времени
journalctl -xe                      # конец журнала с пояснениями
journalctl --since today           # записи с начала сегодняшнего дня
```

**Уточнение:** `journalctl --since today` показывает записи за сегодня, а не только ошибки.

---

## Nginx

**Определение:**

Nginx — веб-сервер, обратный прокси-сервер и балансировщик нагрузки. Часто принимает HTTP/HTTPS-запросы пользователей и передаёт их внутреннему Spring Boot-приложению.

Также умеет раздавать статические файлы, настраивать маршрутизацию, ограничения и TLS.

---

## Обратный прокси (Reverse Proxy)

**Определение:**

Reverse proxy — сервер-посредник перед одним или несколькими backend-приложениями. Он принимает запрос клиента, направляет их приложению и возвращает ответ клиенту.

**Схема:**

```text
Браузер → Nginx (порт 80/443) → Spring Boot (порт 8080)
        ←                    ←
```

**Пример Nginx:**

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
```

---

## Backend

**Определение:**

Backend — серверная часть приложения, которая обрабатывает запросы, выполняет бизнес-логику и формирует ответы. В этой теме backend — Spring Boot-приложение за Nginx.

---

## Балансировка нагрузки (Load Balancing)

**Определение:**

Балансировка нагрузки — распределение входящих запросов между несколькими экземплярами приложения, чтобы не направлять весь трафик в один процесс.

**Пример Nginx:**

```nginx
upstream backend {
    server 127.0.0.1:8081;
    server 127.0.0.1:8082;
    server 127.0.0.1:8083;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

По умолчанию Nginx использует алгоритм round-robin (поочерёдный выбор доступных серверов). **Важно:** входящий порт Nginx (`80`) не должен конфликтовать с портами запущенных приложений (`8081–8083`) на том же адресе.

---

## TLS termination (терминация HTTPS)

**Определение:**

TLS termination — завершение защищённого HTTPS-соединения на прокси-сервере (например, Nginx), который расшифровывает запрос и может передать его backend по HTTP или HTTPS.

**Зачем:** централизовать работу с сертификатами и настройками HTTPS.

**Уточнение:** Spring Boot сам тоже может обслуживать HTTPS; Nginx для этого не обязателен.

---

## Конфигурация Nginx: http, server, location

**Определение:**

Конфигурация Nginx — набор директив, определяющих правила приёма и обработки запросов.

- `http` — общий контекст HTTP-настроек;
- `server` — виртуальный сервер, который принимает запросы по конкретному адресу/порту и имени хоста;
- `location` — правила обработки URL;
- `listen` — адрес и порт прослушивания;
- `server_name` — имя сервера (домен);
- `proxy_pass` — адрес backend, которому нужно передать запрос;
- `upstream` — именованная группа backend-серверов.

**Пример:**

```nginx
http {
    server {
        listen 80;
        server_name example.com;

        location /api/ {
            proxy_pass http://127.0.0.1:8080;
        }
    }
}
```

В Linux основной конфигурационный файл часто расположен в `/etc/nginx/nginx.conf`; на macOS при установке через Homebrew путь может отличаться.

---

## Firewall (межсетевой экран) — дополнительный термин

**Определение:**

Firewall — механизм фильтрации сетевого трафика по правилам: например, какие входящие подключения и порты разрешены.

В названии презентации он есть, но отдельного объяснения или команд для него в слайдах нет.

**Пример задачи:** разрешить пользователям подключаться к Nginx по `443`, но не открывать напрямую в интернет внутренний порт Spring Boot `8080`.
