# Тема 4: Servlet Containers

## Java EE

**Определение:**

Java EE — набор спецификаций, описывающих стандартные корпоративные сервисы и компоненты для Java-приложений.

В презентации упоминается, что сейчас это направление связано с названиями:

```text
Java EE
Jakarta EE
EE4J
```

Главная идея — разработчик пишет бизнес-логику, а инфраструктурные задачи берёт на себя контейнер.

---

## Jakarta EE

**Определение:**

Jakarta EE — современное развитие Java EE.

По смыслу для этой темы:

```text
Java EE → историческое название
Jakarta EE → современное продолжение
```

---

## Container

**Определение:**

Container — среда выполнения, которая управляет компонентами приложения.

Основные задачи контейнера:

```text
1. Управлять жизненным циклом компонентов
2. Предоставлять компонентам инфраструктурные сервисы
```

То есть разработчик не должен вручную писать весь код запуска, регистрации, инициализации и остановки компонентов.

---

## Component

**Определение:**

Component — класс, который создаётся по правилам конкретной спецификации и управляется контейнером.

Например:

```text
Servlet
EJB
JSF component
```

Контейнер знает:

* как создать компонент;
* когда вызвать его методы;
* когда уничтожить;
* какие сервисы ему предоставить.

---

## Lifecycle

**Определение:**

Lifecycle — жизненный цикл объекта или компонента.

Для компонентов контейнера это обычно:

```text
создание
   ↓
инициализация
   ↓
работа
   ↓
завершение
   ↓
уничтожение
```

---

## Lifecycle Management

**Определение:**

Lifecycle Management — управление жизненным циклом компонентов со стороны контейнера.

Вместо того чтобы разработчик вручную писал:

```java
new MyServlet();
```

и сам решал, когда его завершить, этим занимается контейнер.

---

## Infrastructure Code

**Определение:**

Infrastructure Code — технический код, который обеспечивает работу приложения, но не содержит бизнес-логику.

Примеры:

* запуск HTTP-сервера;
* регистрация обработчиков;
* управление потоками;
* создание компонентов;
* сериализация;
* управление жизненным циклом.

Цель контейнера — забрать значительную часть такого кода на себя.

---

## Business Logic

**Определение:**

Business Logic — код, реализующий правила предметной области приложения.

Например:

```text
можно ли удалить пост
как рассчитывается скидка
может ли пользователь выполнить операцию
```

Это не то же самое, что HTTP, JSON, база данных или маршрутизация.

---

## Application Server

**Определение:**

Application Server — серверная среда, реализующая набор Java EE/Jakarta EE спецификаций и контейнеров.

Примеры из презентации:

```text
GlassFish
WildFly
WebSphere
Apache TomEE
```

---

## Servlet Container

**Определение:**

Servlet Container — контейнер, реализующий Servlet API и управляющий жизненным циклом сервлетов.

Он:

* создаёт сервлеты;
* вызывает их методы;
* передаёт HTTP-запросы;
* предоставляет объекты request/response;
* управляет инициализацией и завершением.

Схема:

```text
HTTP Request
     ↓
Servlet Container
     ↓
Servlet
     ↓
Java code
```

---

## Servlet

**Определение:**

Servlet — web-компонент, управляемый Servlet Container и предназначенный для обработки запросов и генерации динамического ответа.

В презентации определение дано как:

```text
web-компонент, управляемый контейнером,
предназначенный для генерации динамического контента
```

---

## Dynamic Content

**Определение:**

Dynamic Content — содержимое, которое формируется во время обработки запроса, а не хранится как готовый статический файл.

Например:

```text
GET /users/15
```

ответ:

```json
{
  "id": 15,
  "name": "Alex"
}
```

создаётся приложением динамически.

В отличие от:

```text
logo.png
style.css
index.html
```

которые могут просто отдаваться с диска.

---

## Servlet API

**Определение:**

Servlet API — набор интерфейсов и классов, определяющих правила написания сервлетов и их взаимодействия с контейнером.

Например:

```text
Servlet
HttpServlet
HttpServletRequest
HttpServletResponse
```

---

## Apache Tomcat

**Определение:**

Apache Tomcat — популярная реализация Servlet Container.

Основная задача Tomcat в рамках этой темы:

```text
принимать HTTP-запросы
        ↓
находить нужный servlet
        ↓
вызывать его
        ↓
формировать HTTP-ответ
```

---

## `HttpServlet`

**Определение:**

`HttpServlet` — базовый класс для создания HTTP-сервлетов.

Пример:

```java
public class MainServlet extends HttpServlet {
}
```

Он уже содержит базовую реализацию обработки HTTP-запросов.

---

## `init()`

**Определение:**

`init()` — lifecycle-метод сервлета, который вызывается контейнером при инициализации сервлета.

Пример:

```java
@Override
public void init() {
    // подготовка зависимостей
}
```

Обычно вызывается не на каждый HTTP-запрос, а при создании/инициализации сервлета.

---

## `service()`

**Определение:**

`service()` — основной метод обработки входящего запроса сервлетом.

Контейнер вызывает его при каждом подходящем HTTP-запросе.

Пример:

```java
@Override
protected void service(
        HttpServletRequest req,
        HttpServletResponse resp
) throws IOException {
}
```

---

## `destroy()`

**Определение:**

`destroy()` — lifecycle-метод сервлета, который вызывается контейнером перед уничтожением сервлета.

Используется для освобождения ресурсов.

Например:

```java
@Override
public void destroy() {
    // закрытие ресурсов
}
```

---

## `HttpServletRequest`

**Определение:**

`HttpServletRequest` — объект, через который servlet получает данные HTTP-запроса.

Например:

```java
req.getMethod();
req.getRequestURI();
req.getParameter("id");
```

Через него можно получить:

* HTTP-метод;
* путь;
* параметры;
* заголовки;
* тело запроса.

---

## `HttpServletResponse`

**Определение:**

`HttpServletResponse` — объект, через который servlet формирует HTTP-ответ.

Например:

```java
resp.setContentType("application/json");
resp.setStatus(200);
resp.getWriter().print("OK");
```

---

## Request Dispatching

**Определение:**

Request Dispatching — выбор кода, который должен обработать конкретный HTTP-запрос.

Упрощённо:

```text
GET /posts
        ↓
controller.all()
```

```text
GET /posts/10
        ↓
controller.getById()
```

В презентации `MainServlet` вручную выполняет такую диспетчеризацию.

---

## Routing

**Определение:**

Routing — сопоставление HTTP-запросов с обработчиками.

Пример:

```text
GET /api/posts
GET /api/posts/10
POST /api/posts
DELETE /api/posts/10
```

Каждый запрос должен быть направлен в нужный обработчик.

---

## Ad Hoc Routing

**Определение:**

Ad Hoc Routing — ручная маршрутизация через набор `if`, `switch`, regex и подобных конструкций.

Например:

```java
if (method.equals("GET")
        && path.equals("/api/posts")) {
    // ...
}
```

```java
if (method.equals("DELETE")
        && path.matches("/api/posts/\\d+")) {
    // ...
}
```

Минус:

при росте приложения такой код быстро становится большим и неудобным.

---

## Deployment

**Определение:**

Deployment — процесс размещения приложения в контейнере или сервере для запуска.

То есть:

```text
собрали приложение
        ↓
передали контейнеру
        ↓
контейнер запустил
```

---

## Deployment Artifact

**Определение:**

Deployment Artifact — файл или набор файлов, подготовленный для развёртывания.

Для servlet-приложения это часто:

```text
WAR
```

---

## WAR

**Определение:**

WAR (Web Application Archive) — формат упаковки Java web-приложения.

В Maven:

```xml
<packaging>war</packaging>
```

WAR содержит:

* классы;
* зависимости;
* ресурсы;
* конфигурацию web-приложения.

---

## Exploded WAR

**Определение:**

Exploded WAR — распакованная версия WAR-приложения.

Вместо одного файла:

```text
app.war
```

контейнер получает директорию с содержимым приложения.

Это удобно при разработке и запуске из IDE.

---

## Runtime

**Определение:**

Runtime — среда и время выполнения программы.

В контексте Maven:

```xml
<scope>provided</scope>
```

означает, что зависимость нужна для компиляции, но в runtime её предоставляет контейнер.

---

## Maven Scope `provided`

**Определение:**

`provided` — scope зависимости Maven, означающий:

> зависимость нужна при компиляции, но предполагается, что во время выполнения её предоставит среда.

Пример:

```xml
<scope>provided</scope>
```

Для Servlet API это логично, потому что реализация уже есть в Tomcat.

---

## Deployment Descriptor

**Определение:**

Deployment Descriptor — конфигурационный файл, описывающий развёртывание приложения.

Для servlet-приложения это:

```text
web.xml
```

---

## `web.xml`

**Определение:**

`web.xml` — deployment descriptor web-приложения.

Он может описывать:

* сервлеты;
* имена сервлетов;
* классы;
* URL mappings;
* параметры загрузки.

Пример:

```xml
<servlet>
    <servlet-name>main</servlet-name>
    <servlet-class>
        ru.example.MainServlet
    </servlet-class>
</servlet>
```

---

## Servlet Registration

**Определение:**

Servlet Registration — регистрация servlet-класса внутри контейнера.

Контейнеру нужно сообщить:

```text
какой servlet существует
и на какие URL он должен реагировать
```

---

## Servlet Mapping

**Определение:**

Servlet Mapping — привязка servlet к URL или шаблону URL.

Пример:

```xml
<url-pattern>/api/*</url-pattern>
```

Теперь запросы:

```text
/api/posts
/api/users
/api/orders
```

могут попадать в один servlet.

---

## URL Pattern

**Определение:**

URL Pattern — шаблон пути, по которому контейнер выбирает servlet.

Пример:

```text
/api/*
```

означает:

```text
все URL, начинающиеся с /api/
```

---

## `load-on-startup`

**Определение:**

`load-on-startup` — настройка servlet, определяющая, должен ли контейнер инициализировать servlet при запуске приложения.

Без неё servlet может быть создан позже, при первом запросе.

---

## HTTP 405 Method Not Allowed

**Определение:**

`405 Method Not Allowed` — HTTP-статус, означающий, что ресурс существует, но указанный HTTP-метод для него не поддерживается.

В презентации он появляется при использовании дефолтной реализации `HttpServlet`.

Например:

```text
GET /api
```

но servlet не реализует нужную обработку GET.

---

## Layered Architecture

**Определение:**

Layered Architecture — архитектурный подход, при котором приложение разделяется на слои с разными зонами ответственности.

В презентации используется схема:

```text
Controller
   ↓
Service
   ↓
Repository
```

---

## Controller Layer

**Определение:**

Controller Layer — слой, отвечающий за взаимодействие с внешним клиентом.

В презентации его задачи:

```text
приём запросов
подготовка ответов
сериализация
десериализация
вызов Service
```

---

## Service Layer

**Определение:**

Service Layer — слой бизнес-логики.

Он не должен заниматься:

```text
HTTP
JSON
хранением данных
```

Он отвечает за правила приложения.

---

## Repository Layer

**Определение:**

Repository Layer — слой, отвечающий за работу с данными.

В презентации:

```text
Repository = хранение данных
```

Он не должен содержать бизнес-логику.

---

## Delegation

**Определение:**

Delegation — передача задачи другому объекту, который отвечает за неё.

Например:

```java
public Post save(Post post) {
    return repository.save(post);
}
```

`Service` делегирует сохранение `Repository`.

---

## Dependency

**Определение:**

Dependency — объект, который нужен другому объекту для выполнения его работы.

Например:

```java
public class PostService {

    private final PostRepository repository;
}
```

`PostRepository` — dependency класса `PostService`.

---

## Dependency Wiring

**Определение:**

Dependency Wiring — связывание объектов приложения друг с другом.

Например:

```java
PostRepository repository =
        new PostRepository();

PostService service =
        new PostService(repository);

PostController controller =
        new PostController(service);
```

Здесь зависимости связываются вручную.

---

## Manual Dependency Wiring

**Определение:**

Manual Dependency Wiring — ручное создание и связывание зависимостей через `new`.

Пример:

```java
repository = new PostRepository();
service = new PostService(repository);
controller = new PostController(service);
```

Это нормально для маленьких приложений, но плохо масштабируется.

---

## Scalability of Code Structure

**Определение:**

Scalability of Code Structure — способность структуры приложения оставаться управляемой при росте функциональности.

В презентации проблема формулируется так:

```text
init становится огромным
routing становится огромным
```

То есть код технически работает, но архитектура плохо масштабируется.

---

## Automatic Dependency Creation

**Определение:**

Automatic Dependency Creation — механизм, при котором framework сам создаёт нужные объекты приложения.

Например, вместо:

```java
new PostRepository();
new PostService(repository);
new PostController(service);
```

framework делает это автоматически.

Это напрямую подводит к Spring.

---

## Automatic Dependency Wiring

**Определение:**

Automatic Dependency Wiring — автоматическое связывание зависимостей между объектами.

Идея:

```text
Controller
   ↓
Service
   ↓
Repository
```

framework сам определяет, какие объекты кому нужны.

---

## Automatic Serialization / Deserialization

**Определение:**

Automatic Serialization / Deserialization — механизм, при котором framework автоматически преобразует:

```text
Java Object → JSON
```

и:

```text
JSON → Java Object
```

Без ручного вызова Gson/Jackson в каждом контроллере.

---

## Container-Managed Component

**Определение:**

Container-Managed Component — компонент, создание и жизненный цикл которого контролирует контейнер.

Servlet — пример такого компонента.

Разработчик пишет класс:

```java
public class MainServlet extends HttpServlet {
}
```

а контейнер решает:

```text
когда создать
когда вызвать init
когда вызвать service
когда вызвать destroy
```

---

# Главное из темы

Самая важная цепочка:

```text
HTTP Request
     ↓
Tomcat
     ↓
Servlet Container
     ↓
Servlet Mapping
     ↓
Servlet
     ↓
Controller
     ↓
Service
     ↓
Repository
```

Жизненный цикл servlet:

```text
container
   ↓
init()
   ↓
service()
   ↓
service()
   ↓
service()
   ↓
destroy()
```

Архитектура:

```text
Controller
    ↓
работа с HTTP / JSON

Service
    ↓
business logic

Repository
    ↓
data storage
```

Главная проблема ручного подхода:

```text
manual object creation
+
manual routing
+
manual serialization
        ↓
слишком много инфраструктурного кода
```

Именно поэтому дальше нужен framework, который автоматизирует:

```text
1. создание объектов
2. связывание зависимостей
3. регистрацию обработчиков
4. routing
5. serialization / deserialization
```

То есть эта тема фактически подводит нас к Spring.
