# Тема: JVM. Организация памяти, сборщики мусора, VisualVM
## JVM

**JVM — Java Virtual Machine** — виртуальная машина, которая загружает и выполняет Java-байткод.

Она отвечает за:

* загрузку классов;
* проверку байткода;
* организацию памяти;
* выполнение инструкций;
* компиляцию горячего кода;
* управление потоками;
* автоматическое освобождение памяти;
* взаимодействие с операционной системой.

Упрощённая цепочка:

```text
Java-код
    ↓
javac
    ↓
байткод
    ↓
JVM
    ↓
машинный код
    ↓
операционная система и процессор
```

На страницах 15–19 презентации эта цепочка показана последовательно: файл `.java` передаётся компилятору `javac`, превращается в `.class`, после чего выполняется JVM конкретной операционной системы. 

---

## Спецификация JVM

**Спецификация JVM** — документ, который описывает, как должна вести себя виртуальная машина Java.

Она определяет:

* формат `.class`;
* набор байткод-инструкций;
* области памяти;
* правила загрузки и инициализации классов;
* работу фреймов;
* обработку исключений;
* требования к выполнению программы.

Спецификация не обязана указывать, как именно всё должно быть написано внутри конкретной JVM.

Это похоже на интерфейс:

```java
public interface JvmSpecification {
    void loadClasses();
    void executeBytecode();
    void manageMemory();
}
```

А HotSpot и OpenJ9 условно являются разными реализациями этого интерфейса.

---

## HotSpot

**HotSpot** — одна из наиболее распространённых реализаций JVM.

Именно с ней обычно работают разработчики, использующие OpenJDK, Oracle JDK, Amazon Corretto и многие другие сборки JDK.

Название связано с поиском «горячих участков» программы — методов и циклов, которые выполняются особенно часто и поэтому выгодны для JIT-компиляции.

---

## JRE

**JRE — Java Runtime Environment** — среда, необходимая для запуска Java-приложений.

Концептуально она включает:

```text
JRE = JVM + стандартные библиотеки + runtime-компоненты
```

Исторически JRE часто устанавливалась отдельно. В современных поставках Java отдельная JRE встречается реже: приложение может запускаться через полный JDK или через специально собранный runtime-образ.

---

## JDK

**JDK — Java Development Kit** — комплект для разработки Java-приложений.

Он содержит:

* Java runtime;
* `java`;
* `javac`;
* `javadoc`;
* `jar`;
* `jdb`;
* `jstack`;
* `jmap`;
* `jcmd`;
* другие инструменты.

Упрощённо:

```text
JDK = runtime + инструменты разработчика
```

---

## WORA

**WORA — Write Once, Run Anywhere** — принцип «написал один раз, запускай везде».

Исходный код компилируется не напрямую в машинные инструкции Windows, macOS или Linux, а в платформенно-независимый байткод.

Для каждой операционной системы существует собственная реализация JVM:

```text
Один и тот же .class
        ├── JVM для Windows
        ├── JVM для Linux
        └── JVM для macOS
```

При этом полностью игнорировать платформу нельзя. Например, программа может зависеть от:

* путей файловой системы;
* кодировок;
* системных библиотек;
* нативного кода;
* доступных ресурсов;
* поведения конкретной JVM.

---

# Компиляция Java-программы

## javac

**`javac`** — компилятор Java, который преобразует исходный код в байткод.

Исходный файл:

```java
public class Main {

    public static void main(String[] args) {
        System.out.println("Hello");
    }
}
```

Компиляция:

```bash
javac Main.java
```

После этого появляется:

```text
Main.class
```

---

## Class-файл

**Class-файл** — бинарный файл с байткодом и служебной информацией о классе.

Он может содержать:

* имя класса;
* имя родительского класса;
* интерфейсы;
* поля;
* методы;
* модификаторы;
* байткод методов;
* таблицу констант;
* аннотации;
* отладочную информацию.

Расширение `.class` не означает, что файл содержит ровно один исходный Java-файл. Например, компилятор создаёт отдельные class-файлы для вложенных и анонимных классов.

---

## Bytecode

**Байткод** — промежуточный набор инструкций JVM.

Он отличается:

* от Java-кода;
* от машинного кода процессора;
* от ассемблера конкретной архитектуры.

Посмотреть байткод можно через:

```bash
javap -c Main.class
```

Пример результата:

```text
0: getstatic
3: ldc
5: invokevirtual
8: return
```

JVM выполняет именно такие инструкции, а не строки исходного файла.

---

## Machine code

**Машинный код** — инструкции, которые непосредственно выполняет процессор.

Примеры архитектур:

```text
x86-64
ARM64
```

JIT-компилятор JVM может преобразовать часто исполняемый байткод в машинный код текущего процессора.

---

# Подсистема загрузки классов

## ClassLoader

**ClassLoader** — компонент JVM, который находит байты класса и создаёт на их основе объект типа `Class<?>`.

Класс может быть загружен:

* из каталога;
* из JAR-файла;
* из модуля;
* из сети;
* из базы данных;
* из массива байтов;
* пользовательским загрузчиком.

Сам `.class` на диске — ещё не загруженный класс. Он становится частью работающей программы после обработки загрузчиком.

---

## Три стандартных загрузчика

На страницах 27–40 презентации показана цепочка стандартных загрузчиков и делегирование запроса от Application ClassLoader к родителям. 

### Bootstrap ClassLoader

**Bootstrap ClassLoader** загружает фундаментальные классы платформы Java.

Например:

```text
java.lang.Object
java.lang.String
java.lang.Class
java.util.List
```

Он реализован внутри JVM и не обязательно представлен обычным Java-объектом.

Поэтому:

```java
System.out.println(String.class.getClassLoader());
```

часто выводит:

```text
null
```

`null` здесь условно обозначает Bootstrap ClassLoader.

---

### Platform ClassLoader

**Platform ClassLoader** загружает платформенные модули, которые не относятся к минимальному набору Bootstrap ClassLoader.

В старых версиях Java похожую роль выполнял Extension ClassLoader.

---

### Application ClassLoader

**Application ClassLoader**, или System ClassLoader, загружает классы приложения и его зависимостей.

Обычно он ищет классы:

* в classpath;
* в module path;
* в JAR-файлах проекта;
* в каталогах с результатами компиляции.

Пример:

```java
System.out.println(Main.class.getClassLoader());
```

может вывести:

```text
jdk.internal.loader.ClassLoaders$AppClassLoader
```

---

## Parent Delegation Model

**Parent Delegation Model** — модель, при которой загрузчик сначала просит родительский загрузчик найти класс, а только потом ищет его самостоятельно.

Упрощённый алгоритм:

```text
Application ClassLoader
        ↓ делегирует
Platform ClassLoader
        ↓ делегирует
Bootstrap ClassLoader
        ↓ не нашёл

Platform ClassLoader ищет сам
        ↓ не нашёл

Application ClassLoader ищет сам
```

Это защищает базовые классы Java от подмены.

Например, если создать собственный:

```java
package java.lang;

public class String {
}
```

приложение не сможет нормально заменить стандартный `java.lang.String`.

---

## loadClass()

Метод:

```java
loadClass(String name)
```

обычно выполняет следующую логику:

1. Проверяет, не загружен ли класс ранее.
2. Делегирует загрузку родителю.
3. Если родитель не нашёл класс, вызывает собственный поиск.
4. Возвращает объект `Class<?>`.
5. При неудаче выбрасывает `ClassNotFoundException`.

---

## findClass()

**`findClass()`** — метод, в котором пользовательский ClassLoader обычно реализует непосредственный поиск байтов класса.

Простейшая идея:

```java
public class CustomClassLoader extends ClassLoader {

    @Override
    protected Class<?> findClass(String name)
            throws ClassNotFoundException {

        byte[] bytes = loadBytes(name);

        return defineClass(
                name,
                bytes,
                0,
                bytes.length
        );
    }

    private byte[] loadBytes(String name)
            throws ClassNotFoundException {
        throw new UnsupportedOperationException();
    }
}
```

В production собственные ClassLoader нужны редко, но используются в:

* серверах приложений;
* плагинных системах;
* IDE;
* системах динамического обновления;
* контейнерах;
* инструментах тестирования;
* фреймворках.

---

## Идентичность класса

Для JVM класс определяется не только именем.

Идентичность класса:

```text
полное имя класса + загрузивший его ClassLoader
```

То есть два класса:

```text
com.example.User
```

могут считаться разными, если были загружены разными ClassLoader.

Из-за этого иногда встречается особенно издевательская ошибка:

```text
ClassCastException:
com.example.User cannot be cast to com.example.User
```

Названия одинаковые, загрузчики разные. JVM в этом случае формально права, хотя выглядит так, будто она решила потроллить разработчика.

---

## Ленивая загрузка классов

Классы обычно загружаются по мере необходимости, а не все сразу при старте JVM.

Например:

```java
public class Main {

    public static void main(String[] args) {
        if (false) {
            SomeLargeClass.doSomething();
        }
    }
}
```

Само наличие имени класса в исходном коде ещё не гарантирует, что он будет загружен и инициализирован.

Правильнее говорить:

> Класс загружается, когда JVM требуется его определение для дальнейшей работы.

# Жизненный цикл класса

На страницах 41–45 показаны основные этапы:

```text
Loading
    ↓
Linking
    ├── Verification
    ├── Preparation
    └── Resolution
    ↓
Initialization
```



## Loading

**Loading** — поиск байтов класса и создание его представления в JVM.

На этом этапе:

* ClassLoader получает байты;
* JVM разбирает class-файл;
* создаётся соответствующий объект `Class<?>`.

---

## Linking

**Linking, или связывание** — подготовка загруженного класса к использованию.

Связывание включает:

```text
Verification → Preparation → Resolution
```

---

## Verification

**Verification** — проверка корректности и безопасности байткода.

JVM проверяет, например:

* правильность структуры `.class`;
* корректность инструкций;
* совместимость типов;
* корректность доступа к локальным переменным;
* отсутствие недопустимых переходов;
* соответствие стека операндов ожидаемым типам.

Благодаря этому JVM не должна слепо исполнять произвольный повреждённый набор байтов.

---

## Preparation

**Preparation** — выделение памяти для статических полей и присваивание им значений по умолчанию.

Пример:

```java
public class User {

    static int count = 10;
    static boolean enabled = true;
    static Object value = new Object();
}
```

Во время подготовки логически устанавливаются значения:

```text
count   = 0
enabled = false
value   = null
```

А присваивания:

```text
10
true
new Object()
```

обычно выполняются позже, во время инициализации класса.

Для compile-time-констант существуют отдельные нюансы: значение из `ConstantValue` может быть установлено уже на этапе подготовки.

---

## Resolution

**Resolution** — преобразование символьных ссылок в конкретные ссылки на классы, поля и методы.

В class-файле может храниться символическое описание:

```text
java/lang/System.out
java/io/PrintStream.println
```

JVM должна связать эти записи с реально загруженными сущностями.

Разрешение может выполняться не строго сразу для всех ссылок. JVM имеет право делать часть работы лениво.

---

## Initialization

**Initialization** — выполнение статической инициализации класса.

Выполняются:

* инициализаторы статических полей;
* статические блоки;
* сгенерированный компилятором метод `<clinit>`.

Пример:

```java
public class Settings {

    static int timeout = loadTimeout();

    static {
        System.out.println("Settings initialized");
    }

    private static int loadTimeout() {
        return 30;
    }
}
```

Порядок выполнения соответствует порядку объявления:

```text
1. timeout = loadTimeout()
2. static-блок
```

Перед инициализацией класса JVM сначала инициализирует его родительский класс.

---

## ClassNotFoundException

**`ClassNotFoundException`** — проверяемое исключение, возникающее, когда код явно попросил загрузить класс, но загрузчик его не нашёл.

Пример:

```java
Class.forName("com.example.Unknown");
```

Метод обязан обработать или объявить исключение:

```java
try {
    Class.forName("com.example.Unknown");
} catch (ClassNotFoundException exception) {
    System.err.println("Класс не найден");
}
```

---

## NoClassDefFoundError

**`NoClassDefFoundError`** означает, что JVM ожидала найти класс во время выполнения, но использовать его не удалось.

Причины:

* зависимость была при компиляции, но отсутствует при запуске;
* class-файл удалён;
* несовместим classpath;
* ранее произошла ошибка инициализации класса.

Разница:

```text
ClassNotFoundException
→ код явно попросил ClassLoader найти класс

NoClassDefFoundError
→ JVM сама попыталась использовать необходимый класс
```

---

## ExceptionInInitializerError

**`ExceptionInInitializerError`** возникает, если во время статической инициализации было выброшено исключение.

```java
public class Config {

    static int value = initialize();

    private static int initialize() {
        throw new IllegalStateException("Ошибка конфигурации");
    }
}
```

После неудачной инициализации класс обычно нельзя нормально использовать в текущем ClassLoader.

---

## UnsupportedClassVersionError

**`UnsupportedClassVersionError`** появляется, если class-файл был скомпилирован для более новой версии Java, чем используемая JVM.

Например:

```text
скомпилировали на Java 25
запускаем на Java 21
```

Решения:

* обновить runtime;
* собирать проект с подходящим `--release`;
* правильно настроить Gradle или Maven.

---

# Runtime Data Areas

**Runtime Data Areas** — области памяти, которые JVM использует во время выполнения программы.

Основные области:

| Область               | Общая или на поток | Назначение             |
| --------------------- | ------------------ | ---------------------- |
| Heap                  | Общая              | Объекты и массивы      |
| Method Area           | Общая              | Данные классов         |
| Runtime Constant Pool | Общая              | Константы class-файлов |
| JVM Stack             | На каждый поток    | Фреймы методов         |
| PC Register           | На каждый поток    | Текущая инструкция     |
| Native Method Stack   | На каждый поток    | Нативные вызовы        |

В HotSpot Method Area в основном реализована через **Metaspace**.

---

# Stack

## JVM Stack

**JVM Stack, или стек JVM** — область памяти отдельного потока, в которой хранятся фреймы вызванных методов.

У каждого Java-потока свой стек:

```text
Thread 1 → Stack 1
Thread 2 → Stack 2
Thread 3 → Stack 3
```

Другой поток не может напрямую использовать фреймы чужого стека.

---

## Stack frame

**Stack frame, или фрейм стека** — структура, создаваемая при вызове метода.

Фрейм содержит:

* локальные переменные;
* параметры;
* ссылку `this` для instance-метода;
* стек операндов;
* информацию для возврата;
* служебные данные.

Пример:

```java
private int sum(int first, int second) {
    int result = first + second;
    return result;
}
```

Условно фрейм содержит:

```text
this
first
second
result
operand stack
return information
```

После завершения метода его фрейм удаляется со стека автоматически.

---

## Local Variable Array

**Local Variable Array** — массив локальных переменных текущего фрейма.

Для instance-метода нулевая позиция обычно содержит:

```java
this
```

Дальше идут параметры и локальные переменные.

Для `static`-метода ссылки `this` нет.

---

## Operand Stack

**Operand Stack** — часть фрейма, которую байткод использует для промежуточных вычислений.

Для выражения:

```java
int result = first + second;
```

упрощённая работа байткода:

```text
загрузить first в стек операндов
загрузить second
сложить два верхних значения
сохранить результат в локальную переменную
```

---

## -Xss

Параметр:

```bash
-Xss512k
```

задаёт приблизительный размер стека одного потока.

Пример запуска:

```bash
java -Xss512k Main
```

Важно: это размер **на один поток**, а не единый стек всего приложения.

Если создать 1 000 потоков со стеком 1 МБ, только под потенциальные стеки может потребоваться около 1 ГБ адресного пространства.

---

## StackOverflowError

**`StackOverflowError`** возникает, когда стек потока переполнен.

Частая причина — бесконечная рекурсия:

```java
public static void recursive() {
    recursive();
}
```

Увеличение `-Xss` может позволить выполнить больше вложенных вызовов, но не исправляет ошибочный алгоритм.

---

# Heap

## Heap

**Heap, или куча** — общая область памяти JVM, где обычно размещаются объекты и массивы.

```java
User user = new User();
```

Упрощённо:

```text
user              → stack
new User()         → heap
```

В стеке находится локальная переменная-ссылка, а сам объект — в куче.

Heap доступен всем потокам, поэтому работа с общими изменяемыми объектами требует синхронизации.

---

## Ссылка и объект

Код:

```java
Object first = new Object();
Object second = first;
```

создаёт:

* один объект;
* две переменные-ссылки.

```text
first  ──┐
         ├──→ Object
second ──┘
```

Присваивание ссылки не копирует объект.

---

## -Xms

Параметр:

```bash
-Xms256m
```

задаёт начальный размер Java heap.

```bash
java -Xms256m Main
```

---

## -Xmx

Параметр:

```bash
-Xmx1g
```

задаёт максимальный размер Java heap.

```bash
java -Xms256m -Xmx1g Main
```

Это не ограничение всей памяти процесса. Кроме heap JVM использует:

* Metaspace;
* стеки потоков;
* Code Cache;
* direct memory;
* нативные библиотеки;
* внутренние структуры GC;
* память самой JVM.

Поэтому процесс с:

```text
-Xmx1g
```

может потреблять заметно больше 1 ГБ RAM.

---

## OutOfMemoryError: Java heap space

Ошибка:

```text
java.lang.OutOfMemoryError: Java heap space
```

означает, что JVM не смогла выделить память в heap.

Причины:

* heap слишком мал;
* утечка памяти;
* загружено слишком много данных;
* неограниченный кэш;
* считывание огромного файла целиком;
* слишком крупная коллекция.

Простое увеличение `-Xmx` не всегда лечит проблему. Иногда оно лишь даёт утечке больше пространства для творчества.

---

# Metaspace

## Method Area

**Method Area** — логическая область памяти из спецификации JVM, содержащая данные, связанные с классами.

Конкретная реализация определяется JVM.

---

## Metaspace

**Metaspace** — реализация значительной части Method Area в HotSpot, используемая начиная с Java 8 вместо PermGen.

В ней находятся метаданные загруженных классов:

* имена;
* описания полей;
* описания методов;
* информация о наследовании;
* служебные структуры;
* runtime constant pools;
* данные ClassLoader.

Metaspace располагается в native memory, то есть вне Java heap.

На страницах 50–53 презентации загрузка классов связывается с размещением метаинформации в Metaspace. 

---

## PermGen

**PermGen — Permanent Generation** — старая область HotSpot, использовавшаяся до Java 8 для метаданных классов.

Начиная с Java 8 она была заменена Metaspace.

Параметры вроде:

```text
-XX:PermSize
-XX:MaxPermSize
```

в современных JDK не используются.

---

## -XX:MaxMetaspaceSize

Параметр:

```bash
-XX:MaxMetaspaceSize=256m
```

ограничивает максимальный размер Metaspace.

Без явного ограничения Metaspace может расти, пока JVM не столкнётся с ограничениями native memory или операционной системы.

---

## -XX:MetaspaceSize

Параметр:

```bash
-XX:MetaspaceSize=64m
```

не следует понимать как точный начальный размер Metaspace.

Он задаёт начальный порог, после достижения которого JVM начинает активнее инициировать сборки мусора, связанные с выгрузкой классов, и затем адаптирует этот порог.

---

## OutOfMemoryError: Metaspace

Ошибка:

```text
java.lang.OutOfMemoryError: Metaspace
```

означает, что JVM не смогла выделить память под метаданные классов.

Причины:

* загружено слишком много классов;
* динамически создаются классы или proxy;
* ClassLoader не освобождается;
* постоянные redeploy в сервере приложений;
* слишком низкий `MaxMetaspaceSize`.

---

## Утечка ClassLoader

ClassLoader может удерживать все загруженные им классы.

Если приложение создаёт новые ClassLoader, но продолжает хранить на них ссылки, метаданные классов не освобождаются.

Типичные источники:

* потоки, не остановленные после redeploy;
* `ThreadLocal`;
* статические коллекции;
* JDBC-драйверы;
* listeners;
* таймеры;
* кэши;
* неправильная архитектура плагинов.

---

# Дополнительные области памяти

## PC Register

**Program Counter Register** — область отдельного потока, содержащая информацию о текущей выполняемой инструкции.

У каждого потока собственный PC Register, поскольку разные потоки могут одновременно выполнять разные участки байткода.

---

## Native Method Stack

**Native Method Stack** используется при выполнении нативных методов.

Нативный метод объявляется через:

```java
public native void execute();
```

Такие методы реализуются не на Java, а, например, на C или C++ через JNI.

---

## Code Cache

**Code Cache** — native memory, где HotSpot хранит машинный код, созданный JIT-компилятором.

Это не Java heap.

Если Code Cache переполняется, JVM может перестать компилировать новые участки кода, что ухудшит производительность.

---

## Direct Memory

**Direct Memory** — нативная память, которую Java-приложение может использовать через direct buffers.

```java
ByteBuffer buffer =
        ByteBuffer.allocateDirect(1024 * 1024);
```

Такая память расположена вне heap, но объект `ByteBuffer`, управляющий ею, находится в heap.

Возможная ошибка:

```text
OutOfMemoryError: Direct buffer memory
```

---

# Разбор примера из презентации

На страницах 54–66 презентация по шагам показывает размещение локальных переменных, ссылок и объектов в stack, heap и Metaspace. 

Код:

```java
public class Memory {

    public static void main(String[] args) {
        int i = 1;

        Object obj = new Object();
        Memory mem = new Memory();

        mem.foo(obj);
    }

    private void foo(Object param) {
        String str = param.toString();
        System.out.println(str);
    }
}
```

## Загрузка класса

ClassLoader загружает:

```text
Memory
Object
String
System
PrintStream
```

Метаданные классов становятся доступны JVM. В HotSpot значительная часть метаданных размещается в Metaspace.

Объекты `Class<?>`, соответствующие этим классам, являются обычными объектами и находятся в heap.

---

## Вызов main()

Для `main()` создаётся фрейм в стеке текущего потока:

```text
Stack
└── main frame
```

В нём появляется параметр:

```java
String[] args
```

Сам массив аргументов — объект в heap, а `args` — ссылка во фрейме.

---

## int i = 1

```java
int i = 1;
```

Примитивное значение хранится в локальных переменных фрейма:

```text
main frame
├── args
└── i = 1
```

---

## new Object()

```java
Object obj = new Object();
```

Создаётся объект в heap:

```text
Heap
└── Object
```

Во фрейме `main()` появляется ссылка:

```text
main frame
└── obj ──→ Object
```

---

## new Memory()

```java
Memory mem = new Memory();
```

Создаётся второй объект:

```text
Heap
├── Object
└── Memory
```

Локальная переменная `mem` хранит ссылку:

```text
main frame
├── obj ──→ Object
└── mem ──→ Memory
```

---

## Вызов foo()

```java
mem.foo(obj);
```

Создаётся новый фрейм:

```text
Stack
├── foo frame
└── main frame
```

Поскольку `foo()` — instance-метод, в его локальных переменных имеются:

```text
this  ──→ объект Memory
param ──→ объект Object
```

Переменные:

```java
obj
param
```

содержат копии одной и той же ссылки.

Сам объект не копируется.

---

## param.toString()

```java
String str = param.toString();
```

Вызывается метод `toString()`, для которого концептуально создаётся ещё один фрейм, если вызов не был оптимизирован JIT-компилятором.

Результат записывается в `str`:

```text
foo frame
├── this
├── param ──→ Object
└── str   ──→ String
```

Для обычного `Object` возвращается строка, похожая на:

```text
java.lang.Object@5acf9800
```

Фактическое создание объектов может быть оптимизировано JVM, поэтому схема полезна как модель, но не гарантирует точное физическое поведение после JIT-оптимизаций.

---

## System.out.println(str)

```java
System.out.println(str);
```

Вызывается метод `println()`. Концептуально для него создаётся новый фрейм и передаётся копия ссылки `str`.

После возврата из `println()` его фрейм удаляется.

Затем завершается `foo()`, и исчезают его локальные переменные:

```text
this
param
str
```

Если созданная строка больше нигде не используется, она может стать доступна для GC.

После завершения `main()` исчезнут ссылки `obj` и `mem`, а их объекты тоже станут недостижимыми.

---

# Execution Engine

**Execution Engine, или движок выполнения** — часть JVM, которая исполняет загруженный байткод.

В презентации выделены три компонента:

```text
Interpreter
JIT Compiler
Garbage Collector
```



---

## Interpreter

**Интерпретатор** читает и выполняет отдельные инструкции байткода.

Преимущество:

* быстро начинает выполнение;
* не требует предварительной компиляции всего приложения.

Недостаток:

* повторное интерпретирование одного и того же кода медленнее выполнения готового машинного кода.

---

## JIT Compiler

**JIT — Just-In-Time compiler** — компилятор, который во время работы программы преобразует подходящие участки байткода в машинный код.

Схема:

```text
Bytecode
   ↓ сначала
Interpreter
   ↓ участок стал горячим
JIT compilation
   ↓
Machine code
```

---

## Hot method

**Hot method, или горячий метод** — метод, который выполняется достаточно часто, чтобы JVM решила его скомпилировать.

JVM собирает profiling-информацию:

* количество вызовов;
* частоту выполнения циклов;
* реальные типы объектов;
* часто выполняемые ветви;
* поведение виртуальных вызовов.

После этого JIT выбирает оптимизации.

---

## OSR

**OSR — On-Stack Replacement** — компиляция и замена уже выполняющегося горячего участка, обычно длинного цикла.

Например:

```java
for (long i = 0; i < Long.MAX_VALUE; i++) {
    calculate(i);
}
```

JVM не обязана ждать завершения метода. Она может скомпилировать цикл и переключить продолжающееся выполнение на оптимизированный машинный код.

---

## Inlining

**Inlining** — подстановка тела вызываемого метода непосредственно в вызывающий код.

До оптимизации:

```java
int result = sum(10, 20);
```

После концептуального inlining:

```java
int result = 10 + 20;
```

Преимущества:

* убирается стоимость вызова;
* открываются дополнительные оптимизации;
* могут исчезнуть временные объекты.

Из-за inlining реальное выполнение после JIT не всегда соответствует учебной схеме «каждый вызов обязательно создаёт заметный фрейм».

---

## Escape analysis

**Escape analysis** — анализ того, выходит ли объект за пределы метода или потока.

Пример:

```java
public int calculate() {
    Point point = new Point(10, 20);
    return point.x() + point.y();
}
```

Если JVM докажет, что объект нигде больше не используется, она может:

* устранить выделение объекта;
* заменить его отдельными значениями;
* удалить ненужную синхронизацию.

Поэтому правило «каждый `new` обязательно создаёт объект в heap» полезно как базовая модель, но после оптимизации не является абсолютным.

---

## Deoptimization

**Deoptimization** — отказ JVM от ранее скомпилированной оптимизированной версии кода, если предположения JIT перестали быть верными.

Например, JIT предположил, что виртуальный метод всегда вызывается у одного класса, но позже появился объект другого типа.

Тогда JVM может вернуться к менее оптимизированному варианту и скомпилировать код заново.

---

# Garbage Collection

## Garbage Collector

**Garbage Collector, или сборщик мусора** — компонент JVM, который автоматически освобождает память от объектов, больше недостижимых приложением.

GC работает прежде всего с heap.

Он не гарантирует:

* немедленное удаление объекта;
* запуск в конкретный момент;
* вызов по просьбе приложения;
* исправление утечек памяти.

---

## Недостижимый объект

Объект считается **недостижимым**, если до него нельзя добраться от корневых ссылок GC.

```java
Object value = new Object();
value = null;
```

После присваивания `null` объект может стать недостижимым, если других ссылок на него нет.

Правильная формулировка:

> Объект становится кандидатом на сборку мусора.

Он не обязан исчезнуть сразу же.

---

## Memory leak в Java

**Утечка памяти** возможна и при наличии GC.

GC удаляет недостижимые объекты. Но он не умеет угадывать, нужен ли объект бизнес-логике.

```java
private static final List<byte[]> CACHE =
        new ArrayList<>();

public static void save(byte[] data) {
    CACHE.add(data);
}
```

Все массивы продолжают быть достижимыми через статическую коллекцию, поэтому GC не может их удалить.

---

# Как определить ненужные объекты

На страницах 78–81 сравниваются два подхода:

```text
reference counting
mark-and-sweep
```



## Reference counting

**Reference counting** — подсчёт количества ссылок на объект.

Условно:

```text
счётчик > 0 → объект используется
счётчик = 0 → объект можно удалить
```

Главная проблема — циклические ссылки:

```java
class Node {
    Node next;
}
```

```java
Node first = new Node();
Node second = new Node();

first.next = second;
second.next = first;

first = null;
second = null;
```

Объекты ссылаются друг на друга, но приложение больше не может до них добраться.

Простой подсчёт ссылок увидит ненулевые счётчики и ошибочно сохранит объекты.

---

## Tracing Garbage Collector

**Tracing GC** начинает с известных корней и обходит граф объектов.

```text
GC Roots
   ↓
достижимые объекты
   ↓
достижимые объекты второго уровня
```

Всё, до чего нельзя добраться от корней, считается мусором.

---

## GC Roots

**GC Roots** — начальный набор ссылок, от которого сборщик мусора начинает поиск достижимых объектов.

К корням могут относиться:

* локальные ссылки в активных фреймах потоков;
* активные Java-потоки;
* статические ссылки;
* JNI-ссылки;
* объекты, удерживаемые JVM;
* активные мониторы;
* ClassLoader и связанные структуры.

Упрощённый граф:

```text
GC Root
   ↓
User
   ↓
Order
   ↓
Product
```

Все три объекта достижимы и не могут быть удалены.

---

## Mark phase

**Mark** — этап, на котором GC отмечает достижимые объекты.

```text
GC Roots → обход графа → пометка живых объектов
```

---

## Sweep phase

**Sweep** — освобождение памяти, занятой непомеченными объектами.

Недостаток простого mark-sweep — фрагментация:

```text
[живой][свободно][живой][свободно][живой]
```

Свободной памяти может быть много суммарно, но большие непрерывные блоки отсутствуют.

---

## Compact phase

**Compaction** — перемещение живых объектов ближе друг к другу.

До:

```text
[живой][мусор][живой][мусор][живой]
```

После:

```text
[живой][живой][живой][свободная память]
```

Преимущество — меньше фрагментация.

Цена — необходимость перемещать объекты и обновлять ссылки.

---

## Copying collection

**Copying collector** переносит живые объекты из одной области памяти в другую.

После переноса исходную область можно очистить целиком.

Этот подход эффективен, если большинство объектов быстро умирает.

---

# Поколения heap

На странице 82 показано классическое разделение:

```text
Young Generation
├── Eden
├── Survivor 0
└── Survivor 1

Old Generation
└── Tenured
```



## Generational hypothesis

**Гипотеза поколений** утверждает:

> Большинство объектов живёт недолго, а объекты, пережившие несколько сборок, вероятнее всего проживут дольше.

Примеры короткоживущих объектов:

* временные DTO;
* строки во время обработки запроса;
* объекты итераций;
* временные коллекции;
* результаты промежуточных вычислений.

---

## Young Generation

**Young Generation** — часть heap для новых объектов.

В классической схеме состоит из:

* Eden;
* Survivor 0;
* Survivor 1.

Конкретная физическая организация зависит от выбранного сборщика мусора.

---

## Eden

**Eden** — область, куда обычно помещаются новые объекты.

```java
new User();
new Order();
new byte[1024];
```

Когда Eden заполняется, может запускаться Young GC.

---

## Survivor Spaces

**Survivor Space** — области, куда копируются объекты, пережившие сборку молодого поколения.

Обычно используются две области:

```text
S0
S1
```

Одна выступает источником, другая — назначением. После сборки их роли меняются.

---

## Object age

**Возраст объекта** — количество сборок молодого поколения, которые объект пережил.

После достижения определённого возраста объект может быть перемещён в Old Generation.

---

## Promotion

**Promotion** — перенос объекта из Young Generation в Old Generation.

Причины:

* объект пережил достаточно Young GC;
* Survivor не хватает места;
* объект слишком крупный;
* решение конкретного сборщика.

---

## Old Generation

**Old Generation**, или Tenured Generation, содержит долгоживущие объекты.

Например:

* долгоживущие кэши;
* singleton-объекты;
* конфигурация;
* инфраструктурные компоненты;
* объекты, удерживаемые приложением длительное время.

---

## Young GC

**Young GC** очищает молодое поколение.

Поскольку большая часть молодых объектов обычно уже мертва, такая сборка часто эффективна.

---

## Major GC и Full GC

Термины `Major GC` и `Full GC` используются неоднозначно.

Обычно:

```text
Major GC → сборка старого поколения
Full GC  → сборка большей части или всего heap
```

Но точное значение зависит от сборщика и JVM.

В production лучше смотреть реальные GC-логи, а не полагаться только на разговорные названия.

---

# Stop-The-World

**Stop-The-World, или STW** — пауза, во время которой JVM приостанавливает Java-потоки приложения для выполнения безопасной операции.

На странице 83 это отдельно отмечено как важный термин. 

Во время STW приложение:

* не обрабатывает запросы;
* не выполняет бизнес-логику;
* не продолжает обычные Java-вычисления.

При этом внутренние потоки JVM могут продолжать работу.

---

## Safepoint

**Safepoint** — состояние, в котором JVM знает достаточно о потоках и объектах, чтобы безопасно выполнить специальную операцию.

Причины достижения safepoint:

* фаза GC;
* deoptimization;
* снятие thread dump;
* некоторые операции со стеками;
* выгрузка классов.

STW и GC связаны, но Stop-The-World может происходить не только из-за GC.

---

## Concurrent GC

**Concurrent GC** выполняет значительную часть работы одновременно с Java-потоками приложения.

Однако «concurrent» не означает полное отсутствие пауз. Обычно остаются короткие STW-фазы.

---

## Throughput

**Throughput** — доля времени, в течение которого приложение выполняет полезную работу.

```text
throughput =
время работы приложения /
общее время
```

Сборщик, оптимизированный под throughput, может допускать более длинные паузы, но тратить меньше общего процессорного времени на GC.

---

## Latency

**Latency** — задержка обработки операции или запроса.

Для web-сервисов важны:

* среднее время ответа;
* p95;
* p99;
* максимальные паузы.

Даже при высоком throughput длинные STW-паузы могут ухудшить пользовательский опыт.

---

# Сборщики мусора

**Алгоритм GC** описывает принцип работы: mark, sweep, compact, copy.

**Сборщик мусора** — конкретная реализация, использующая один или несколько алгоритмов.

## Serial GC

Работает преимущественно одним GC-потоком.

Подходит для:

* небольших heap;
* простых приложений;
* сред с ограниченным количеством CPU.

Обычно делает заметные STW-паузы.

---

## Parallel GC

Использует несколько потоков сборки мусора.

Главная цель — высокий throughput.

Может быть подходящим для:

* batch-обработки;
* вычислительных задач;
* приложений, где допустимы более длинные паузы.

---

## G1 GC

**G1 — Garbage-First** делит heap на регионы и старается сначала очищать области, содержащие больше всего мусора.

Цели:

* управляемые паузы;
* работа с крупными heap;
* конкурентная сборка части старого поколения;
* постепенная компактификация.

---

## ZGC

**ZGC** ориентирован на очень короткие паузы и выполняет значительную часть работы конкурентно.

Применяется, когда особенно важна низкая latency.

Цена может проявляться в:

* дополнительном потреблении ресурсов;
* сложности внутренней реализации;
* отличающемся поведении throughput.

---

## Shenandoah

**Shenandoah GC** также ориентирован на короткие паузы за счёт конкурентного перемещения объектов.

Доступность конкретного сборщика зависит от используемой сборки и версии JDK.

---

# System.gc()

Вызов:

```java
System.gc();
```

не означает:

> Немедленно выполни полную сборку мусора.

Это лишь рекомендация JVM.

JVM может:

* выполнить сборку;
* отложить её;
* проигнорировать;
* обработать вызов согласно настройкам.

В production вручную вызывать `System.gc()` обычно не следует без конкретной причины и измерений.

# VisualVM

На страницах 84–85 VisualVM представлена как инструмент наблюдения за использованием памяти и работой GC. 

## VisualVM

**VisualVM** — графический инструмент анализа работающих Java-приложений.

Он позволяет наблюдать:

* heap;
* Metaspace;
* активность GC;
* количество классов;
* потоки;
* загрузку CPU;
* состояние приложения;
* heap dump;
* thread dump;
* CPU sampling;
* memory sampling.

---

## Monitor

Раздел **Monitor** показывает графики:

* CPU;
* Heap;
* Metaspace;
* Classes;
* Threads.

Для нормального приложения график heap часто похож на пилу:

```text
память растёт
      /
     /
    / ← GC
___/  \____
```

Рост означает создание объектов, падение — освобождение памяти после GC.

---

## Как выглядит возможная утечка

Подозрительная картина:

```text
после каждой сборки
используемая память остаётся всё выше
```

```text
GC 1 → осталось 100 MB
GC 2 → осталось 150 MB
GC 3 → осталось 220 MB
GC 4 → осталось 300 MB
```

Это ещё не доказательство утечки, но повод исследовать heap.

---

## Heap dump

**Heap dump** — снимок объектов в heap в конкретный момент.

Он содержит информацию:

* какие классы имеют экземпляры;
* сколько объектов создано;
* сколько памяти они занимают;
* какие объекты на них ссылаются;
* почему объект остаётся достижимым;
* путь до GC Root.

Heap dump используют для поиска утечек памяти.

Важно: снятие heap dump может остановить приложение и потребовать много дискового пространства.

---

## Thread dump

**Thread dump** — снимок состояния всех потоков.

Он показывает:

* имена потоков;
* состояния;
* stack trace;
* блокировки;
* ожидания;
* deadlock.

Типичные состояния:

```text
RUNNABLE
BLOCKED
WAITING
TIMED_WAITING
```

---

## Sampler

**Sampler** периодически проверяет, чем занято приложение.

Например:

* какие методы чаще встречаются в стеке;
* какие классы создают больше объектов;
* где расходуется CPU.

Плюс — сравнительно небольшое влияние на приложение.

Минус — результат статистический: короткий вызов может не попасть в выборку.

---

## Profiler

**Profiler** может более детально отслеживать вызовы и выделения памяти.

Плюсы:

* более подробные данные;
* точные цепочки вызовов;
* анализ allocations.

Минусы:

* более высокая нагрузка;
* возможное искажение поведения приложения;
* осторожность при использовании в production.

Для первого анализа обычно разумно начинать с sampler.

---

## Classes

Раздел с классами позволяет увидеть:

* количество загруженных классов;
* количество выгруженных классов;
* динамику class loading.

Постоянный рост количества классов после повторных redeploy может указывать на утечку ClassLoader и рост Metaspace.

---

## Threads

Раздел потоков помогает найти:

* слишком большое число потоков;
* заблокированные потоки;
* deadlock;
* поток, постоянно нагружающий CPU;
* зависшие операции;
* неработающий thread pool.

---

# Практические JVM-параметры

Пример запуска:

```bash
java \
  -Xms256m \
  -Xmx512m \
  -Xss512k \
  -XX:MaxMetaspaceSize=256m \
  -jar application.jar
```

| Параметр                    | Назначение                 |
| --------------------------- | -------------------------- |
| `-Xms256m`                  | Начальный размер heap      |
| `-Xmx512m`                  | Максимальный размер heap   |
| `-Xss512k`                  | Размер стека одного потока |
| `-XX:MaxMetaspaceSize=256m` | Ограничение Metaspace      |

Единицы:

```text
k — килобайты
m — мегабайты
g — гигабайты
```

---

## GC logging

В современных Java-приложениях полезно включать GC-логи:

```bash
-Xlog:gc*
```

С записью в файл:

```bash
-Xlog:gc*:file=gc.log:time,uptime,level,tags
```

В логах можно увидеть:

* тип сборки;
* причину запуска;
* продолжительность;
* размер heap до и после;
* объём освобождённой памяти;
* STW-паузы;
* promotion;
* Full GC.

# Типичные ошибки памяти

## StackOverflowError

Причина:

* слишком глубокая или бесконечная рекурсия;
* чрезмерно глубокая цепочка вызовов;
* слишком маленький `-Xss`.

---

## OutOfMemoryError: Java heap space

Причина:

* закончился heap;
* объекты удерживаются ссылками;
* heap недостаточен для нагрузки.

---

## OutOfMemoryError: Metaspace

Причина:

* слишком много классов;
* утечка ClassLoader;
* ограничен Metaspace.

---

## OutOfMemoryError: Direct buffer memory

Причина:

* исчерпана direct memory;
* direct buffers освобождаются медленнее, чем создаются;
* приложение удерживает ссылки на `ByteBuffer`.

---

## Unable to create native thread

Ошибка:

```text
OutOfMemoryError:
unable to create native thread
```

Не обязательно означает переполненный Java heap.

Причины:

* слишком много потоков;
* закончилась native memory;
* ограничения операционной системы;
* слишком крупные стеки потоков.

---

# Что важно в production

Размер памяти нельзя выбирать по принципу «поставим побольше, тогда GC испугается и уйдёт».

Нужно измерять:

* реальное потребление heap после GC;
* allocation rate;
* частоту и продолжительность пауз;
* количество потоков;
* Metaspace;
* native memory;
* direct memory;
* p95 и p99 latency;
* поведение под нагрузкой.

Практический порядок:

```text
1. Снять метрики
2. Посмотреть GC-логи
3. Воспроизвести нагрузку
4. Определить проблему
5. Изменить одну настройку
6. Повторить измерения
```

Слепое изменение сразу десяти JVM-параметров превращает диагностику в гадание на кофейной гуще, только кофе при этом потребляет сервер.

# Практическое задание

Создай класс:

```java
import java.util.ArrayList;
import java.util.List;

public class MemoryExperiment {

    private static final List<byte[]> STORAGE =
            new ArrayList<>();

    public static void main(String[] args)
            throws InterruptedException {

        for (int iteration = 1; iteration <= 1_000; iteration++) {
            byte[] data = new byte[256 * 1024];

            if (iteration % 2 == 0) {
                STORAGE.add(data);
            }

            System.out.printf(
                    "Iteration: %d, stored arrays: %d%n",
                    iteration,
                    STORAGE.size()
            );

            Thread.sleep(100);
        }
    }
}
```

Запусти с ограниченным heap:

```bash
java -Xms32m -Xmx64m MemoryExperiment
```

В VisualVM проследи:

1. Как увеличивается heap.
2. Когда запускается GC.
3. Как выглядит график памяти.
4. Сколько массивов остаётся достижимыми через `STORAGE`.
5. Что изменится, если убрать:

```java
STORAGE.add(data);
```

6. Что изменится, если периодически выполнять:

```java
STORAGE.clear();
```
