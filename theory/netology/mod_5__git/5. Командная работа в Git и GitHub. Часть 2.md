# Словарь разработчика: командная работа в Git и GitHub. Часть 2

## 1. Open-source project

**Определение**
Open-source project — это проект с открытым исходным кодом, в развитие которого могут вносить вклад разные участники сообщества.

**Пример**

```text
Linux, Git, MySQL — известные open-source проекты.
```

---

## 2. Открытый исходный код

**Определение**
Открытый исходный код — это код проекта, который доступен для просмотра, изучения и часто для доработки другими разработчиками.

**Пример**

```text
Разработчик может открыть репозиторий на GitHub,
изучить код и предложить исправление через pull request.
```

---

## 3. Community / комьюнити

**Определение**
Комьюнити — это сообщество людей, которые участвуют в развитии проекта: пишут код, находят ошибки, предлагают улучшения, помогают другим.

**Пример**

```text
В open-source проекте баг может найти один человек,
исправить другой, а проверить третий.
```

---

## 4. Issue

**Определение**
Issue — это задача, сообщение об ошибке или предложение по улучшению проекта в GitHub.

**Пример**

```text
Пользователь заметил ошибку в программе.
Он создаёт issue и описывает проблему.
```

---

## 5. Issues

**Определение**
Issues — это система ведения задач в GitHub. По сути, облегчённый вариант трекера задач.

**Пример**

```text
Во вкладке Issues можно создать задачу,
обсудить её, назначить исполнителя и закрыть после решения.
```

---

## 6. Трекер задач

**Определение**
Трекер задач — это система для создания, обсуждения, распределения и контроля выполнения задач.

**Пример**

```text
GitHub Issues — простой трекер задач внутри репозитория.
Jira — более сложный корпоративный трекер.
```

---

## 7. Bug / баг

**Определение**
Баг — это ошибка в программе или проекте.

**Пример**

```text
Кнопка должна открывать форму,
но при нажатии ничего не происходит.
Это баг.
```

---

## 8. Feature / фича

**Определение**
Фича — это новая функция или возможность в проекте.

**Пример**

```text
Добавить тёмную тему на сайт — это новая фича.
```

---

## 9. Improvement / улучшение

**Определение**
Improvement — это доработка существующей функции, которая делает проект лучше, удобнее или стабильнее.

**Пример**

```text
Форма уже работает, но нужно сделать более понятные сообщения об ошибках.
Это improvement.
```

---

## 10. Feedback / обратная связь

**Определение**
Обратная связь — это сообщения от пользователей или участников команды о проблемах, идеях и пожеланиях по проекту.

**Пример**

```text
Пользователь написал issue:
"На мобильном экране меню открывается некорректно".
```

---

## 11. New issue

**Определение**
New issue — кнопка на GitHub для создания новой задачи.

**Пример**

```text
Repository → Issues → New issue
```

---

## 12. Submit new issue

**Определение**
Submit new issue — кнопка, которая создаёт issue после заполнения заголовка и описания.

**Пример**

```text
Заполнил заголовок задачи, описание проблемы
и нажал Submit new issue.
```

---

## 13. Заголовок issue

**Определение**
Заголовок issue — это короткое название задачи или проблемы.

**Пример хорошо**

```text
Форма регистрации не отправляется после заполнения
```

**Пример плохо**

```text
Ошибка
```

---

## 14. Описание issue

**Определение**
Описание issue — это подробное объяснение задачи, ошибки или предложения.

**Пример**

```markdown
## Что произошло

При нажатии на кнопку "Отправить" форма не отправляется.

## Как повторить

1. Открыть страницу регистрации
2. Заполнить поля
3. Нажать "Отправить"

## Ожидаемый результат

Форма отправляется успешно.
```

---

## 15. Assignee

**Определение**
Assignee — это человек, назначенный ответственным за выполнение задачи.

**Пример**

```text
Issue назначили на разработчика Danil.
Теперь он assignee этой задачи.
```

---

## 16. Labels

**Определение**
Labels — это метки, которыми помечают задачи и pull request для удобной сортировки.

**Пример**

```text
bug
enhancement
documentation
question
design
```

---

## 17. Label

**Определение**
Label — это одна конкретная метка задачи или pull request.

**Пример**

```text
Issue с ошибкой можно пометить label "bug".
```

---

## 18. Mention / упоминание

**Определение**
Mention — это упоминание пользователя через символ `@`.

**Пример**

```markdown
@danil посмотри, пожалуйста, эту задачу.
```

GitHub отправит пользователю уведомление.

---

## 19. Ссылка на issue через `#`

**Определение**
В GitHub можно ссылаться на issue или pull request через символ `#` и номер задачи.

**Пример**

```markdown
Связано с #12
```

---

## 20. Номер issue

**Определение**
Номер issue — это порядковый номер задачи в репозитории.

**Пример**

```text
Issue #7
Pull request #8
```

По номеру удобно ссылаться на задачу в обсуждениях и коммитах.

---

## 21. Closed issue

**Определение**
Closed issue — это закрытая задача. Её нельзя удалить, но можно закрыть, если она решена или больше неактуальна.

**Пример**

```text
Баг исправили.
Issue закрыли.
Теперь она находится в разделе Closed.
```

---

## 22. Pull request

**Определение**
Pull request — это запрос на слияние изменений из одной ветки или форка в другую ветку проекта.

**Пример**

```text
Ты сделал задачу в ветке feature-header.
Создал pull request в main.
Команда проверила код и после этого влила изменения.
```

---

## 23. PR

**Определение**
PR — сокращение от Pull Request.

**Пример**

```text
"Создай PR" = "создай pull request".
```

---

## 24. Запрос на слияние

**Определение**
Запрос на слияние — русское название pull request. Это предложение добавить изменения в проект.

**Пример**

```text
Разработчик не вливает код сразу в main,
а создаёт запрос на слияние.
```

---

## 25. Code review / код-ревью

**Определение**
Code review — это процесс проверки кода другим разработчиком перед слиянием в основную ветку.

**Пример**

```text
Ты сделал pull request.
Тимлид посмотрел код, оставил комментарии,
попросил переименовать переменную и поправить структуру.
```

---

## 26. Reviewer

**Определение**
Reviewer — это человек, который проверяет pull request.

**Пример**

```text
В pull request можно назначить reviewer,
чтобы он провёл code review.
```

---

## 27. Reviewers

**Определение**
Reviewers — поле в pull request, где выбирают людей для проверки кода.

**Пример**

```text
В Reviewers выбрали senior-разработчика.
Он должен проверить изменения перед merge.
```

---

## 28. Merge pull request

**Определение**
Merge pull request — действие, при котором изменения из pull request вливаются в целевую ветку.

**Пример**

```text
Pull request проверили.
Ошибок нет.
Нажали Merge pull request.
Изменения попали в main.
```

---

## 29. Base branch

**Определение**
Base branch — ветка, в которую хотят влить изменения.

**Пример**

```text
base: main
compare: feature-header
```

Значит, изменения из `feature-header` хотят влить в `main`.

---

## 30. Compare branch

**Определение**
Compare branch — ветка, из которой предлагают изменения в pull request.

**Пример**

```text
base: main
compare: fix-readme
```

`fix-readme` — ветка с изменениями.

---

## 31. `compare across forks`

**Определение**
`compare across forks` — функция GitHub, которая позволяет создать pull request из форка в исходный репозиторий.

**Пример**

```text
У тебя нет прав на чужой репозиторий.
Ты сделал fork, изменил код и через compare across forks предложил изменения автору проекта.
```

---

## 32. Fork для pull request

**Определение**
Fork нужен, когда у тебя нет прав на запись в чужой репозиторий, но ты хочешь предложить изменения.

**Пример**

```text
1. Сделал fork чужого проекта
2. Внёс изменения в своём форке
3. Создал pull request в исходный репозиторий
```

---

## 33. Contribute

**Определение**
Contribute — кнопка на GitHub, через которую можно предложить изменения из своего форка в исходный проект.

**Пример**

```text
На странице форка нажал Contribute → Open pull request.
```

---

## 34. Open pull request

**Определение**
Open pull request — действие создания нового pull request.

**Пример**

```text
После изменений в форке GitHub может предложить:
Open pull request.
```

---

## 35. Closing keywords / закрывающие слова

**Определение**
Closing keywords — специальные слова в описании pull request, которые автоматически закрывают связанную issue после слияния.

**Пример**

```markdown
fix #12
close #15
resolve #20
```

Когда pull request будет влит, указанная issue закроется автоматически.

---

## 36. `fix #номер`

**Определение**
`fix #номер` — запись в описании pull request, которая связывает PR с issue и автоматически закрывает задачу после merge.

**Пример**

```markdown
fix #7
```

После слияния pull request задача `#7` будет закрыта.

---

## 37. `close #номер`

**Определение**
`close #номер` — закрывающее слово, которое автоматически закрывает issue после слияния pull request.

**Пример**

```markdown
close #10
```

---

## 38. GitHub Markdown

**Определение**
GitHub Markdown — расширенная версия Markdown, которая используется в GitHub для README, issues, pull request и комментариев.

**Пример**

## 39. GitHub Pages

**Определение**
GitHub Pages — бесплатный хостинг от GitHub для публикации статических сайтов.

**Пример**

```text
Можно загрузить HTML, CSS и JavaScript в репозиторий
и опубликовать сайт через GitHub Pages.
```

---

## 40. Static site / статический сайт

**Определение**
Статический сайт — это сайт, состоящий из готовых файлов HTML, CSS, JavaScript и изображений, без серверной логики.

**Пример**

```text
Лендинг на HTML/CSS можно опубликовать через GitHub Pages.
Java backend-приложение так просто через GitHub Pages не запустить.
```

---

## 41. Hosting / хостинг

**Определение**
Хостинг — это сервис, который размещает сайт в интернете.

**Пример**

```text
GitHub Pages — хостинг для статических сайтов.
```

---

## 42. `/root`

**Определение**
`/root` в настройках GitHub Pages — это корневая папка репозитория, из которой GitHub берёт файлы сайта.

**Пример**

```text
Если index.html лежит прямо в репозитории,
можно выбрать /root.
```

---

## 43. `index.html`

**Определение**
`index.html` — главный HTML-файл сайта, который обычно открывается первым.

**Пример**

```text
GitHub Pages ищет index.html
и показывает его как главную страницу сайта.
```

---

## 44. Ошибка 404 на GitHub Pages

**Определение**
404 — ошибка, которая означает, что страница не найдена. После включения GitHub Pages она может временно появляться, пока сайт публикуется.

**Пример**

```text
Ты включил GitHub Pages.
Сразу открыл ссылку и увидел 404.
Это не всегда ошибка — публикация может занять время.
```

# Коротко: что нужно запомнить

```text
Issue — задача, баг или предложение в GitHub.
Issues — встроенный трекер задач в GitHub.

Assignee — ответственный за задачу.
Labels — метки для сортировки задач.
@username — упоминание человека.
#номер — ссылка на issue или pull request.

Pull request — запрос на слияние изменений.
PR — сокращение от pull request.
Code review — проверка кода перед слиянием.
Reviewer — человек, который проверяет PR.

Если есть права в репозитории:
создаём ветку → пушим ветку → создаём pull request.

Если нет прав:
делаем fork → меняем код в своём форке → создаём pull request в исходный проект.

fix #номер или close #номер — автоматически закрывают issue после слияния PR.

GitHub Pages — бесплатная публикация статических сайтов.
404 после включения GitHub Pages может быть временной.
Danger zone — раздел с опасными действиями, например удалением репозитория.
```

# Мини-шпаргалка процесса pull request

```text
Вариант 1: есть права на репозиторий

1. Создать отдельную ветку
2. Внести изменения
3. Сделать commit
4. Отправить ветку на GitHub
5. Открыть вкладку Pull requests
6. Создать New pull request
7. Выбрать base branch и compare branch
8. Описать изменения
9. Назначить reviewer
10. Дождаться code review
11. После одобрения выполнить merge
```

```text
Вариант 2: нет прав на репозиторий

1. Сделать fork проекта
2. Внести изменения в своём форке
3. Открыть pull request в исходный репозиторий
4. Использовать compare across forks
5. Описать изменения
6. Дождаться проверки от владельцев проекта
```

---

# Мини-шпаргалка GitHub Pages

```text
1. Открыть репозиторий
2. Перейти в Settings
3. Найти Pages
4. Выбрать ветку
5. Выбрать папку, например /root
6. Нажать Save
7. Дождаться публикации сайта
```

```markdown
## Фактический результат

Ничего не происходит.
```
