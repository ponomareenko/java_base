# Тема 5: Методологии разработки — TDD

## Практика разработки

**Определение:**

Практика разработки — конкретный способ выполнения части работы над программой: написания кода, тестирования, проектирования или поставки изменений.

TDD точнее называть практикой или техникой разработки, а не самостоятельной методологией управления проектом. Методологии и фреймворки описывают организацию всей работы команды, а TDD — порядок написания тестов и производственного кода.

---

## Test-driven development (TDD)

**Определение:**

Test-driven development, или TDD, — практика разработки, при которой сначала пишется автоматический тест для небольшого нового поведения, а затем код, необходимый для прохождения этого теста.

Основной цикл TDD:

1. написать один небольшой тест;
2. убедиться, что тест падает по ожидаемой причине;
3. написать минимальный код для прохождения теста;
4. убедиться, что все тесты проходят;
5. улучшить структуру кода без изменения поведения;
6. повторить цикл для следующего поведения.

TDD используют не только для поиска ошибок. Тесты помогают заранее сформулировать контракт будущего кода и влияют на его дизайн.

---

## Test-first development

**Определение:**

Test-first development — подход «сначала тест», при котором тест пишется до производственного кода.

Test-first является важной частью TDD, но одного порядка «тест перед кодом» недостаточно. Полный TDD также предполагает короткие циклы, минимальную реализацию и регулярный рефакторинг.

---

## Red–Green–Refactor

**Определение:**

Red–Green–Refactor — короткий повторяющийся цикл TDD.

### Red

Написать тест для ещё не реализованного поведения и увидеть ожидаемое падение.

```java
class CalculatorTest {

    @Test
    void shouldAddTwoIntegers() {
        Calculator calculator = new Calculator();

        int result = calculator.add(2, 3);

        assertEquals(5, result);
    }
}
```

На этапе Red класс или метод может ещё не существовать. После добавления минимальной заготовки тест должен завершиться ошибкой проверки, а не из-за неправильной настройки окружения.

### Green

Написать самый простой корректный код, достаточный для прохождения теста.

```java
public class Calculator {

    public int add(int first, int second) {
        return first + second;
    }
}
```

Цель этапа Green — быстро получить работающую реализацию, а не сразу построить идеальную архитектуру.

### Refactor

Улучшить структуру производственного и тестового кода, сохраняя поведение и зелёные тесты.

Можно:

* улучшать названия;
* удалять дублирование;
* выделять методы и классы;
* упрощать условия;
* улучшать архитектуру.

После каждого изменения тесты должны продолжать проходить.

---

## Ожидаемое падение теста

**Определение:**

Ожидаемое падение — ситуация, когда новый тест завершается неуспешно именно потому, что требуемое поведение ещё не реализовано.

Этот шаг подтверждает, что тест действительно способен обнаружить отсутствие функциональности.

Если новый тест сразу проходит, возможны причины:

* поведение уже реализовано;
* тест проверяет не то условие;
* проверка написана неправильно;
* тест вообще не запускается.

В продакшене важно смотреть не только на красный результат, но и на причину падения.

---

## Минимальная реализация

**Определение:**

Минимальная реализация — самый простой код, который корректно удовлетворяет текущему тесту.

Она помогает не проектировать функции «на будущее», требования к которым ещё не подтверждены тестами.

Минимальная реализация не означает намеренно плохой код. После получения зелёного результата наступает этап рефакторинга.

---

## Unit test

**Определение:**

Unit test, или модульный тест, — быстрый автоматический тест небольшой единицы поведения в изоляции от ненужных внешних систем.

Такой единицей может быть метод, класс или небольшая группа тесно связанных объектов. Важнее проверять наблюдаемое поведение, а не внутреннее устройство метода.

**Пример:**

```java
@Test
void shouldThrowExceptionWhenDivisorIsZero() {
    Calculator calculator = new Calculator();

    assertThrows(
            ArithmeticException.class,
            () -> calculator.divide(10, 0)
    );
}
```

Модульные тесты особенно удобны для TDD, потому что быстро запускаются и дают точную обратную связь. Но TDD не запрещает интеграционные или приёмочные тесты.

---

## System under test (SUT)

**Определение:**

System under test, или SUT, — объект или часть системы, поведение которой проверяет конкретный тест.

```java
Calculator calculator = new Calculator(); // Calculator — SUT
```

Термин помогает отличать проверяемый объект от его зависимостей и тестовой инфраструктуры.

---

## Test case

**Определение:**

Test case, или тестовый сценарий, — конкретная проверка поведения при заданных исходных данных и ожидаемом результате.

Хороший тестовый сценарий отвечает на три вопроса:

1. в каких условиях выполняется код;
2. какое действие совершается;
3. какой результат ожидается.

Название теста должно описывать поведение:

```java
void shouldReturnDifferenceOfTwoIntegers()
```

Название вроде `testSubtraction()` сообщает меньше информации о проверяемом результате.

---

## Arrange–Act–Assert (AAA)

**Определение:**

Arrange–Act–Assert — структура теста из трёх частей:

* Arrange — подготовить данные и зависимости;
* Act — выполнить проверяемое действие;
* Assert — проверить результат.

**Пример:**

```java
@Test
void shouldMultiplyTwoIntegers() {
    // Arrange
    Calculator calculator = new Calculator();

    // Act
    int result = calculator.multiply(4, 5);

    // Assert
    assertEquals(20, result);
}
```

В коротких тестах комментарии можно не писать: пустые строки уже визуально разделяют этапы.

---

## Assertion

**Определение:**

Assertion — проверка, сравнивающая фактическое поведение программы с ожидаемым.

Основные проверки JUnit 5:

```java
assertEquals(expected, actual);
assertTrue(condition);
assertFalse(condition);
assertNull(value);
assertNotNull(value);
assertThrows(ExceptionType.class, executable);
```

Для сравнения значений лучше использовать специализированную проверку:

```java
assertEquals(expected, actual);
```

вместо:

```java
assertTrue(expected == actual);
```

`assertEquals()` яснее показывает намерение и обычно формирует более полезное сообщение об ошибке.

---

## Test suite

**Определение:**

Test suite, или набор тестов, — совокупность автоматических тестов проекта или его части.

Перед рефакторингом и после него запускают весь подходящий набор тестов, а не только последний добавленный тест. Это позволяет обнаруживать поломки старого поведения.

---

## Регрессия

**Определение:**

Регрессия — повторное появление ранее исправленной ошибки или поломка существующего поведения после изменения кода.

**Регрессионный тест** фиксирует ожидаемое поведение и падает, если проблема появляется снова.

При исправлении дефекта через TDD сначала пишут тест, воспроизводящий ошибку, затем исправляют код:

1. тест подтверждает наличие дефекта;
2. исправление делает тест зелёным;
3. тест остаётся в наборе и защищает от повторения ошибки.

---

## Рефакторинг

**Определение:**

Рефакторинг — изменение внутренней структуры кода без изменения его наблюдаемого поведения.

Примеры:

* переименование переменной;
* выделение метода;
* удаление дублирования;
* разбиение большого класса;
* упрощение сложного условия.

Тесты снижают риск рефакторинга, но только в пределах поведения, которое они действительно проверяют.

---

## Test double

**Определение:**

Test double, или тестовый двойник, — объект, который заменяет настоящую зависимость во время теста.

Основные разновидности:

| Вид | Назначение |
|---|---|
| Dummy | Передаётся для заполнения параметра, но не используется |
| Stub | Возвращает заранее заданные ответы |
| Fake | Имеет упрощённую рабочую реализацию, не подходящую для продакшена |
| Spy | Записывает информацию о вызовах |
| Mock | Проверяет ожидаемые взаимодействия между объектами |

Моки не являются обязательным условием TDD. Их используют, когда нужно изолировать медленную, нестабильную или внешнюю зависимость.

Чрезмерное количество моков часто означает, что тест слишком сильно привязан к внутренней реализации.

---

## Детерминированный тест

**Определение:**

Детерминированный тест — тест, который при одинаковом коде и условиях всегда даёт одинаковый результат.

Для обычного модульного теста лучше использовать явно заданные значения:

```java
@Test
void shouldDivideTwoIntegers() {
    Calculator calculator = new Calculator();

    int result = calculator.divide(10, 2);

    assertEquals(5, result);
}
```

Случайные данные без фиксированного seed затрудняют повторение ошибки:

```java
int divisor = new Random().nextInt(); // Может оказаться равным 0
```

Для проверки разных наборов данных лучше использовать параметризованный тест:

```java
@ParameterizedTest
@CsvSource({
        "10, 2, 5",
        "9, 3, 3",
        "-8, 2, -4"
})
void shouldDivideIntegers(int dividend, int divisor, int expected) {
    Calculator calculator = new Calculator();

    assertEquals(expected, calculator.divide(dividend, divisor));
}
```

## Flaky test

**Определение:**

Flaky test — нестабильный тест, который без изменения кода то проходит, то падает.

Частые причины:

* случайные данные;
* зависимость от времени;
* порядок выполнения тестов;
* общие изменяемые данные;
* сеть, файловая система или база данных;
* проблемы синхронизации.

Flaky-тесты подрывают доверие к тестовому набору. Их нужно исправлять, а не просто перезапускать до зелёного результата.

---

## Тестируемость

**Определение:**

Тестируемость — свойство кода, показывающее, насколько легко проверить его поведение автоматически.

Тестируемый код обычно:

* имеет небольшие и понятные обязанности;
* получает зависимости извне;
* не скрывает важные зависимости в глобальном состоянии;
* отделяет бизнес-логику от базы данных, сети и пользовательского интерфейса;
* возвращает наблюдаемый результат.

TDD часто повышает тестируемость, потому что разработчик сначала использует будущий API из теста и замечает неудобный дизайн раньше.

---

## Преимущества TDD

* требования превращаются в исполняемые примеры;
* ошибки обнаруживаются короткими циклами;
* формируется регрессионный набор тестов;
* безопаснее выполнять рефакторинг;
* код обычно проектируется с учётом тестируемости;
* проще реализовывать поведение небольшими шагами.

TDD снижает риски, но не гарантирует отсутствие ошибок и не заменяет code review, интеграционные, системные, нагрузочные и ручные проверки.

---

## Ограничения TDD

* требуется навык декомпозиции требований на маленькие сценарии;
* тестовый код тоже нужно сопровождать;
* плохие тесты могут закрепить плохую архитектуру;
* чрезмерная привязка к реализации усложняет рефакторинг;
* интерфейсы, конкурентный код и интеграции требуют дополнительных видов тестирования;
* нефункциональные характеристики проверяются специализированными тестами.

TDD не означает, что нужно покрывать моками каждый метод. Проверять следует значимое поведение и риски системы.

# Практическое задание

## Задание 1

Реализуй через цикл Red–Green–Refactor метод:

```java
boolean isEven(int number)
```

Порядок работы:

1. сначала напиши тест для чётного числа;
2. запусти его и зафиксируй ожидаемое падение;
3. добавь минимальную реализацию;
4. добавь сценарии для нечётного и отрицательного чисел;
5. выполни рефакторинг.

---

## Задание 2

Напиши тесты для метода:

```java
int divide(int dividend, int divisor)
```

Проверь:

* обычное деление;
* отрицательное число;
* целочисленное округление;
* деление на ноль через `assertThrows()`.

Не используй случайные значения.

---

## Задание 3

Перепиши тест со слайда в стиле JUnit 5 и Arrange–Act–Assert:

```java
assertTrue(var1 + var2 == sumResult);
```

Используй `assertEquals()` и дай тесту название, описывающее ожидаемое поведение.

---

## Задание 4

Создай параметризованный тест для умножения со следующими сценариями:

```text
2 × 3 = 6
0 × 10 = 0
-4 × 5 = -20
-3 × -2 = 6
```

Используй `@ParameterizedTest` и `@CsvSource`.

## Задание 5

Ответь письменно:

1. Почему в TDD новый тест сначала должен упасть?
2. Чем этап Green отличается от Refactor?
3. Почему тесты не гарантируют отсутствие всех ошибок?
4. Чем stub отличается от mock?
5. Почему случайные данные могут сделать тест flaky?
6. Чем TDD отличается от простого написания тестов после реализации?

## Неточности в презентации

* TDD точнее называть практикой или техникой разработки, а не полной методологией управления разработкой.
* TDD чаще всего использует быстрые модульные тесты, но не ограничивается только ими и моками.
* Случайные значения делают примеры нестабильными; в тесте деления случайный делитель может оказаться равным нулю.
* Для сравнения результата `assertEquals(expected, actual)` понятнее и информативнее, чем `assertTrue(expected == actual)`.
* Английское название операции вычитания — `subtraction`, поэтому методы `substraction()` и `testSubstraction()` названы с ошибкой.
* TDD помогает снижать риски, но само по себе не гарантирует расширяемость, хороший дизайн и отсутствие дефектов.
