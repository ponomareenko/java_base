# Тема 4: Коллекции для параллельной работы

## Конкурентная коллекция

**Определение:**

Конкурентная коллекция (concurrent collection) — коллекция, рассчитанная на безопасную работу нескольких потоков без необходимости вручную защищать каждый отдельный вызов её методов.

Такие коллекции находятся преимущественно в пакете `java.util.concurrent`.

**Важно:**

Потокобезопасность отдельных методов не делает атомарной произвольную последовательность действий:

```java
if (!users.containsKey(userId)) {
    users.put(userId, user); // Между проверкой и записью может вмешаться другой поток
}
```

Для составных действий нужно использовать специальные атомарные методы коллекции:

```java
users.putIfAbsent(userId, user);
```

---

## Copy-on-write

**Определение:**

Copy-on-write — подход, при котором операция чтения использует существующие данные, а при изменении создаётся их новая копия.

Цена чтения получается низкой, но каждое добавление, удаление или изменение требует копирования массива. Поэтому подход подходит для небольших коллекций с частыми чтениями и редкими изменениями.

---

## `CopyOnWriteArrayList`

**Определение:**

`CopyOnWriteArrayList<E>` — потокобезопасная реализация `List`, в которой изменяющие операции создают новую копию внутреннего массива.

**Когда использовать:**

* элементов относительно немного;
* чтений и обходов намного больше, чем изменений;
* читатели не должны блокировать друг друга;
* допустимо, что уже созданный итератор не увидит последующие изменения.

Типичный пример — список обработчиков событий или конфигураций, которые редко обновляются.

**Пример:**

```java
public class EventPublisher {
    private final List<Consumer<String>> listeners =
            new CopyOnWriteArrayList<>();

    public void addListener(Consumer<String> listener) {
        listeners.add(listener);
    }

    public void publish(String event) {
        listeners.forEach(listener -> listener.accept(event));
    }
}
```

`CopyOnWriteArrayList` поддерживает `sort()`. Ограничение относится не к сортировке списка, а к изменению коллекции через её snapshot-итератор.

---

## Snapshot-итератор

**Определение:**

Snapshot-итератор — итератор, который обходит снимок массива, существовавший в момент создания итератора.

Он:

* не выбрасывает `ConcurrentModificationException` из-за параллельных изменений списка;
* не видит элементы, добавленные или удалённые после его создания;
* не поддерживает `remove()`, а `ListIterator` также не поддерживает `add()` и `set()`.

**Пример:**

```java
CopyOnWriteArrayList<String> names =
        new CopyOnWriteArrayList<>(List.of("Alice", "Bob"));

Iterator<String> iterator = names.iterator();
names.add("Carol");

iterator.forEachRemaining(System.out::println);
// Alice
// Bob
```

Снимок копирует массив ссылок, а не сами объекты. Если объект внутри списка изменяемый, его состояние всё равно может измениться.

## `BlockingQueue`

**Определение:**

`BlockingQueue<E>` — потокобезопасная очередь, которая умеет приостанавливать поток при попытке:

* забрать элемент из пустой очереди;
* поместить элемент в заполненную ограниченную очередь.

`BlockingQueue` часто используется для передачи задач или данных между потоками.

**Пример:**

```java
BlockingQueue<String> tasks = new ArrayBlockingQueue<>(100);

public void submit(String task) throws InterruptedException {
    tasks.put(task); // Ждёт, если очередь заполнена
}

public String receive() throws InterruptedException {
    return tasks.take(); // Ждёт, если очередь пуста
}
```

Методы `put()` и `take()` реагируют на прерывание, поэтому `InterruptedException` нельзя бездумно проглатывать.

## Producer-consumer

**Определение:**

Producer-consumer — модель взаимодействия, в которой одни потоки создают данные или задачи, а другие получают и обрабатывают их через общую очередь.

* producer — производитель;
* consumer — потребитель;
* очередь разделяет скорость производства и обработки.

**Пример:**

```java
BlockingQueue<String> orders = new ArrayBlockingQueue<>(50);

Runnable producer = () -> {
    try {
        orders.put("order-42");
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
    }
};

Runnable consumer = () -> {
    try {
        String order = orders.take();
        System.out.println("Обрабатываем: " + order);
    } catch (InterruptedException exception) {
        Thread.currentThread().interrupt();
    }
};
```

В продакшене ограниченная очередь защищает приложение от бесконечного накопления задач при медленных потребителях.

---

## Ограниченная очередь

**Определение:**

Ограниченная очередь (bounded queue) — очередь с максимальным количеством элементов.

Когда она заполнена, производитель должен ждать, отказаться от добавления или обработать переполнение другим способом. Это создаёт обратное давление (backpressure): быстрый производитель вынужден учитывать скорость потребителя.

Неограниченные очереди удобнее, но под нагрузкой могут заполнить память. Поэтому в продакшене ёмкость очереди обычно задают осознанно.

---

## Группы методов `BlockingQueue`

| Операция | Исключение | Специальное значение | Ожидание | Ожидание с тайм-аутом |
|---|---|---|---|---|
| Добавить | `add(e)` | `offer(e)` | `put(e)` | `offer(e, time, unit)` |
| Извлечь и удалить | `remove()` | `poll()` | `take()` | `poll(time, unit)` |
| Посмотреть начало | `element()` | `peek()` | — | — |

Различия:

* `add()` выбрасывает исключение, если ограниченная очередь заполнена;
* `offer()` сразу возвращает `false`, если элемент добавить нельзя;
* `put()` ждёт свободного места;
* `offer(..., timeout)` ждёт не дольше указанного времени;
* `remove()` выбрасывает исключение для пустой очереди;
* `poll()` возвращает `null` для пустой очереди;
* `take()` ждёт появления элемента;
* `peek()` читает начало очереди, не удаляя элемент.

Для серверного кода часто удобнее `offer()` с тайм-аутом: поток не зависает навсегда, а переполнение можно обработать явно.

## `ArrayBlockingQueue`

**Определение:**

`ArrayBlockingQueue<E>` — ограниченная блокирующая FIFO-очередь на основе массива.

После создания её ёмкость изменить нельзя. Внутренний массив используется как кольцевой буфер: после достижения конца массива позиции снова используются с его начала.

**Пример:**

```java
BlockingQueue<String> messages = new ArrayBlockingQueue<>(1_000);

boolean accepted = messages.offer("event", 200, TimeUnit.MILLISECONDS);

if (!accepted) {
    System.out.println("Очередь переполнена");
}
```

Конструктор позволяет включить честный порядок доступа:

```java
BlockingQueue<String> fairQueue = new ArrayBlockingQueue<>(100, true);
```

При `fair = true` ожидающие производители и потребители получают доступ примерно в FIFO-порядке. Это уменьшает риск голодания, но обычно снижает пропускную способность.

`null` хранить нельзя: значение `null` используется методами вроде `poll()` как признак отсутствия элемента.

---

## Основные конкурентные очереди

| Класс | Особенность | Когда применять |
|---|---|---|
| `ConcurrentLinkedQueue` | Неограниченная неблокирующая FIFO-очередь | Нужны быстрые операции без ожидания |
| `ConcurrentLinkedDeque` | Неблокирующая двусторонняя очередь | Добавление и извлечение с обоих концов |
| `ArrayBlockingQueue` | Ограниченная FIFO-очередь на массиве | Нужна фиксированная ёмкость и backpressure |
| `LinkedBlockingQueue` | FIFO-очередь на связанных узлах, ёмкость задаётся необязательно | Нужна блокирующая очередь с гибкой ёмкостью |
| `LinkedBlockingDeque` | Блокирующая двусторонняя очередь | Ожидание при работе с обоими концами |
| `PriorityBlockingQueue` | Неограниченная очередь по приоритету | Сначала нужно обрабатывать более приоритетные элементы |
| `SynchronousQueue` | Не хранит элементы; передача происходит напрямую между потоками | Нужна синхронная передача задачи потребителю |
| `LinkedTransferQueue` | Производитель может дождаться получения элемента потребителем | Передача сообщений с подтверждением получения |
| `DelayQueue` | Элемент извлекается только после истечения задержки | Отложенные задачи, тайм-ауты и повторные попытки |

**Важно:**

`PriorityBlockingQueue` логически не ограничена, поэтому её `put()` не ждёт свободного места. Порядок обхода итератором также не обязан совпадать с порядком извлечения элементов.

## `ConcurrentHashMap`

**Определение:**

`ConcurrentHashMap<K, V>` — потокобезопасная хеш-таблица, которая поддерживает параллельные чтения и высокую степень параллельности обновлений.

Чтения обычно не требуют блокировки всей таблицы. Обновления разных ключей могут выполняться параллельно.

**Пример:**

```java
ConcurrentMap<String, Integer> wordCounts = new ConcurrentHashMap<>();

public void registerWord(String word) {
    wordCounts.merge(word, 1, Integer::sum);
}
```

`merge()` атомарно выполняет обновление для конкретного ключа. Вариант через `get()` и `put()` был бы подвержен состоянию гонки:

```java
Integer current = wordCounts.get(word);
wordCounts.put(word, current == null ? 1 : current + 1); // Небезопасная комбинация
```

`ConcurrentHashMap` не допускает `null` ни в качестве ключа, ни в качестве значения. Благодаря этому `null`, возвращённый `get()`, однозначно означает отсутствие сопоставления.

Современная реализация `ConcurrentHashMap` не делит таблицу на фиксированные сегменты. Описание сегментной архитектуры относится к старым реализациям до Java 8.

---

## Атомарные методы `ConcurrentHashMap`

| Метод | Назначение |
|---|---|
| `putIfAbsent(key, value)` | Добавляет значение, только если ключ отсутствует |
| `remove(key, value)` | Удаляет запись, только если ключ связан с указанным значением |
| `replace(key, oldValue, newValue)` | Заменяет значение при совпадении со старым |
| `computeIfAbsent(key, function)` | Вычисляет значение, если ключ отсутствует |
| `compute(key, function)` | Пересчитывает значение для ключа |
| `merge(key, value, function)` | Добавляет начальное значение или объединяет его с существующим |

**Пример частотного словаря:**

```java
ConcurrentHashMap<String, LongAdder> frequencies =
        new ConcurrentHashMap<>();

public void register(String word) {
    frequencies
            .computeIfAbsent(word, ignored -> new LongAdder())
            .increment();
}
```

Атомарность гарантируется для операции над конкретным ключом, а не для произвольной бизнес-операции над всей картой.

Функции, переданные в `compute...()` и `merge()`, должны быть короткими и не должны изменять эту же карту рекурсивно. Пока вычисляется значение, другие обновления этого ключа могут ожидать.

## Weakly consistent iterator

**Определение:**

Weakly consistent iterator — итератор конкурентной коллекции, который может безопасно работать одновременно с её изменением.

Он:

* не выбрасывает `ConcurrentModificationException` из-за конкурентных изменений;
* гарантированно видит элементы, существовавшие и не удалённые к моменту их посещения;
* может увидеть часть изменений, произошедших после создания итератора;
* не предоставляет атомарный снимок всей коллекции.

Так ведут себя, например, итераторы `ConcurrentHashMap` и `ConcurrentLinkedQueue`.

Не путай его со snapshot-итератором `CopyOnWriteArrayList`: snapshot-итератор работает с зафиксированной версией массива, а weakly consistent iterator может наблюдать некоторые новые изменения.

---

## `ConcurrentHashMap.newKeySet()`

**Определение:**

`ConcurrentHashMap.newKeySet()` — фабричный метод, создающий потокобезопасное множество, построенное на `ConcurrentHashMap`.

**Пример:**

```java
Set<String> onlineUsers = ConcurrentHashMap.newKeySet();

onlineUsers.add("alice");
onlineUsers.add("bob");
```

Внутри элементы множества хранятся как ключи карты, связанные с техническим значением `Boolean.TRUE`.

Такое множество подходит для частых конкурентных добавлений, удалений и проверок наличия элемента.

Если нужен отсортированный конкурентный набор, используется `ConcurrentSkipListSet`.

---

## `CopyOnWriteArraySet`

**Определение:**

`CopyOnWriteArraySet<E>` — потокобезопасное множество, которое использует внутри `CopyOnWriteArrayList`.

Оно подходит, когда:

* множество обычно небольшое;
* обходов намного больше, чем изменений;
* требуется snapshot-итератор;
* элементы должны быть уникальными.

**Пример:**

```java
Set<String> featureFlags = new CopyOnWriteArraySet<>();

featureFlags.add("NEW_CHECKOUT");
featureFlags.add("NEW_CHECKOUT");

System.out.println(featureFlags.size()); // 1
```

При частых добавлениях и удалениях обычно лучше использовать множество из `ConcurrentHashMap.newKeySet()`.

---

## Как выбрать коллекцию

| Задача | Подходящая коллекция |
|---|---|
| Небольшой список, очень много чтений, редкие изменения | `CopyOnWriteArrayList` |
| Небольшое множество, очень много обходов, редкие изменения | `CopyOnWriteArraySet` |
| Часто изменяемое конкурентное множество | `ConcurrentHashMap.newKeySet()` |
| Часто изменяемая карта | `ConcurrentHashMap` |
| Ограниченная очередь producer-consumer | `ArrayBlockingQueue` |
| Блокирующая FIFO-очередь на связанных узлах | `LinkedBlockingQueue` |
| Неблокирующая FIFO-очередь | `ConcurrentLinkedQueue` |
| Прямая передача элемента от производителя потребителю | `SynchronousQueue` |
| Очередь задач по приоритету | `PriorityBlockingQueue` |
| Отложенная обработка | `DelayQueue` |
| Отсортированная конкурентная карта или множество | `ConcurrentSkipListMap` / `ConcurrentSkipListSet` |

Выбор следует делать по характеру нагрузки, а не только по наличию слова `Concurrent` в названии.

## Неточности в презентации

* `CopyOnWriteArrayList` — не единственный способ получить потокобезопасный `List`. Существуют также `Vector` и `Collections.synchronizedList()`, но у них другая модель синхронизации.
* `CopyOnWriteArrayList` существует с Java 5, а не с Java 6.
* `CopyOnWriteArrayList` поддерживает `sort()`. Не поддерживается изменение структуры коллекции через snapshot-итератор.
* Современный `ConcurrentHashMap`, начиная с Java 8, не использует фиксированные сегменты как основную архитектуру.
* Последний слайд подписан `ConcurrentHashMap`, но перечисленные свойства относятся к `CopyOnWriteArraySet`.
